STAGE 03Character Stats · Apache Doris

벡터화된 MPP의 해부도.

FE는 메타데이터·플래너·코디네이터, BE는 데이터·실행 노드. 두 노드 사이에 흐르는 것은 Thrift RPC와 Brpc, 그리고 columnar Block 이다.

Storage Hierarchy — 한 행은 어디에 떨어지는가

논리: Database → Table → Partition → Bucket(=Tablet). 물리: Tablet → Rowset(트랜잭션 1건) → Segment(파일 1개) → Column → Page(I/O 단위, 64KiB). 각 페이지마다 ZoneMap(min/max/null)·BloomFilter·Bitmap Index·Inverted Index(2.0+) 가 붙는다 — 즉 술어는 페이지 단위로 스킵된다. 

orders/                     # 한 테이블의 BE 디스크 경로 단순화
└── partition=2026_05/
    └── tablet_10341/        # bucket(=tablet) 단위, replica 3개 분산
        ├── rowset_3.dat     # 트랜잭션 publish 한 건
        │   └── segment_0/
        │       ├── ord_id  # 행 ordinal
        │       ├── data    # 컬럼별 page (64KiB)
        │       ├── zone    # ZoneMap (min/max/null)
        │       ├── bloom   # 옵션
        │       ├── bitmap  # 옵션
        │       ├── inv     # Inverted index (2.0+)
        │       └── pk_idx  # PrimaryKey index (Unique-MoW)
        └── delete_bitmap/   # MoW 핵심: (segment_id, ord_id) 비트맵

3가지 Key Model — 한 번 정하면 못 바꾼다

Duplicate Key

중복 허용 + 정렬

Key 컬럼을 정렬 인덱스로만 사용. 모든 행을 그대로 보관. 가장 자유롭고 분석 쿼리에 유리. 로그·이벤트 사실 테이블에 적합.

Unique Key

키별 최신 1행만

PK 단위 row-level UPSERT. 1.2부터 MoW가 기본. 차원/운영계 미러링에 적합.

Aggregate Key

선집계 저장

Key별로 SUM/MAX/MIN/REPLACE를 저장 시점에 적용. 지표 사전집계, 광고 리포팅에 적합.

MoR vs MoW — Unique Key의 두 갈림길

커널 딥다이브 — MoW가 실제로 하는 일 (DeleteBitmap, sequence column, compaction)

MoW의 핵심은 두 자료구조다 — PrimaryKeyIndex와 DeleteBitmap.

1) Write Path · 각 BE는 load 채널로 들어온 row를 PK 정렬해 메모리 버퍼에 쌓는다. flush 직전, 이전 segment들의 PK Index(B+ 트리 + Bloom)를 차례로 lookup. 같은 PK가 발견되면 그 segment의 (segment_id, ordinal_id)를 새 segment의 DeleteBitmap에 기록한다 (RoaringBitmap). 새 데이터는 새 segment로 flush 되고, 트랜잭션은 publish 단계에서 FE에 보고된다.

2) Read Path · 쿼리 실행기는 segment를 스캔할 때 해당 segment의 DeleteBitmap을 ZoneMap·Bloom과 함께 push-down. 비트가 켜진 ordinal은 그냥 건너뛴다 — SELECT 시점엔 병합이 없다. 그래서 술어 pushdown이 가능하고, MoR 대비 쿼리 비용이 일정하다.

3) Compaction · cumulative compaction은 작은 rowset들을 묶고, base compaction은 누적된 cumulative 결과를 base와 머지하면서 DeleteBitmap에 마킹된 행을 물리적으로 제거한다. 즉 디스크 사이즈와 read amplification은 시간이 지날수록 자연스럽게 감소.

4) Sequence Column · 같은 PK에 늦게 도착한 행이 더 작은 timestamp를 가지면? 테이블 정의 시 sequence_col(또는 sequence_type)을 받아 비교. 새 값이 sequence가 작으면 현재 segment의 행을 DeleteBitmap에 마킹하고 옛 값을 유지. 즉 out-of-order CDC에 강하다.

5) Partial Update · 컬럼 일부만 업데이트하려면 MoW에서 partial_columns 옵션을 켠다. 빠진 컬럼은 PK index lookup으로 옛 행에서 읽어와 새 segment에 채운 후 옛 행을 DeleteBitmap에 마킹.

Pipeline X — morsel-driven NUMA-aware 실행 엔진

Doris BE는 columnar Block(보통 1024 rows)을 단위로 처리한다. 연산자는 Block을 in/out으로 받는 함수이고, 표현식은 SIMD 가속된 함수 디스패치 테이블로 실행된다.

2.0부터 도입된 Pipeline X는 NUMA-aware morsel scheduling이다. 쿼리 fragment를 morsel(작은 task)로 쪼개고, 각 코어가 자기 큐에서 work-steal 한다. Local Exchange로 같은 노드 안에서는 RPC 없이 컬러 데이터를 주고받는다 — Brpc는 노드 사이 shuffle/broadcast 에만 쓰임.

Hash Join은 build/probe 두 페이즈로 나뉘고, build 입력이 작으면 broadcast, 크면 shuffle hash join 선택. Aggregation은 two-phase: BE-local pre-aggregation → shuffle → final aggregation. Xiaomi가 "Paimon SDK의 single-thread MoR sort 병목"을 제거할 때 도입한 게 바로 이 분산 Hash 집계다.

Materialized View — Sync(Rollup) vs Async

Sync MV (Rollup) · 베이스 테이블과 같은 트랜잭션에서 동기 갱신. 단일 테이블 GROUP BY/표현식만 지원, 업데이트마다 비용 발생. Aggregate Key/Duplicate에서 주로 사용.

Async MV (3.0+) · 별도 스케줄로 비동기 새로고침. 다중 테이블 조인·외부 카탈로그(Paimon/Iceberg) 모두 지원. Xiaomi가 추가한 snapshot-level incremental refresh는 이 Async MV에 들어갔다 — 변경된 snapshot 범위만 다시 계산, 비파티션 거대 테이블에도 분 단위 갱신 가능.

옵티마이저(CBO)가 Transparent Query Rewrite로 베이스 테이블 쿼리를 자동으로 MV로 바꿔준다 — 사용자는 평소처럼 베이스를 쿼리하고, 가속은 자동.

Ingestion 3대 — Stream Load · Routine Load · Group Commit

Stream Load · HTTP PUT 한 방으로 CSV/JSON 적재. 외부 ETL이 호출하기 좋다. 한 번에 수 GB까지 처리.

Routine Load · BE에 내장된 Kafka consumer. 토픽-파티션 단위 task로 지속 적재. 운영에서는 Debezium → Kafka 다음에 가장 자주 쓰이는 sink 패턴.

Group Commit · 다수의 작은 INSERT를 BE 내부에서 큐잉/배치. 클라이언트는 즉시 응답을 받고, FE는 일정 주기마다 한 번에 publish. 이로써 commit fan-out과 메타 부담이 폭발하는 걸 막는다 — 실시간 대량 적재에 필수.

Multi-Catalog — Internal · Hive · Iceberg · Paimon · Hudi · JDBC · ES

Doris는 카탈로그를 마운트 포인트처럼 다룬다. 한 SQL 안에서 internal.db.t·hive.bd.t·paimon_lake.ods.t를 자유롭게 join 할 수 있다.

Paimon Catalog는 2.1+부터 정식 지원. 백엔드는 filesystem warehouse / Hive Metastore / DLF REST 셋 중 하나를 고른다. Doris는 Paimon snapshot을 직접 읽고, native Parquet reader가 페이지 단위 술어 pushdown을 적용한다.

3.0의 Compute Group은 같은 메타데이터 위에서 워크로드별로 BE를 격리해 자원 보호한다 — Xiaomi의 self-service 클러스터 운영 패턴.

STAGE 03 · KERNELQuery Lifecycle · CBO · Shuffle · Failure

SQL이 Block이 되는 여정.

SQL 한 줄이 Doris BE의 컬럼별 64KiB 페이지를 두드리기까지 — Parser·CBO·Coordinator·Pipeline X·Brpc가 각각 무슨 일을 하는지 단계별로 해부한다. 이 흐름을 그릴 수 있으면 EXPLAIN 출력이 서사처럼 읽힌다.

Query Lifecycle — 8단계 Swim-Lane

FE Coordinator는 ⑤까지 책임지고, ⑥부터는 BE의 Pipeline X 스케줄러가 morsel 단위로 분배한다. Block은 BE 사이를 Brpc로 흐르고, 같은 BE 안에서는 Local Exchange로 RPC 없이 전달된다.

① SQL Parse — JSqlParser 기반 AST 생성

FE 진입점은 StmtExecutor. JSqlParser가 SQL을 LL(*) 파싱해 StatementBase 트리로 만든다. SET·USE·SELECT·INSERT 등 분기. 표현식 트리는 Expr 노드(SlotRef, FunctionCallExpr, BinaryPredicate 등)로 정규화되고, 권한 체크가 이 단계에서 수행된다.

Doris 2.1+는 차세대 옵티마이저 Nereids가 기본. Nereids는 Cascades 스타일 규칙 기반으로 변환·최적화·물리화를 한 트리에서 처리한다. 이전 옵티마이저(Legacy Planner)와 코드 경로가 분리돼 있다.

② Logical Plan — Nereids analyzer 규칙 30+

Logical Plan은 관계대수 트리: LogicalProject·LogicalFilter·LogicalJoin·LogicalAggregate·LogicalOlapScan. Analyzer는 30개 이상 규칙을 적용 — 이름 해석, 타입 추론, 함수 시그니처 매칭, 서브쿼리 unnesting, CTE 인라인, predicate push-down, column pruning, projection merge.

Materialized View matcher가 이 단계에서 등판한다 — Transparent Query Rewrite: 베이스 테이블 쿼리가 사전 정의된 MV의 부분집합이면 자동 치환. 매칭은 Compensation 알고리즘(MV 트리와 쿼리 트리의 차이를 보충 가능한가)을 사용한다.

③ CBO Optimize — 통계, NDV, histogram, join-order DP

CBO는 비용 모델 + 통계 기반 dynamic programming. 비용은 NetworkCost + CpuCost + MemoryCost의 가중합. 통계는 information_schema.column_statistics에 저장: row_count, ndv(HLL 추정), nulls, min/max, avg_size, hot_value(top-k). 2.1+에서 equi-height histogram이 추가돼 selectivity 추정이 정밀해졌다.

Join order는 4 테이블 이하면 exhaustive DP, 그 이상이면 left-deep greedy + heuristic. star-join detection이 켜져 있으면 fact table을 중심으로 dim table을 broadcast로 매단다.

통계가 stale 하면 ANALYZE TABLE t WITH SAMPLE PERCENT 10로 표본 갱신, 또는 자동 분석(auto.analyze.enable=true) 의존. 외부 카탈로그(Paimon/Hive)는 partition-level 통계까지 받아쓸 수 있다.

ANALYZE TABLE orders WITH SAMPLE PERCENT 10;
SHOW COLUMN STATS orders;
-- ndv·null_count·data_size·hot_values 확인

EXPLAIN SELECT /*+ SET_VAR(enable_nereids_planner=true) */
  o.region, SUM(o.amount)
FROM orders o JOIN dim_region r ON o.region_id = r.id
GROUP BY o.region;
-- 출력에 ndv, distribute mode(BROADCAST/SHUFFLE), runtime filter 노출
④ Physical Plan — Distribute mode, Runtime Filter 주입

Logical join 한 노드가 물리적으로는 broadcast hash join(작은 build 입력) 또는 shuffle hash join(양쪽 큰 입력)으로 결정된다. colocated join은 두 테이블이 동일 distribution(같은 bucket key + 같은 bucket count)일 때 RPC 없이 BE-local 처리.

옵티마이저는 build 측에서 Runtime Filter를 주입한다. 종류는 입력 카디널리티에 따라:

  • IN — build row가 적을 때(보통 ≤1024). probe 측 SQL의 WHERE가 그대로 in-list로 변환.
  • BLOOM — 중간 규모(수만~수백만). probe 측 컬럼에 Bloom 필터 적용, 거짓 양성률 보통 1%.
  • MIN_MAX — 정렬 가능한 타입의 범위형 스킵. ZoneMap pushdown과 결합되면 페이지 단위 스캔이 통째로 빠진다.

EXPLAIN 출력에 RuntimeFilter[id=RF000, type=BLOOM, build=col_a, target=col_b] 형태로 표시. probe → build의 의존이 있어 build가 끝나야 probe가 본격적으로 스캔하는 게 정상.

⑤ Fragment Tree — DataSink·Exchange Operator

Plan은 Plan Fragment로 자른다. 같은 BE 안에서 RPC 없이 흐르는 연산자 묶음이 한 fragment. fragment 사이엔 반드시 ExchangeNode가 있고, 그 위쪽 fragment의 DataStreamSink(또는 BroadcastSink)가 Brpc로 데이터를 흘려보낸다.

Fragment의 instance 수는 destination의 분산 정책에 따라 결정 — UNPARTITIONED(1개), HASH_PARTITIONED(BE 수만큼), RANDOM(균등). FE Coordinator는 BE에 TExecPlanFragmentParams Thrift 메시지를 보내고, BE는 FragmentExecState로 받아 Pipeline X에 등록한다.

Shuffle Topology — Broadcast vs Shuffle vs Colocate

Runtime Filter — IN / BLOOM / MIN_MAX 자동 선택

Runtime Filter는 hash join의 build가 끝난 직후, build 측 키들을 가지고 probe 측 스캔에 술어를 역방향으로 던지는 메커니즘이다. 가장 큰 효과는 fact-dim 조인의 fact 스캔 — dim의 키 집합을 받아 dim에 매칭 안 될 fact 행을 스토리지 단계에서 스킵.

선택은 build 측 row count의 임계로:

  • IN: build row ≤ runtime_filter_max_in_num(기본 1024). probe SQL의 IN 술어로 그대로 변환, ZoneMap·Bloom·Bitmap 인덱스 모두 활용.
  • BLOOM: 중간 규모. m = -n·ln(p)/(ln 2)²로 비트 수 결정. 예: n=1M, p=0.01 → m ≈ 9.6M bit ≈ 1.2MB. probe 측에서 SIMD vectorized lookup.
  • MIN_MAX: 정수·날짜·decimal 같이 ordering이 명확한 타입. probe 측 ZoneMap pushdown과 결합되면 페이지 통째 스킵 가능.

EXPLAIN 보는 법: RuntimeFilter[id=RF000, type=IN_OR_BLOOM, expr=<col>, target=tbl.<col>]. SET runtime_filter_wait_time_ms=1000으로 probe가 build를 기다릴 시간 조정.

Pipeline X — morsel-driven NUMA-aware 실행 (확장)

Morsel은 fragment의 작은 작업 단위(보통 한 segment 또는 그 일부). Pipeline X 스케줄러는 코어마다 task queue를 만들고, 자기 큐가 비면 다른 코어 큐에서 work-steal 한다 — 정적 라운드 로빈보다 부하 분산이 우수.

NUMA awareness: morsel은 가능하면 데이터가 매핑된 NUMA 노드의 코어에 할당된다. memtable과 컬럼 page도 같은 노드에 할당되도록 numactl --interleave=all 설정을 운영에서 권장.

Local Exchange: 같은 BE 안에서는 Brpc 없이 in-process queue로 전달. 노드 간 fan-out(broadcast/shuffle)에서만 Brpc.

Aggregation은 two-phase: BE-local pre-aggregation → shuffle by group key → final aggregation. 메모리 절감과 네트워크 절감을 동시에. Xiaomi가 Paimon SDK의 단일-스레드 정렬 병목을 제거할 때 도입한 것이 바로 이 분산 Hash 집계.

Memory Tracker — 5-level 계층, spill, OOM 진단

BE 메모리는 5-level tracker로 추적: process → query → fragment instance → operator → allocator. 각 레벨은 부모를 reference하므로 한 query의 메모리는 전체 fragment 합과 같다. SHOW PROC '/cluster_balance/be_memory' 또는 information_schema.processlist에서 query별 사용량 확인.

Operator별 한도: hash table(exec_mem_limit), sort buffer, agg dict 등. 한도 초과 시 enable_spill=true이면 spill-to-disk(보통 storage_root_path의 spill 디렉토리). spill 빈도가 높으면 일관되게 workload_group 메모리 할당이나 BE 스케일을 늘려야 함.

OOM 진단 흐름: ① be.INFO 로그에서 last allocation top — 어떤 operator가 임계를 깼는지. ② SHOW LOAD WARNINGS·SHOW QUERIES로 직전 쿼리. ③ Memory Profile 활성(enable_profile=true) 후 재현 — operator별 peak 메모리.

Tablet Lifecycle — Clone, Decommission, Balance Score

Tablet replica의 상태는 NORMAL·REDUNDANT·MISSING·SCHEMA_CHANGE·VERSION_INCOMPLETE·RECOVERY. FE의 TabletScheduler가 1초마다 스캔해 부적절한 상태를 큐에 넣는다.

  • Clone: 주 BE에서 다른 BE로 replica 복제. version·schema·delete bitmap을 함께 옮긴다. 기본 priority NORMAL, urgent 모드는 MISSING 발견 시.
  • Decommission: BE를 안전 종료. ALTER SYSTEM DECOMMISSION BACKEND → 해당 BE의 모든 tablet에 대해 다른 BE로 clone, 끝나면 DROP BACKEND.
  • Balance score: BE 사이 tablet 수·디스크 사용량의 표준편차. 임계 초과 시 자동 rebalance. SHOW PROC '/cluster_balance'로 모니터링.

장애: BE heartbeat lost 시 tablet_repair_delay_factor_second 만큼 대기 후 missing replica 보충. 너무 짧으면 일시적 네트워크 흔들림에 과도한 clone 폭증, 너무 길면 가용성 위험.

Compaction — cumulative · base · vertical, score 수식

BE는 두 종류의 compaction을 백그라운드에서 돌린다.

  • Cumulative compaction: 작은 rowset들을 묶어 중간 크기 rowset 1개로. 자주, 빠르게.
  • Base compaction: 누적된 cumulative 결과를 base와 합쳐 큰 1개 rowset으로. 드물게, 비싸게. 이 시점에 DeleteBitmap의 비트가 켜진 행이 물리적으로 제거된다.
  • Vertical compaction: 컬럼 단위 streaming write. 와이드 테이블(수백 컬럼)에서 메모리 friendly.

Compaction Score 수식(개략): score = num_rowsets + size_factor × Σ(rowset_size / base_size). cumulative_compaction_score_threshold를 넘으면 cumulative 트리거. 운영에서는 SHOW PROC '/compactions'로 backlog 확인, 폭주 시 cumulative_compaction_min_deltas를 올리거나 max_concurrent를 조정.

MoW 테이블은 base compaction에서 DeleteBitmap을 소비해 디스크 공간이 회수된다. 그래서 MoW의 실효 storage는 시간이 지나면 자연스럽게 줄어든다.

FE Raft 실패 모델 — BDB JE Master/Follower/Observer

FE는 BDB JE(Berkeley DB Java Edition)의 replicated log를 Raft 변형으로 사용한다. 세 가지 역할: Master(쓰기·메타데이터 master), Follower(election에 참여, 읽기 가능), Observer(election 미참여, 읽기 전용 — read scale-out 용).

FE Raft 동작 — election timeout, log replication, write commit

Master는 edit log(메타 변경 record)를 BDB JE에 쓰고 followers에 비동기 복제한다. Quorum(majority) ack 후 commit 표시 → Master 메모리의 메타데이터에 반영. Master 다운 시 followers는 election timeout(5~15초) 후 새 leader 선출.

Observer는 election에 참여하지 않으므로 cluster size를 키우지 않고 read 처리량만 늘릴 수 있다. 단, 메타 변경이 Observer에 도착하기까지 약간의 지연 발생.

운영 함정: split-brain 방지를 위해 Master + Follower 합 = 홀수(3 또는 5). Follower 추가/제거는 정확한 순서로 해야 함 — 자세한 절차는 ALTER SYSTEM ADD FOLLOWER 후 가서 BDB JE replication group에 join 확인.

왜 LSM 인가 — 레이크 위에서 OLTP-같은 UPSERT를 하는 트릭

전통 레이크 포맷(예: Iceberg COW)은 같은 파티션의 행을 하나만 수정해도 그 파일을 통째로 다시 쓴다. 반면 Paimon은 memtable + sorted run의 LSM 구조를 객체 스토리지 위에 흉내낸다.

Write · Flink writer가 PK로 정렬된 memtable을 메모리에 채운다 → 임계치를 넘으면 level-0 sorted run으로 flush. 같은 키가 한 sorted run 안에서는 절대 겹치지 않는다.

Compaction · 백그라운드 압축이 level-0의 여러 run을 머지해 level-1로 올린다. num-sorted-run.compaction-trigger(기본 5)에 도달하면 트리거. level≥1 끼리는 키 범위가 겹치지 않는 leveled 구조 (RocksDB와 같은 사상).

Read · 쿼리 시 모든 level의 run을 multi-way merge. PK 같은 행은 merge engine 규칙(deduplicate / partial-update / aggregation / first-row)으로 합친다.

그 결과: 파일 재작성 없이 UPSERT/DELETE를 흡수하고, 작은 파일이 누적돼도 compaction이 정리한다. Iceberg의 "수많은 delete file → query slow" 문제의 우아한 회피.

Append-Only · Deletion Vector · Branch / Tag

Append-Only 테이블 — PK 없는 LSM-free 모드 (z-order, hilbert)

PK가 없는 append-only 테이블은 LSM 머지가 없다. 대신 z-order/hilbert space-filling curve로 incremental clustering을 한다 — 다차원 술어가 같이 hit 하는 행을 물리적으로 가깝게 재배치. BloomFilter·Bitmap·Range Bitmap 같은 file index도 같이 쓰인다.

스트리밍 소스로도 동작 — Kafka topic처럼 사용 가능. deletion-vectors.enabled = true로 MoW 모드의 저비용 DELETE를 켤 수 있다.

Deletion Vector — 행 삭제를 비트맵 한 장으로

DELETE/UPDATE 후 옛 행을 물리적으로 지우려면 파일을 다시 써야 한다. DV(Deletion Vector)는 그러지 않고, "이 파일의 어느 ordinal이 지워졌는지"를 별도 비트맵 파일에 기록한다 (RoaringBitmap).

Doris의 native Parquet reader는 DV를 vectorized C++로 적용한다 — 행을 메모리에 로드한 직후 비트마스크로 제거. JNI 호출 없이 SIMD 친화적이다. Xiaomi 사례에서 5× 가속 일부의 핵심 메커니즘.

Branch / Tag — git처럼 분기, snapshot처럼 고정

Tag는 특정 snapshot에 영구 라벨을 붙인다. 만료되지 않으며 시간여행 앵커로 안전. 사고 복구·월말 결산 스냅샷에 적합.

Branch는 mutable 분기. 한 데이터셋 위에 실험·재처리 라인을 만들고 검증되면 main으로 머지. ML 데이터 버전 관리 패턴.

쿼리는 SELECT * FROM t /*+ OPTIONS('scan.tag-name'='before-incident') */ 또는 scan.branch-name으로 명시.

Snapshot 만료 — 너무 오래 갖고 있으면 안 되는 이유

Paimon은 기본적으로 최소 10개 snapshot을 유지하고, snapshot.time-retained(기본 1h)을 넘으면 만료한다. 만료된 snapshot이 참조하던 manifest와 data file 중 다른 snapshot이 더 이상 참조하지 않는 것은 cleanup으로 삭제된다.

Tag로 잡힌 snapshot은 만료되지 않는다 — 재현성·복구 앵커는 반드시 Tag로.

Compaction 전략 — Universal vs Leveled · write-amp 30× 수식

Paimon LSM은 RocksDB와 같은 두 전략을 모두 제공.

  • Universal (size-tiered): num-sorted-run.compaction-trigger(기본 5) 초과 시, level-0의 모든 overlapping run을 단일 level-1 run으로 머지. write 부하가 spiky하지만 latency 평균이 낮다. 고-처리량 인제스트에 적합.
  • Leveled: 표준 RocksDB 사상. L0→L1→L2 단계적 머지, 각 레벨 size ratio = 10×. write가 amortized smooth, read는 레벨 수만큼 검색. 읽기 우선 워크로드.

Write Amplification 수식(leveled, level k까지): WA ≈ 1 + Σ(level_size_ratio_i). 기본 ratio 10에서 L0→L1→L2 약 1+10+10 ≈ 21, L3까지면 ≈ 31. 즉 한 행이 디스크에 평균 30번 쓰여진다.

Read Amplification: 한 키의 가장 최신 값을 찾으려면 Σ runs_in_L0 + 1 per higher level의 binary search. L0 5개 + L1·L2 각 1개 ≈ 7회 lookup이 worst-case 기준.

운영 다이얼: num-sorted-run.compaction-trigger(보통 5), num-levels(기본 자동), compaction.max.file-num, target-file-size(기본 128MB PK / 256MB append).

Manifest Math — 한 snapshot이 가리키는 file-set 계산

Snapshot은 단순한 ID가 아니다. 여러 manifest list와 manifest entry의 합집합이 그 시점의 파일 집합을 정의한다. Paimon이 데이터 파일을 단 한 번도 다시 쓰지 않으면서 update를 표현하는 트릭은 manifest entry의 ADD/DELETE 마킹에 있다. 

// snapshot-3 (이전 예제와 동일)
{
  "version": 3,
  "id": 3,
  "baseManifestList": "manifest-list-2c1f9-0",   // 누적된 base
  "deltaManifestList": "manifest-list-2c1f9-1",  // 이 commit의 ADD/DELETE
  "changelogManifestList": "manifest-list-2c1f9-2"
}

// manifest-list-2c1f9-0 (Avro decoded)
[
  { "file": "manifest-aaa-0.avro", "partitionStats": { ... }, "schemaId": 0 },
  { "file": "manifest-bbb-0.avro", "partitionStats": { ... }, "schemaId": 0 }
]

// manifest-aaa-0.avro 내부 entry
[
  { "kind": "ADD", "file": "bucket-0/data-43a6-0.parquet",
    "partition": "2026-05", "level": 0,
    "minKey": "a", "maxKey": "c", "rowCount": 12483 },
  { "kind": "ADD", "file": "bucket-0/data-43a6-1.parquet", ... },
  { "kind": "DELETE", "file": "bucket-0/data-19c2-3.parquet", // compacted away }
]
file-set 계산 알고리즘 — base ∪ delta, apply DELETE

한 snapshot의 effective file set은:

  1. baseManifestList 모두 열어 manifest entry를 모두 모은다.
  2. deltaManifestList의 entry를 합친다.
  3. kind=DELETE 인 항목을 살아있는 file 집합에서 제거.
  4. (옵션) kind=ADD with level=0 + duplicate PK in higher level → merge engine이 read 시점에 합친다.

새 commit은 항상 delta manifest list를 만들고, periodic하게 base manifest list로 누적 압축한다 — manifest 자체에도 LSM 비슷한 누적-압축 구조. 그래서 snapshot이 늘어나도 manifest 메모리/IO는 commutative하게 유지.

Memtable Mechanics — write-buffer-size, sort-buffer, spill

Flink writer 한 인스턴스는 BufferedRowDataWriteBuffer에 PK-정렬된 KV를 누적한다. write-buffer-size(기본 256MB)에 도달하면 sort 후 KeyValueFileWriter로 parquet flush. write-buffer-spillable=true이면 메모리 초과 시 로컬 디스크로 spill (write-buffer-spill-disk-size 한도).

핵심 다이얼:

  • write-buffer-size — 작을수록 작은 파일 누적, 클수록 메모리 압박.
  • sort-buffer-size — sort 시 메모리 한도. 초과 시 external sort.
  • local-merge-buffer-size — partial-update에서 같은 PK row를 미리 머지하는 버퍼.

메모리 부족하면 spill 파일이 부풀어 IO bound가 된다 — 그 시점엔 TaskManager 메모리를 늘리거나 buffer 크기를 줄여 더 자주 flush.

Lookup Compaction — changelog +U/-U를 정확하게 만드는 법

changelog-producer=lookup의 핵심: compaction 중에 새 PK가 나타날 때, higher level의 그 PK 옛 값을 빠르게 찾아서 +U(new) / -U(old) 형태의 changelog를 emit 해야 한다.

최적화: 각 sorted run에 BloomFilter를 붙여서 lookup 시 거짓양성을 빠르게 거른다. 그래도 cold tail key는 매번 디스크 한 번 읽어야 함 → IO 증가의 주요 원인.

대안: full-compaction은 정확하지만 느리고, none은 가장 빠르지만 downstream이 정규화 책임. input은 입력이 이미 changelog일 때(가장 빠르고 정확).

Concurrent Commit — 누가 양보하는가

Paimon은 객체 스토리지의 atomic rename(또는 conditional write)을 이용한 optimistic concurrency를 쓴다. 여러 writer가 동시에 commit하면 (commitUser, commitIdentifier) 조합이 멱등 키 역할. 충돌 시 loser가 retry — 충돌 종류에 따라 retry 비용이 다르다.

충돌 종류의미해결
append-vs-append두 writer가 동시에 새 데이터 파일 추가거의 항상 안전 — 새 manifest 생성, 두 commit 다 통과
append-vs-compactwriter가 append하는 동안 compactor가 같은 파티션 압축compactor의 base list가 stale → compactor retry. writer는 통과
compact-vs-compact두 compactor가 동일 파티션을 동시에 압축loser가 retry — 같은 파일을 재압축하지 않도록 검증 후
overwrite-vs-anythingOVERWRITE 모드와 일반 commit이 같은 파티션OVERWRITE가 우선, 진행 중 다른 commit은 invalidate
Optimistic concurrency 알고리즘 — read-validate-write

한 commit의 흐름:

  1. 현재 LATEST snapshot ID 읽음 → baseSnapshotId.
  2. 로컬에서 새 manifest entry들 만들고, snapshot JSON 작성 → snapshot-(N+1).
  3. Validation: baseSnapshotId 이후 다른 commit이 같은 파티션·파일을 건드렸는지 manifest entry 비교.
  4. 충돌 없으면 LATEST 힌트 파일을 atomic rename으로 갱신.
  5. 충돌 있으면 ① 새 baseSnapshotId 읽고 ② manifest 다시 만들고 ③ retry.

같은 (commitUser, commitIdentifier)로 재시도하면 멱등 — 이미 적용된 commit은 no-op으로 판정. Flink가 checkpoint 재시작 시 같은 identifier를 다시 보내도 안전.

운영 함정: retry storm. 동시 writer 수가 많고 같은 파티션을 많이 건드리면 retry 폭주. 완화: commit.max-retries 조정, writer를 partition별 hot-path 분리, 또는 mode=append-only로 conflict 가능성 자체 제거.

Recovery — LATEST replay, manifest scan, orphan 마킹

장애 후 복구 단계:

  1. LATEST 힌트 파일 읽음 → 현재 valid snapshot ID. 없으면 EARLIEST부터 차례로 검사.
  2. 해당 snapshot JSON parse, manifest list 검증, manifest entry 검증, data file 존재 여부 확인.
  3. 일부 file이 없거나 corrupt 하면: 그 snapshot이 cleanup 와중에 끊어졌을 가능성 → 한 단계 이전 snapshot으로 fall-back.
  4. Tag로 표시된 snapshot은 항상 살아있음 — 사고 복구 앵커로 사용.
  5. 참조되지 않는 data file은 orphan으로 마킹, orphan-files 행동(삭제/유지)은 옵션.

Branch 의미: branch는 mutable, main과 독립적으로 commit 가능. 검증 후 main으로 머지(metadata 만 교체). 사고 시 main을 잃어도 다른 branch에서 복원 가능.

Iceberg COW vs Paimon LSM — 비용 모델 비교

Iceberg의 기본 모드 copy-on-write(COW): 한 파일에서 행 1개를 update하려면 그 파일 전체를 복사 + 변경 + 새 파일로 적고, manifest에서 옛 파일 DELETE + 새 파일 ADD. 100MB 파일에서 행 10개만 바뀌어도 100MB write가 발생.

Paimon LSM: 같은 100MB 파일 = level-1 sorted run. 변경 10개 → memtable에 누적 → level-0 sorted run으로 flush(작은 KB~MB). compaction이 나중에 level-0 run을 level-1과 머지하면서 변경된 부분만 다시 쓴다(sort-merge로 양쪽 run 길이의 합).

Iceberg가 MoR + position delete를 지원하면서 격차는 좁혀졌지만, MoR의 read 비용(delete file을 읽어 비교)은 Paimon의 sorted-run merge보다 일반적으로 더 크다. 고-빈도 update가 핵심이면 Paimon, append-mostly + 모든 엔진 호환성이 핵심이면 Iceberg.

Transactional · order_events 테이블, 한 행 = 한 상태 변경(접수/결제/출고/배송완료). 모든 이벤트 보존, time-series 분석에 강력. 같은 주문이 여러 행으로 흩어짐 — current state는 가장 최근 행을 GROUP BY로 찾음.

Periodic Snapshot · order_daily_status, 한 행 = (주문ID, 일자, 그날 마지막 status). 일별 retrospective 분석에 직관적. 그러나 같은 주문 진행 중 여러 날에 같은 행이 반복.

Accumulating Snapshot · order_lifecycle, 한 행 = 주문 1건. 컬럼: placed_at, paid_at, shipped_at, delivered_at, current_status. 새 이벤트마다 같은 행을 update — Paimon partial-update + sequence-group이 정확히 이 패턴을 위한 도구.

FROM   fact_orders f
JOIN   dim_user u
  ON f.user_id = u.user_id
 AND f.order_dt BETWEEN u.eff_from AND u.eff_to

Conformed · Junk · Degenerate · Role-Playing

Conformed

여러 마트가 공유하는 dim

dim_date·dim_customer처럼 여러 fact가 공유. Bus matrix의 핵심 — 마트 간 일관성 보장. 외부 카탈로그(Polaris/Unity/Gravitino)에 등록해 도메인 간에도 공유.

Junk

잡다한 flag 통합 dim

여러 boolean/code flag(is_promo, is_returned, channel_code)를 한 dim 테이블로 묶어 fact의 키 컬럼 폭주 방지. 가능한 조합 수만큼 row.

Degenerate

fact에 박힌 키 — dim 없음

order_id, invoice_no처럼 dim 테이블이 따로 없는 비즈니스 키. fact에 그대로 두고 GROUP BY 차원으로 사용.

Role-Playing

하나의 dim, 여러 역할

dim_date가 fact의 order_dt·ship_dt·paid_dt 세 컬럼에 다 join. 뷰로 alias(v_dim_order_date, …)를 만들면 BI 도구가 깔끔히 인식.

Streaming DW — Lambda vs Kappa, retraction stream

Lambda

Batch + Speed 두 라인

batch layer = 정확한 누적, speed layer = 최근 N분 근사. 둘을 serving layer에서 머지. 정확성 + 신선도 둘 다 챙기지만 코드 두 벌.

Kappa

Stream-only, 필요 시 replay

모든 처리는 stream 한 라인. 정정이 필요하면 Kafka offset 또는 Paimon snapshot 시점부터 replay. Paimon + Flink가 가장 자연스러운 Kappa 구현 — Paimon snapshot이 replay 앵커.

Retraction Stream — Flink RowKind UPDATE_BEFORE/UPDATE_AFTER

Flink는 changelog row에 RowKind를 붙인다 — +I(insert), -D(delete), -U(update_before), +U(update_after). MV·groupBy 같이 stateful 연산자는 입력의 변경을 정확히 반영하기 위해 retraction(즉 -U로 옛 결과 빼고 +U로 새 결과 더하기)을 emit.

Paimon의 changelog-producer=lookup이나 input은 정확히 이 retraction 시퀀스를 만들거나 그대로 보존. Doris는 Routine Load consumer가 retraction을 받으면 MoW의 sequence_col로 멱등 처리.

Debezium 의 진짜 파이프라인 — snapshot 모드와 schema 변화

3. Idempotency — Debezium 중복이 와도 살아남기

모든 CDC 파이프라인은 at-least-once가 기본. exactly-once는 비싸고 깨지기 쉽다. 대신 sink 측에서 PK + sequence로 멱등을 보장해 중복이 와도 결과가 일정하게 만든다. 

-- Paimon 측 sequence.field로 out-of-order 멱등
CREATE TABLE orders (
  order_id BIGINT,
  status   STRING,
  updated_at BIGINT,
  PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
  'merge-engine' = 'deduplicate',
  'sequence.field' = 'updated_at',
  'bucket' = '8'
);

-- Debezium 재시작 시 같은 binlog 위치 다시 보내도, 같거나 더 큰 sequence만 살아남는다.
-- updated_at이 더 작으면 새 row가 무시되고 기존 row 유지.

ORDER BY edits_seen DESC LIMIT 10;

폐쇄망 운영 노트.

에어갭, 이미지 미러, 네트워크 분리, IAM, 캐시 경로, 컴팩션 트리거, 장기 보관 — 운영은 작은 결정의 누적이다.

에어갭 이미지 미러

DMZ에서 docker pull 후 docker save -o doris-fe.tar → 폐쇄망 사내 Harbor/Nexus로 push. SBOM과 sha256을 함께 기록. 핵심: apache/doris, apache/flink, minio/minio, curlimages/curl.

메타데이터 백업

FE의 doris-meta/는 BDB JE Raft 로그. snapshot 백업이 ① FE 메타와 ② Paimon warehouse 의 snapshot 디렉토리 두 군데 필요. Paimon snapshot은 immutable이라 객체스토리지 버전관리와 궁합이 좋다.

컴팩션 튜닝

Paimon: num-sorted-run.compaction-trigger(기본 5), bucket 200MB–1GB. Doris: cumulative_compaction_min_deltas, base_compaction_check_interval_seconds를 워크로드(쓰기 빈도)에 맞춰 조정.

시간여행 / 시간 관리

Paimon snapshot 기본 1시간 만료. snapshot.time-retained·snapshot.num-retained.min과 Tag(영구 앵커)로 분석 재현성을 보장. 사고 복구 시 scan.tag-name='before-incident'.

캐시 / 디스크 레이아웃

BE 1대당 NVMe의 30%를 file cache로 분리. 핫 데이터는 Paimon이 아니라 Doris의 NVMe에 산다 — S3 round trip 0회. cache-warmup 잡을 정기 스케줄.

관측성

Doris: information_schema.table_metrics + Prometheus exporter + OpenTelemetry. Flink: JobManager metrics, checkpoint duration/state size. Paimon: snapshot 수, level 별 file 수, compaction backlog.

Capacity Sizing — back-of-envelope 계산

실측 통계가 없을 때 빠르게 BE 수와 Paimon bucket 수를 추정하는 공식.

# 입력
rows_per_day            = 100,000,000     // 1억 row
avg_row_bytes           = 200             // 압축 전 평균
columnar_compress_ratio = 4               // Parquet ZSTD 가정
hot_window_days         = 30
disk_per_be             = 4 TB            // NVMe 1대
safety_factor           = 1.5             // 갑작스런 spike

# 일별 압축 후 데이터
bytes_per_day = rows_per_day * avg_row_bytes / columnar_compress_ratio
              = 100M * 200 / 4 = 5 GB / day

# Paimon bucket 수 (1 bucket ≤ 1 GB 권장)
buckets_paimon = ceil(bytes_per_day * hot_window_days / 1 GB)
              = ceil(5 * 30 / 1) = 150 buckets

# Doris BE 수 (3-replica 가정)
total_bytes = bytes_per_day * hot_window_days * 3 * safety_factor
            = 5 GB * 30 * 3 * 1.5 = 675 GB
be_count = ceil(total_bytes / disk_per_be)
         = ceil(675 GB / 4 TB) ≈ 1 BE  (cold용 추가 1 더)

# CPU
queries_per_sec_target = 100
cpu_per_query_ms       = 200            // P50 단위 쿼리 비용
cores_needed = (queries_per_sec * cpu_per_query_ms) / 1000 * safety
             = 100 * 0.2 * 1.5 = 30 cores
be_cores = 30 / be_count = ~30 cores per BE

이 숫자는 시작점일 뿐 — 핵심 검증은 ① rowset 폭증 시 compaction이 따라오는지, ② NVMe IOPS·throughput이 ZoneMap skip 후에도 충분한지, ③ FE 메타 메모리(tablet 수 × 약 10KB)가 heap 안에 들어가는지.

자주 만나는 함정

① 작은 파일이 쌓여 쿼리가 느려진다

checkpoint가 너무 자주 일어나면 Paimon level-0가 쌓인다. execution.checkpointing.interval 30s 권장, bucket 수를 늘려 키 분산을 잡고, lookup compaction을 켜 두면 자연스럽게 정리된다.

② Doris가 Paimon 변경을 즉시 못 본다

Doris external catalog는 metadata 캐시를 둔다. REFRESH CATALOG paimon_lake 또는 refresh_table_meta_interval_ms(기본 60s) 조정. 더 빠르게 보고 싶다면 incremental Async MV의 스케줄을 짧게 하거나 직접 catalog refresh 호출.

③ MoW 테이블에서 PK 인덱스 비대화

키가 너무 길거나 카디널리티가 너무 높으면 PK index + Bloom 메모리 풋프린트가 커진다. bigint 단조 키나 8–16바이트 ULID가 좋은 선택. UUID v4는 분산도는 좋지만 로컬리티가 깨져서 정렬 비용이 든다.

④ Paimon partial-update에서 늦은 도착 처리

여러 토픽이 동시에 같은 PK를 갱신할 때, 늦게 온 행이 옛 컬럼을 덮어쓰면 곤란. fields.<col>.sequence-group으로 컬럼별 timestamp 가드. ignore-delete를 켤지 끌지 결정.

⑤ HDFS / S3 long-tail latency

Xiaomi가 upstream에 기여한 패치 — HDFS read timeout을 100ms로 줄이고, replica 재시도. S3는 fs.s3.connect-timeout·fs.s3.request-timeout을 ms 단위로 강하게 잡고, retry 정책을 jitter+exponential backoff로 설정.

⑥ Flink checkpoint 폭증과 backpressure

state size가 GB를 넘기 시작하면 RocksDB state backend로 전환 필수. checkpoint interval은 30s 기준으로 시작, end-to-end 지연 요구가 더 빠르면 incremental checkpoint와 unaligned checkpoint를 함께. Paimon writer의 write-buffer-size를 키우면 작은 파일 생성을 줄일 수 있다.
