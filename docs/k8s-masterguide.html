0.1이 문서의 사용법

이 가이드는 위에서 아래로 순서대로 읽도록 설계돼 있습니다. 앞 챕터에서 정의한 용어와 그림을 뒤 챕터가 전제로 삼습니다. 그러나 각 파트의 문패 페이지는 해당 파트의 목적을 독립적으로 설명하므로, 이미 익숙한 영역은 건너뛰어도 큰 무리는 없습니다.

문서 안에는 네 가지 상호작용 요소가 있습니다.

① 용어 호버 툴팁
본문 곳곳에 파란 점선이 그어진 NIC 같은 용어 위로 마우스를 올리면, 그 용어의 풀네임과 1~2문장 해설이 즉시 팝업으로 떠오릅니다. 본문 흐름을 끊지 않고 모르는 약어를 해결할 수 있도록 설계했습니다.
② 가상 kubectl 터미널
화면 우측 하단의 동그란 $_ 버튼을 누르면 창이 하나 올라옵니다. kubectl get pods, kubectl describe pod nginx-abc, kubectl logs -f web-0 같은 명령을 쳐보면 미리 준비된 모의 응답이 돌아옵니다. 실제 클러스터와 대화하는 것은 아니지만, "어떤 명령이 어떤 출력을 내는지"의 감각을 본문에서 벗어나지 않고 익힐 수 있습니다.
③ 아키텍처 다이어그램 클릭
Part 2의 컨트롤 플레인 그림에서 kube-apiserver, etcd, kubelet 같은 네모 상자를 클릭하면 우측에서 상세 설명 패널이 슬라이드로 들어옵니다. 각 컴포넌트의 역할과 파생 이슈를 한 번에 묶어 볼 때 유용합니다.
④ 트러블슈팅 분기 시나리오 & 챕터별 퀴즈
Part 8은 모든 사례가 "증상 → 원인 후보 선택 → 진단 명령 → 해결" 흐름으로 전개됩니다. 잘못된 후보를 선택하면 왜 그게 오답인지 즉시 피드백이 뜹니다. 각 챕터 끝에는 3~5문항의 객관식 퀴즈가 있어 방금 읽은 내용의 이해도를 스스로 확인할 수 있습니다.
NOTE 이 문서의 모든 인터랙션은 JavaScript가 활성화된 환경에서 동작합니다. 단, JS 없이도 본문 텍스트는 100% 읽을 수 있도록 마크업을 유지했습니다. 프린트 시 인터랙티브 요소(터미널·패널·퀴즈)는 자동으로 숨겨집니다.

0.2사전 지식 체크

이 문서는 리눅스에 로그인해서 ls, ps, cat을 쳐본 적 있는 수준을 시작점으로 가정합니다. 더 정확히 표현하면 다음과 같습니다.

알고 있어야 하는 것
  • "프로세스"라는 것이 메모리에 적재돼 CPU에서 실행되는 실행 단위라는 감각
  • 파일 시스템에 디렉터리와 파일이 있고, 권한(rwx)이라는 개념이 있다는 점
  • TCP/IP가 "IP 주소와 포트"로 통신한다는 정도의 네트워크 상식
  • YAML이 들여쓰기로 계층을 표현하는 설정 형식이라는 점
몰라도 되는 것
  • 커널 스케줄러의 CFS 구현 세부 — 본문에서 필요한 만큼 짚습니다
  • eBPF의 바이트코드 문법 — Cilium을 다룰 때 개념만 설명합니다
  • Raft 합의 알고리즘의 수학적 증명 — etcd 챕터에서 직관으로 풀어냅니다
  • Go 언어 — Kubernetes 소스 투어에서는 의사 코드로 읽습니다

이 문서가 말하지 않는 것도 있습니다. 단일 호스트에서 Docker로 컨테이너를 띄우는 방법, 혹은 Helm 차트의 템플릿 문법 같은 "하우투" 성격의 내용은 다루지 않습니다. 이 문서의 목적은 왜에 집중하는 것이기 때문입니다. "어떻게"는 공식 문서와 kubectl explain이 이미 훌륭히 답해 줍니다.

0.3용어 약속

기술 약어는 처음 등장할 때 풀네임과 한국어 설명을 괄호로 덧붙입니다. 예를 들어 본문에서 NIC 같은 단어가 처음 보이면 "Network Interface Card(네트워크 인터페이스 카드, 흔히 랜 카드라 불리는 하드웨어)" 형태로 풀어씁니다. 이미 등장한 용어는 이후 약어만으로 사용하되, 화면에 마우스를 올리면 언제든 해설이 다시 뜨도록 마크업돼 있습니다.

kubectl 명령과 YAML 필드명은 영문 원문을 그대로 사용합니다. 번역하면 공식 문서·에러 메시지·커뮤니티 글과 매칭이 어긋나 오히려 혼란을 일으키기 때문입니다. 대신 이들이 가리키는 개념은 본문에서 한국어로 설명합니다.

Kubernetes 버전은 1.30을 기준으로 합니다. 1.29 이전에서 달라진 필드나 1.31 이후에 등장할 내용이 있을 때는 명시적으로 버전을 언급합니다. EKS는 1.30 지원 시점(2024년 중반~2026년 봄) 기준으로 기술합니다.

PART 1 · CS Foundation

CS 파운데이션 — 왜 컨테이너가 필요했는가

Kubernetes가 해결하려 한 문제를 이해하려면 그 아래의 하드웨어·OS·네트워크가 먼저 보여야 합니다. 물리 머신에서 가상화, 컨테이너, 오케스트레이션까지의 계층을 맨 밑바닥부터 다시 쌓습니다.

1.1물리에서 가상까지 — 컴퓨터의 계층

Kubernetes를 이해한다는 것은 "서버 여러 대에 컨테이너를 잘 배치하는 시스템"을 이해하는 것입니다. 그런데 "서버"란 무엇이고 "컨테이너"란 무엇일까요? 답을 하려면 먼저 현대의 컴퓨터가 어떻게 생겼는지부터 내려가 봐야 합니다.

① 물리 서버

한 대의 물리 서버는 메인보드 위에 CPU(Central Processing Unit, 중앙 처리 장치) 몇 개, RAM(Random Access Memory, 주기억 장치) 모듈, NIC, 그리고 디스크(SSD/HDD)가 꽂힌 덩어리입니다. 이 하드웨어 위에서 단 하나의 운영체제(OS)가 부팅되고, 그 OS가 프로세스 여러 개를 동시에 실행합니다. 2000년대 초까지만 해도 전형적인 서비스 운영은 "한 서버에 한 서비스"였습니다. 서버가 남아도 다른 서비스를 같이 올리기 부담스러웠던 이유는 격리가 없었기 때문입니다. 한 애플리케이션이 디스크를 가득 채우거나 메모리를 다 먹거나 80 포트를 쓰면 다른 애플리케이션이 바로 영향을 받습니다.

② 가상화 시대

이 문제를 푼 첫 번째 돌파구는 하이퍼바이저(Hypervisor) 기반 VM(Virtual Machine, 가상 머신)입니다. VMware, Xen, KVM 같은 소프트웨어가 물리 하드웨어를 "에뮬레이션"해 각 VM이 자기만의 CPU·메모리·NIC·디스크를 가진 것처럼 속입니다. 각 VM은 독립된 커널을 부팅하고, 서로의 프로세스를 절대 볼 수 없습니다. 격리는 완벽했지만, 부팅에 수십 초 걸리고 VM 하나마다 수백 MB~GB의 커널·라이브러리가 중복돼 밀도(한 호스트에 몇 개 올릴 수 있는가)는 낮았습니다.

③ 컨테이너의 등장

컨테이너는 발상의 전환입니다. "커널 전체를 복제하지 말고, 커널은 하나로 공유하되 프로세스에게 자기만의 세상을 보여주자." 이 트릭의 두 재료가 바로 리눅스 커널의 namespace(네임스페이스)와 cgroup입니다. 네임스페이스는 프로세스가 보는 자원 목록(다른 프로세스, 마운트 지점, 네트워크 인터페이스, 호스트명 등)을 칸막이로 갈라 주고, cgroup은 프로세스 그룹이 소비할 수 있는 CPU·메모리·I/O의 양을 제한합니다. 이 두 기능을 묶어 "프로세스가 자기가 단독 OS에 사는 것처럼 착각"하게 만든 것이 컨테이너의 본질입니다.

Docker(2013)가 이 아이디어를 "이미지"라는 배포 포맷과 붙여 폭발적으로 확산시켰고, 수백 개의 작은 컨테이너를 수십 대의 호스트에 배치·스케줄·복구하는 문제가 즉시 대두됐습니다. 이 문제를 푸는 시스템의 이름이 바로 Kubernetes입니다. Google이 내부에서 10여 년 운영한 Borg의 교훈을 오픈소스로 재설계한 결과물이죠.

④ 오케스트레이터로서의 K8s의 위치

그림으로 그리면 이렇습니다.

┌──────────────────────────────────────────────────────┐ │ Kubernetes │ ← 컨테이너를 "어디에" "얼마만큼" 띄울지 결정 ├──────────────────────────────────────────────────────┤ │ 컨테이너 (containerd, runc) │ ← namespace + cgroup으로 격리된 프로세스 ├──────────────────────────────────────────────────────┤ │ 운영체제 (Linux kernel, systemd, ...) │ ├──────────────────────────────────────────────────────┤ │ 하드웨어 (CPU, MMU, RAM, NIC, SSD, ...) │ └──────────────────────────────────────────────────────┘

Kubernetes는 맨 위 계층입니다. 아래에 있는 것들 — 커널과 하드웨어, 컨테이너 런타임 — 이 어떻게 동작하는지를 알아야 K8s에서 왜 어떤 설정이 필요하고 왜 어떤 장애가 터지는지 설명할 수 있습니다. 그래서 우리는 맨 아래부터 시작합니다.

1.2CPU·메모리·I/O — 하드웨어 언더레이

이 챕터의 목표는 K8s 본문에서 돌아다닐 하드웨어 용어에 부담을 없애는 것입니다. 외울 필요는 없고, 나중에 "아, 그때 이게 이런 거였지" 정도로 떠오르면 충분합니다.

CPU: 링과 모드

x86 아키텍처의 CPU는 4개의 보호 링(Ring 0~3)을 갖습니다. 낮은 숫자일수록 권한이 높습니다. 실제 현대 OS는 Ring 0(커널 모드)과 Ring 3(사용자 모드) 두 개만 사용합니다. 일반 애플리케이션은 Ring 3에서 돕니다. 디스크에 쓰기, 네트워크 송신, 메모리 매핑 같은 특권 연산은 Ring 3에서 직접 할 수 없고, "커널님 대신 해주세요"라고 부탁해야 합니다. 이 부탁의 메커니즘이 바로 syscall입니다.

컨테이너는 이 Ring 구조 위에서 돌아갑니다. 컨테이너 안의 프로세스도 Ring 3에서 시작해서, 시스템 콜을 호출하고, 커널로 Ring 0 전환이 일어납니다. VM과 달리 하이퍼콜(hypercall)을 거치지 않기 때문에 이 전환 비용이 훨씬 싸고, 그래서 컨테이너가 VM보다 빠릅니다.

MMU와 가상 메모리

MMU(Memory Management Unit, 메모리 관리 장치)는 CPU 안의 하드웨어 블록으로, "가상 주소를 물리 주소로" 매 접근마다 번역합니다. 프로세스는 자기 전용의 연속적인 가상 주소 공간을 본다고 믿지만, 실제 물리 메모리에서는 4KB 단위의 페이지로 흩어져 있습니다. 이 번역표(페이지 테이블)는 커널이 관리하고, 빈번히 사용되는 부분은 CPU의 TLB(Translation Lookaside Buffer, 주소 변환 캐시)에 들어가 속도를 올립니다.

컨테이너 관점에서 기억할 점은, 같은 호스트의 컨테이너는 모두 동일한 MMU·TLB를 공유한다는 것입니다. VM처럼 하드웨어를 가상화하지 않으므로 메모리 접근은 오버헤드가 없지만, "한 컨테이너가 너무 많은 메모리를 쓰면 호스트의 TLB·캐시가 오염"되는 간섭은 발생할 수 있습니다.

NUMA와 CPU 바인딩

서버 CPU가 여러 소켓일 때는 각 소켓이 자기 쪽의 메모리를 가깝게 들고 있습니다. 이 구조를 NUMA(Non-Uniform Memory Access, 비균일 메모리 접근)라고 부릅니다. 다른 소켓의 메모리에 접근하면 훨씬 느리기 때문에, 고성능 애플리케이션은 CPU 코어와 메모리를 같은 NUMA 노드에 고정(pinning)합니다. K8s에는 이를 지원하는 CPU Manager와 Topology Manager가 있습니다. Part 6에서 다시 만납니다.

NIC와 DMA

네트워크 패킷이 서버에 들어오면 NIC가 이를 받아 메모리에 직접 씁니다. CPU를 거치지 않고 메모리에 직접 쓰는 이 기능을 DMA(Direct Memory Access, 직접 메모리 접근)라고 합니다. 그 뒤 NIC가 CPU에 인터럽트를 걸면 커널의 네트워크 스택이 깨어나 패킷을 처리합니다. 이 경로 전체가 "패킷이 Pod에 닿기까지의 첫 50마이크로초"입니다. Part 4에서 CNI를 다룰 때 이 경로가 왜 중요한지 보게 됩니다.

PCIe와 장치 트리

NIC·GPU·NVMe 같은 고속 장치는 PCIe(Peripheral Component Interconnect Express, PCI 익스프레스) 버스로 CPU와 연결됩니다. 서버에서 lspci를 치면 이 트리가 나옵니다. K8s에서 GPU·특수 하드웨어를 파드에 할당하려면 Device Plugin이라는 프레임워크가 이 장치들을 광고하고, 스케줄러가 그 속성을 토대로 파드를 배치합니다.

왜 중요한가 K8s에서 requests.cpu: 500m 같은 값을 설정할 때, 그 숫자가 cgroup의 CPU 쿼터로 번역되고, 커널 스케줄러가 이를 기준으로 각 프로세스에게 CPU 시간을 나눠 준다는 흐름을 기억해 두면 좋습니다. 결국 모든 것이 하드웨어 자원 위의 추상입니다.

1.3syscall과 커널 경계

사용자 프로세스가 파일을 열거나 소켓에 바이트를 쓸 때마다 커널로 진입합니다. 리눅스에는 약 400개의 syscall이 있고, strace로 확인할 수 있습니다. 예를 들어 cat /etc/hostname을 실행하면 openat(AT_FDCWD, "/etc/hostname", O_RDONLY) → read(fd, buf, 131072) → write(1, buf, 11) → close(fd) → exit(0) 의 syscall 시퀀스가 찍힙니다.

kernel space vs user space

프로세스의 가상 주소 공간은 보통 상위 영역이 kernel space(리눅스 x86_64에서 0xFFFF...), 하위가 user space로 나뉘어 있습니다. user space 프로그램이 kernel space에 직접 접근하면 즉시 세그폴트가 납니다. 반드시 syscall을 통해야 하고, syscall은 인자 검증 → 권한 체크 → 실제 작업 → 반환값 복사 순으로 진행됩니다.

file descriptor — 유닉스의 '모든 것은 파일'

파일뿐 아니라 소켓, 파이프, 타이머, 이벤트, 심지어 사인까지 리눅스에서는 모두 FD(File Descriptor, 파일 디스크립터)라는 정수 번호로 다룹니다. 프로세스가 open()하면 커널이 FD를 부여하고, 이후 read/write/close는 이 FD로 합니다. 한 프로세스가 사용할 수 있는 FD 수는 ulimit -n으로 정해지며, Pod 수가 많은 노드에서는 이 한도가 차서 "Too many open files" 오류가 나곤 합니다. 이는 Part 8 트러블슈팅에서 다시 만납니다.

fork/exec

리눅스에서 새 프로세스는 fork()로 현재 프로세스를 복제하고, exec()로 다른 프로그램으로 덮어쓰는 2단계로 만들어집니다. 이 설계가 셸의 파이프라인, 그리고 컨테이너 런타임이 "호스트 PID에서 fork 뒤 namespace를 바꾸고 exec" 하는 방식을 가능하게 합니다.

예시 — strace로 들여다 본 kubectl get pods 내부

kubectl 바이너리를 strace에 걸면 아래와 비슷한 요약이 나옵니다 (실제로는 수천 줄이 나옵니다): 

% strace -c kubectl get pods
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 45.22    0.081230          61      1324           futex
 18.77    0.033712          30      1104           epoll_pwait
 12.04    0.021632          14      1493           read
  8.91    0.016012          21       763           write
  5.33    0.009573          46       207           openat
  ...

대부분의 시간이 futex(동기화)와 epoll_pwait(이벤트 대기)에 쓰이고, read/write가 그 뒤를 잇습니다. API 서버와 HTTPS로 대화하는 그 바이너리가 결국은 수천 번의 시스템 콜로 이루어진다는 사실 — 이 추상의 두께가 쿠버네티스 디버깅의 어려움이자 재미입니다.

1.4네트워크 7계층과 실전 축약

OSI(Open Systems Interconnection, 개방형 시스템 간 상호접속) 7계층 모델은 "이론상" 네트워크를 7개로 나누지만, K8s에서 자주 등장하는 것은 네 개입니다. 여기에만 집중하겠습니다.

계층이름데이터 단위K8s에서 어디에서 만나는가
L2Data Link프레임노드 간 같은 서브넷에서 MAC 주소로 전달 · MetalLB L2 모드
L3Network패킷(IP)Pod IP, Service IP, Calico/Cilium 라우팅, BGP
L4Transport세그먼트(TCP/UDP)Service의 포트, kube-proxy iptables NAT, 헬스 체크

IP, MAC, ARP

IP(Internet Protocol, 인터넷 프로토콜) 주소는 L3의 논리 주소이고, MAC(Media Access Control, 미디어 접근 제어) 주소는 NIC 고유의 L2 하드웨어 주소입니다. 같은 서브넷 내에서 IP로 상대를 찾아도 실제 프레임 전송은 MAC으로 합니다. "이 IP가 누구 MAC이지?"를 묻는 프로토콜이 ARP(Address Resolution Protocol)입니다. ARP 캐시가 꼬이면 같은 서브넷 통신이 끊기는 장애가 납니다.

MTU와 MSS

MTU(Maximum Transmission Unit, 최대 전송 단위)는 한 번에 네트워크를 탈 수 있는 프레임의 바이트 크기입니다. 이더넷 기본 MTU는 1500입니다. VXLAN·IPIP 같은 오버레이를 쓰면 헤더가 추가돼 실제 payload가 줄어듭니다. 이 때 MSS(Maximum Segment Size) 조정이 안 되면 "큰 패킷은 안 가는데 작은 패킷은 가는" 기묘한 장애가 발생합니다. Calico·Flannel의 MTU 설정이 왜 중요한지의 뿌리입니다.

NAT과 conntrack

NAT(Network Address Translation, 네트워크 주소 변환)은 패킷의 IP를 중간에 바꾸는 기술입니다. K8s의 Service(ClusterIP)가 바로 이 방식으로 구현됩니다. 리눅스 커널의 netfilter 프레임워크 위의 iptables가 "목적지가 10.96.0.5:80이면 실제 Pod IP 중 하나로 DNAT"을 수행하고, 응답 패킷의 원복을 위해 conntrack(connection tracking, 연결 추적 테이블)이 각 플로우를 기억합니다. conntrack 테이블이 가득 차면 새 연결이 끊기는 장애가 발생 — Part 8에 사례가 있습니다.

veth와 bridge

같은 호스트의 두 컨테이너가 통신할 때는 veth(Virtual Ethernet, 가상 이더넷 페어)가 사용됩니다. 한 쌍의 "파이프" 같은 것으로 한쪽 끝은 컨테이너의 네트워크 네임스페이스에, 다른 끝은 호스트의 브리지(cni0, docker0)에 꽂힙니다. 브리지는 L2 스위치처럼 동작해 같은 호스트의 파드 사이를 전달합니다.

1.5리눅스 네임스페이스 7종

리눅스 커널이 컨테이너에 제공하는 7개 네임스페이스는 각각 한 가지 자원의 "시야"를 분리합니다. 컨테이너 런타임은 새 프로세스를 만들 때 이 중 필요한 것들을 unshare로 잘라냅니다.

mnt (Mount)
파일 시스템 마운트 지점의 시야. 컨테이너는 자기만의 루트 파일 시스템(이미지의 내용)을 봅니다.
pid (Process ID)
프로세스 번호. 컨테이너 안의 PID 1은 실제 호스트에서는 PID 15342 같은 식. ps aux로 호스트 프로세스가 보이지 않는 이유.
net (Network)
NIC·라우팅 테이블·방화벽 룰·ARP 캐시·포트. 각 파드는 자기만의 net 네임스페이스를 갖고, 그 안에 eth0(veth의 한쪽)가 꽂힙니다.
uts (Unix Timesharing)
hostname과 domainname. 컨테이너가 자기 이름을 가질 수 있는 이유.
ipc (Inter-Process Communication)
System V IPC, POSIX 메시지 큐. 다른 컨테이너의 IPC와 격리.
user
UID/GID 매핑. 컨테이너 안에서 root(UID 0)인 프로세스가 호스트에서는 일반 사용자(UID 100000)로 매핑될 수 있음. "rootless container"의 기반.
cgroup
(리눅스 4.6부터) cgroup의 계층 시야. 컨테이너가 자기 위쪽의 cgroup 구조를 못 보게 함.

손으로 만들어 보는 컨테이너

개념을 확실히 다지려면 10줄짜리 "손컨테이너"를 만들어 보세요. 아래가 bash 한 줄로 가능한 namespace 조합입니다. 

# 새 mnt · net · pid · uts · ipc 네임스페이스에서 bash를 띄운다
sudo unshare --fork --pid --mount-proc --uts --ipc --net \
     --mount bash
# 안에서 확인
hostname isolated         # 바깥 호스트명과 다른 이름 지정
ps aux                    # PID 1이 bash다
ip addr                   # lo만 존재 — 새 net 네임스페이스

여기에 cgroup 제한을 걸고, 루트 파일 시스템을 이미지 디렉터리로 pivot_root 하면 본격 컨테이너가 됩니다. Docker·containerd·runc가 하는 일의 99%는 이걸 "안전하게·효율적으로·반복 가능하게" 래핑하는 일입니다.

1.6cgroups: CPU와 메모리의 울타리

네임스페이스가 "무엇을 보는가"를 제한한다면, cgroups(control groups)는 "얼마나 쓸 수 있는가"를 제한합니다. Kubernetes의 resources.requests와 resources.limits는 모두 이 cgroup 값으로 번역됩니다.

v1 vs v2

cgroup v1은 하위 시스템(cpu, memory, blkio, …)마다 별개의 계층 트리를 가졌습니다. 실무에서는 관리가 복잡하고 여러 이슈가 있었기에, 리눅스 4.5부터 v2가 도입됐고 2023년 이후에는 대부분의 배포판이 v2를 기본으로 씁니다. Kubernetes 1.25부터 v2 지원이 기본값입니다. v2는 "하나의 통합된 트리"에서 모든 컨트롤러를 다룹니다.

CPU 제한 — quota와 period

cpu.cfs_quota_us와 cpu.cfs_period_us로 제한합니다. 예를 들어 period=100ms, quota=50ms면 해당 cgroup은 매 100ms마다 최대 50ms의 CPU 시간만 쓸 수 있습니다. 이를 50%(혹은 500m)로 표기합니다. 중요한 함정 — quota를 넘는 순간 커널은 해당 프로세스를 다음 period 시작까지 일시 정지(throttle)합니다. 이 때문에 limits.cpu를 타이트하게 걸면 레이턴시가 튀는 문제가 자주 발생합니다. Part 8에 관련 사례가 있습니다.

메모리 제한과 OOMKiller

memory.max(v2) 또는 memory.limit_in_bytes(v1)를 초과하면 커널의 OOM Killer(Out-Of-Memory Killer)가 동작합니다. cgroup 내에서 oom_score가 가장 높은 프로세스가 SIGKILL로 강제 종료됩니다. 컨테이너의 PID 1이 죽으면 컨테이너 전체가 종료되고, kubelet이 이를 감지해 파드 상태를 OOMKilled로 표시합니다.

직접 보기

# cgroup v2 기준, 실행 중인 파드의 cgroup 경로
cat /proc/$(pidof nginx)/cgroup
# 0::/kubepods.slice/kubepods-burstable.slice/kubepods-burstable-pod.slice/cri-containerd-.scope

# 그 cgroup의 CPU 제한
cat /sys/fs/cgroup/kubepods.slice/.../cpu.max
# 50000 100000   → 100ms마다 50ms → 500m

# 그 cgroup의 메모리 제한
cat /sys/fs/cgroup/kubepods.slice/.../memory.max
# 536870912       → 512 MiB

# throttle 당한 통계
cat /sys/fs/cgroup/kubepods.slice/.../cpu.stat
# usage_usec 12345678
# nr_periods 123
# nr_throttled 40        ← CPU를 빼앗긴 횟수
# throttled_usec 6543210 ← 빼앗긴 시간
운영 팁 nr_throttled이 0이 아닌 파드가 있다면 CPU limit이 병목입니다. Part 8에서 이 상황의 해법을 다룹니다.

이 전체 생태계는 OCI(Open Container Initiative) 표준 덕에 교체 가능한 부품들이 됩니다. 현재 두 스펙이 핵심입니다.

OCI Runtime Spec
"컨테이너를 실행하는 프로그램(runc)은 어떤 JSON 설정을 받아 어떤 절차로 프로세스를 만드는가"를 규정. runc 외에도 kata-containers(경량 VM), gVisor(유저스페이스 커널), crun(C로 작성한 경량 runc) 등이 이 스펙을 구현합니다.
OCI Image Spec
컨테이너 이미지의 디렉터리·매니페스트·레이어 포맷 규정. Docker Hub, ECR, GHCR 등 모든 레지스트리가 이 스펙을 따릅니다.

CRI

kubelet은 컨테이너 런타임과 직접 통신하지 않고 CRI(Container Runtime Interface, 컨테이너 런타임 인터페이스)라는 gRPC API를 씁니다. 1.24 전에는 dockershim(도커용 어댑터)이 kubelet 코드 안에 있었는데, 1.24부터 제거됐습니다. 현재 표준은 containerd(CNCF 졸업 프로젝트)와 CRI-O(Red Hat 주도)입니다. Docker 자체는 내부적으로 containerd를 사용하지만, kubelet이 containerd를 직접 부르면 되므로 Docker 계층은 불필요해진 것입니다.

역사 "Kubernetes가 Docker를 버린다"는 뉴스가 2020년에 크게 떠돈 적이 있습니다. 정확히는 dockershim 폐지였고, 기존 Docker 이미지는 여전히 OCI 이미지로 호환되므로 사용자가 푸시하던 이미지는 그대로 돕니다. 엔지니어 입장에서 바뀐 것은 노드의 런타임이 containerd로 전환된다는 점 정도입니다.

1.8이미지와 overlayfs

컨테이너 이미지는 여러 레이어(Layer)의 적층입니다. 각 레이어는 tar로 압축된 파일 시스템 변경분이고, 콘텐츠 기반 해시(sha256:...)로 식별됩니다. 같은 해시의 레이어는 레지스트리와 노드 모두에서 한 번만 저장되고 공유됩니다. 이것이 대용량 이미지도 push/pull이 빠른 이유입니다.

overlayfs의 구조

레이어를 실행 시점에 "하나의 파일 시스템처럼" 보여주는 것이 overlayfs(union filesystem)입니다. 각 레이어는 lowerdir로 쌓이고, 맨 위에 컨테이너가 변경한 파일을 담는 upperdir이 얹힙니다. 두 디렉터리를 합쳐 보여주는 것이 merged입니다.

merged/ ← 컨테이너가 보는 / (루트) ├── bin/ ← lower1에서 옴 ├── app/ ← lower3에서 옴 └── tmp/cache ← upper(변경분)에만 있음 upperdir/ ← 컨테이너가 쓴 내용 (종료 시 삭제) lowerdir/ ← 이미지 레이어들 (읽기 전용, 공유) workdir/ ← overlayfs가 atomic 연산에 쓰는 스크래치

Copy-on-Write

컨테이너가 /etc/nginx/nginx.conf를 수정하면, overlayfs는 먼저 lower에서 그 파일을 upper로 복사한 뒤 그 복사본을 수정합니다. 이것을 Copy-on-Write(CoW)라고 합니다. 많은 파일을 수정하면 upper가 비대해지고 디스크를 잡아먹을 수 있으므로, "컨테이너 내부에 큰 쓰기 작업을 하지 말고 emptyDir 혹은 Persistent Volume을 쓰라"는 권고가 나옵니다.

이미지를 바이트 레벨에서 까 보기

docker pull nginx:1.25
docker save nginx:1.25 -o nginx.tar
tar -xf nginx.tar -C nginx-inspect
ls nginx-inspect
# manifest.json  repositories  /layer.tar  ...

# manifest.json 안을 보면
cat nginx-inspect/manifest.json | jq
# [
#   {
#     "Config": ".json",
#     "RepoTags": ["nginx:1.25"],
#     "Layers": [
#       "/layer.tar",
#       "/layer.tar",
#       ...
#     ]
#   }
# ]

각 layer.tar을 풀어 보면 단순히 디렉터리 트리입니다. 컨테이너 이미지는 복잡한 포맷이 아니라 "tar들의 모음 + 메타 JSON"이 전부라는 점을 기억해 두면, 이미지 풀링 실패 같은 문제를 디버깅할 때 덜 무섭습니다.

1.9가상 실습 · docker run 안쪽에서 무엇이 일어나는가

이제까지의 모든 것을 한 번에 묶어 봅시다. docker run -p 8080:80 nginx 한 줄이 실제로 유발하는 시스템 수준 사건들을 14단계로 나눠 봤습니다. 이 흐름을 익혀 두면 K8s가 Pod를 띄우는 Part 9의 "250ms 타임라인"이 훨씬 빨리 들어옵니다.

T+0ms
docker CLI가 Docker 데몬에 HTTP 요청
dockerd는 유닉스 소켓(/var/run/docker.sock)에서 요청을 받습니다. 인자는 JSON으로 전송됩니다.
T+20ms
이미지 존재 확인 → 없으면 풀링
레지스트리에 HTTPS로 매니페스트를 받고, 이미 있는 레이어는 스킵합니다. sha256로 무결성 검증.
T+200ms
overlayfs 스냅샷 생성
lower(이미지 레이어들) + upper(쓰기용 빈 디렉터리) + work를 mount -t overlay로 결합.
T+220ms
OCI Runtime Spec JSON 생성
config.json에 루트 경로, 명령(nginx -g 'daemon off;'), 환경 변수, 마운트, capabilities, cgroup 경로가 채워집니다.
T+230ms
containerd-shim 포크
각 컨테이너마다 한 개씩 뜨는 shim. stdout/stderr 파이프와 exit status 관측 담당.
T+235ms
runc가 clone() 호출
CLONE_NEWNS|CLONE_NEWPID|CLONE_NEWNET|CLONE_NEWUTS|CLONE_NEWIPC|CLONE_NEWCGROUP 플래그와 함께. 새 namespace가 만들어집니다.
T+240ms
setuid·capabilities 설정
대부분의 capabilities를 떨어뜨리고(dropped), 최소한의 권한(CAP_NET_BIND_SERVICE 등)만 남깁니다.
T+245ms
pivot_root
루트 파일 시스템을 이미지의 overlayfs로 전환. 이후 컨테이너는 호스트의 /를 볼 수 없습니다.
T+250ms
veth 페어 생성
한 쪽은 vethA@ifX로 호스트 브리지(docker0)에 꽂고, 다른 쪽은 컨테이너 net 네임스페이스로 이동 → eth0으로 이름 변경.
T+260ms
iptables PREROUTING 규칙 추가
-p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80. 호스트 8080 → 컨테이너 80으로 변환.
T+270ms
cgroup 설정
/sys/fs/cgroup/...에 cgroup 디렉터리를 만들고 PID를 넣습니다. limits가 있으면 cpu.max, memory.max 기록.
T+275ms
execve(nginx)
프로세스 이미지가 교체됩니다. PID 1은 이제 nginx master.
T+300ms
nginx가 80 포트 bind·listen
컨테이너의 eth0 인터페이스 위에서 bind(80) → listen().
T+310ms
엔드포인트 준비 완료
외부에서 http://<host>:8080 접근 시 ① 커널 netfilter DNAT → ② veth → ③ 컨테이너 eth0 → ④ nginx 응답.

이 14단계 중 Kubernetes 문맥에서 달라지는 것은 (10)의 포트 바인딩 방식과 (1)의 요청 주체(사용자 CLI 대신 kubelet)뿐입니다. 나머지 "컨테이너를 띄운다"의 뼈대는 동일합니다. 이 관점이 본 문서 전체의 북극성입니다.

Part 1 · Self Check
Q1. 컨테이너가 VM보다 가벼운 가장 큰 이유는 무엇인가요?
  1. 컨테이너는 커널 모드에서 동작하기 때문
  2. 컨테이너는 파일 시스템을 쓰지 않기 때문
  3. 컨테이너는 호스트의 커널을 공유하고, 하이퍼바이저 계층을 거치지 않기 때문
  4. 컨테이너는 systemd가 관리하기 때문
VM은 각자 커널을 부팅하고 하드웨어를 에뮬레이션하느라 무겁습니다. 컨테이너는 호스트 커널을 namespace+cgroup으로 나눠 쓰므로 프로세스 기동만큼 가볍습니다.
Q2. cpu.max 50000 100000 설정이 의미하는 것은?
  1. 1초에 50ms만 CPU를 쓴다
  2. 100ms마다 최대 50ms의 CPU 시간을 쓸 수 있다 (대략 0.5 코어)
  3. CPU 주파수를 50MHz로 고정한다
  4. 최대 100개 스레드만 허용한다
cgroup v2의 cpu.max는 "quota period" 쌍입니다. period 안에 quota만큼 쓰면 throttle됩니다.
Q3. 다음 중 컨테이너 관점에서 커널 네임스페이스로 격리되지 않는 것은?
  1. 프로세스 목록 (ps aux)
  2. 네트워크 인터페이스 목록 (ip link)
  3. 호스트 이름 (hostname)
  4. CPU의 클럭 속도 (/proc/cpuinfo)
CPU 주파수·모델·코어 수는 네임스페이스로 숨길 수 없습니다. 컨테이너 안에서 /proc/cpuinfo를 보면 호스트와 같은 값이 나옵니다.

PART 2 · Architecture

K8s 아키텍처 심층

컨트롤 플레인 5대장과 노드 에이전트가 어떻게 협력하며, 그 핵심인 etcd·Watch·Admission·Scheduler가 내부적으로 어떻게 동작하는지를 다룹니다.

2.1인터랙티브 구조도

Kubernetes 클러스터는 크게 컨트롤 플레인(Control Plane)과 워커 노드(Worker Node) 두 덩어리로 나뉩니다. 아래 다이어그램의 각 상자를 클릭하면 우측에서 해당 컴포넌트의 상세 설명이 슬라이드로 들어옵니다.

각 상자 클릭 시 상세 패널 표시 · 점선 박스는 논리 경계 · 화살표는 주요 gRPC/HTTPS 흐름

이 그림에서 기억해야 할 두 가지 사실이 있습니다. 첫째, etcd와 직접 대화하는 것은 kube-apiserver뿐입니다. 스케줄러·컨트롤러·kubelet 그 누구도 etcd에 바로 붙지 않습니다. 둘째, 컨트롤 플레인과 노드는 영구적 TCP 연결이 없습니다 — kubelet이 주기적으로 apiserver에 GET /api/v1/pods?watch=1을 열어 변경 사항을 스트리밍으로 받을 뿐입니다. 이 두 설계 결정이 Kubernetes의 탄력성과 확장성을 상당 부분 설명합니다.

2.2컨트롤 플레인 해부

kube-apiserver — 유일한 정문

외부(kubectl, 컨트롤러, kubelet)로부터 들어오는 모든 요청은 apiserver를 거칩니다. 요청 처리는 다음 5단계 파이프라인으로 흐릅니다.

(1) TLS 종결 ← client 인증서 / 서비스 계정 JWT 검증 (2) Authentication ← x509, OIDC, webhook, ServiceAccount 토큰 중 하나로 사용자 신원 확정 (3) Authorization ← RBAC(또는 Webhook) — "이 사용자가 이 verb를 이 resource에 실행 가능?" (4) Admission ← Mutating → Validating (CRD 정책, ValidatingAdmissionPolicy) (5) Storage ← etcd에 read/write, Watch 스트림에 이벤트 브로드캐스트

정말로 중요한 점: apiserver는 상태를 가지지 않습니다(stateless). 모든 지속 상태는 etcd에 있습니다. 그래서 apiserver를 수평으로 확장하는 것이 자연스럽고, 장애 시 교체도 간단합니다.

kube-controller-manager — reconcile의 집합

컨트롤러 매니저는 40개 이상의 "컨트롤러 루프"를 한 바이너리 안에서 돌립니다. 각 루프는 for { watch; diff; act; } 형태입니다. 대표적인 컨트롤러 몇 개:

  • Deployment Controller — Deployment를 보고 ReplicaSet을 생성·업데이트
  • ReplicaSet Controller — ReplicaSet을 보고 필요한 수만큼 Pod 생성·삭제
  • Node Controller — kubelet의 하트비트(리스)가 끊기면 노드를 NotReady로 표시, 일정 시간 후 Pod evict
  • ServiceAccount Controller — 네임스페이스마다 default SA 자동 생성
  • Endpoint/EndpointSlice Controller — Service의 셀렉터와 매칭되는 Pod의 IP를 모아 EndpointSlice 업데이트
  • GC Controller — orphan 객체 회수, ownerReferences 기반 종속 삭제

kube-scheduler

Pod가 생성되고 아직 spec.nodeName이 비어 있으면 스케줄러가 나섭니다. 알고리즘은 뒤의 2.6에서 자세히 봅니다.

cloud-controller-manager (CCM)

클라우드 특화 로직(LoadBalancer 만들기, 노드 메타데이터 읽기, 라우팅 테이블 설정)을 분리한 바이너리입니다. AWS·GCP·Azure는 각각 자체 CCM을 제공합니다. 온프레미스 클러스터라면 이 바이너리는 없을 수 있습니다.

2.3etcd와 Raft

etcd는 Kubernetes의 유일한 영구 저장소입니다. 모든 Pod, Service, ConfigMap, Secret의 상태가 여기에 KV 쌍으로 담깁니다. K8s의 가용성·일관성 특성은 사실상 etcd의 그것과 동일합니다.

Raft 합의 알고리즘

etcd는 Raft라는 합의 알고리즘으로 여러 노드 간의 일관된 상태를 유지합니다. Raft의 골자:

  1. Leader election: 노드들 중 하나가 리더가 되고, 나머지는 팔로워가 됩니다. 리더가 죽으면 재선출.
  2. Log replication: 쓰기(Put)는 리더만 처리합니다. 리더는 변경을 로그로 기록하고, 과반수(quorum)의 팔로워에게 복제된 뒤에야 "커밋"으로 인정합니다.
  3. Safety: 한 번 커밋된 로그는 절대 바뀌지 않습니다 — 리더가 바뀌어도.

왜 홀수 노드인가

쿼럼(과반수)이 필요하므로 3노드면 2가 과반, 5노드면 3이 과반입니다. 짝수 노드는 쿼럼 경계가 애매해 리더 선출이 교착되기 쉽고, 추가 노드로 얻는 내결함성이 제한적입니다 (4노드 클러스터의 쿼럼은 3 — 3노드와 같은 장애 허용치 1, 비용만 더). 그래서 대개 3 또는 5를 씁니다.

Split-brain 방지

네트워크 파티션이 일어나 클러스터가 두 덩어리로 갈라지면, 한쪽에만 과반수가 있습니다. 과반수를 가진 쪽만 리더를 뽑을 수 있으므로 두 리더가 동시에 존재하며 서로 다른 커밋을 만드는 사태는 일어나지 않습니다. 이것이 Raft가 CAP 정리의 C(일관성)를 택한 이유입니다.

K8s의 etcd 사용 패턴

  • 쓰기는 드물고 읽기(Watch)가 많음: 모든 컨트롤러가 Watch를 열어 상태 변화를 스트리밍으로 받음
  • 키는 리소스 버전(RV)으로 모노토닉 증가: 컨트롤러가 "내가 본 마지막 RV 이후"만 받아 idempotent 처리
  • Compact & Defrag: 오래된 revision을 주기적으로 compact, 디스크 공간 회수를 위해 defrag 필요
REAL-WORLD etcd 디스크 I/O 레이턴시가 12ms를 넘어가면 클러스터 전체가 느려집니다. SSD 필수이고, 네트워크 지연이 낮은 같은 AZ 혹은 같은 랙에 배치하는 것이 표준입니다. 대규모 클러스터(수천 노드)에서 etcd는 apiserver와 함께 제일 먼저 병목이 되는 지점입니다.

2.4Watch·Informer 패턴

Kubernetes 내부에서 가장 많이 쓰이는 패턴 하나만 꼽으라면 List-Watch입니다. 모든 컨트롤러(kube-controller-manager의 40여 개 + 사용자 Operator들)가 이 패턴으로 동작합니다.

왜 Watch인가

만일 컨트롤러가 "매초 모든 Pod를 GET"한다면, Pod가 5만 개 있는 클러스터에서 5만 건/초의 트래픽이 apiserver에 쏟아집니다. 낭비도 심하고, "방금 바뀐 Pod"를 감지하는 데 최대 1초가 걸립니다. 대신 한 번 LIST해서 초기 상태를 받고, 이후 Watch 스트림을 열어 증분(add/update/delete)만 받으면 트래픽은 실제 변경량에만 비례하고 지연은 밀리초입니다.

Informer — client-go의 고수준 추상

Kubernetes의 Go 클라이언트 라이브러리 client-go는 Informer라는 고수준 API를 제공합니다. Informer의 내부 구조:

Reflector ← List + Watch 수행, 받은 객체를 DeltaFIFO에 push ↓ DeltaFIFO ← Added/Updated/Deleted 이벤트 큐 ↓ Indexer (thread-safe cache) ← 사용자 코드가 읽는 in-memory 스토어 ↓ EventHandler ← OnAdd/OnUpdate/OnDelete 콜백 호출 ↓ WorkQueue ← 처리할 key들을 모음 (rate-limited) ↓ Worker goroutine ← queue에서 꺼내 reconcile() 수행

이 구조의 장점은 (1) apiserver 부하가 낮고, (2) 재시작 시 전체 List로 캐시를 복구하며, (3) 네트워크가 끊겨 Watch가 죽어도 resourceVersion을 기억해 그 이후부터 재개할 수 있다는 점입니다.

ResourceVersion의 정체

모든 객체에는 metadata.resourceVersion이 있습니다. 이는 etcd의 revision 번호이고, 클러스터 전체에서 모노토닉하게 증가합니다. Watch 요청에 ?resourceVersion=12345를 붙이면 "12345 이후 변경"만 스트림으로 받습니다. 이 값은 다른 객체와 비교하면 안 됩니다 — 같은 리소스 종류 내에서만 의미 있습니다.

2.5Admission 체인

Authentication/Authorization을 통과한 요청은 Admission 단계에서 한 번 더 검열됩니다. 두 종류가 있습니다.

  • Mutating Admission: 객체를 수정할 수 있음. 예: PodSecurity가 기본 securityContext를 채움, sidecar 주입.
  • Validating Admission: 객체를 허가/거부함. 예: ResourceQuota 초과 차단, ValidatingAdmissionPolicy(CEL).

빌트인 Admission 플러그인

apiserver 바이너리에 내장된 플러그인만 30개 이상입니다. 중요한 것 몇 개:

NamespaceLifecycle
존재하지 않는 네임스페이스의 객체 생성 거부, 삭제 중인 네임스페이스의 생성 거부.
LimitRanger
LimitRange 정책에 따라 기본 리소스 limits 자동 추가.
ResourceQuota
네임스페이스 쿼터 초과 요청 거부.
PodSecurity (1.25+)
네임스페이스 레이블에 따라 Privileged/Baseline/Restricted 검증.
ServiceAccount
Pod에 SA 토큰 볼륨 자동 마운트.
MutatingAdmissionWebhook / ValidatingAdmissionWebhook
외부 HTTPS webhook 호출 — OPA/Gatekeeper, Kyverno, cert-manager, Istio 사이드카 주입 등이 이 메커니즘을 사용.
ValidatingAdmissionPolicy (1.30 GA)
Webhook 없이 CEL(Common Expression Language)로 정책 표현. 낮은 레이턴시·쉬운 디버깅.
장애 사례 "Webhook 서버가 죽으면 전체 클러스터가 마비된다"는 유명한 장애 패턴이 있습니다. failurePolicy: Fail로 설정된 웹훅이 응답하지 않으면 apiserver가 모든 쓰기를 거부합니다. 따라서 웹훅은 (1) failurePolicy: Ignore를 고려하거나 (2) objectSelector로 범위를 좁히거나 (3) 네임스페이스를 제외하는 것이 표준 방어입니다. Part 8의 사례 중 하나로 나옵니다.

2.6스케줄러 내부

kube-scheduler는 한 번에 한 Pod씩 처리하는 2단계 파이프라인입니다: Filter → Score.

Filter 단계

노드 목록에서 "이 Pod를 실행할 수 없는 노드"를 제외합니다. 기준은 여러 플러그인의 AND입니다:

  • 노드에 요청한 리소스(CPU/Mem/GPU)가 남아 있는가
  • 노드의 taint를 Pod의 toleration이 커버하는가
  • nodeSelector/nodeAffinity 조건을 만족하는가
  • Pod가 요청한 PV가 해당 노드 AZ에서 접근 가능한가(VolumeBinding)
  • TopologySpreadConstraints를 위반하지 않는가
  • podAffinity/antiAffinity 조건

Score 단계

남은 노드들에 0~100 점수를 매깁니다. 높은 점수가 선호. 대표 플러그인:

  • NodeResourcesFit (LeastAllocated): 리소스가 남은 노드 선호 — 분산
  • NodeResourcesFit (MostAllocated): 리소스가 꽉 찬 노드 선호 — 빈 팩(bin-packing), Karpenter의 기본 전략
  • InterPodAffinity: 선호하는 Pod들과 가까이/멀리
  • TaintToleration: PreferNoSchedule taint를 피하면 가점
  • ImageLocality: 이미 해당 이미지가 캐시된 노드 가점

Bind

최고 점수 노드에 Pod를 바인드 — 이는 spec.nodeName 필드를 업데이트하는 것뿐입니다. 실제 실행은 해당 노드의 kubelet이 Watch로 감지해 처리합니다.

Preemption (선점)

높은 우선순위 Pod가 스케줄링에 실패하면, 낮은 우선순위 Pod를 같은 노드에서 evict하고 자리를 만들 수 있습니다. PriorityClass로 우선순위를 부여하며, 기본 컴포넌트(CoreDNS 등)는 system-cluster-critical (2000000000)로 보호됩니다.

2.7kubelet의 24시간

kubelet은 각 노드에서 돌며 "이 노드에 있어야 할 Pod가 있다/없다"를 지속적으로 재조정합니다. 주요 소스와 루프를 알아 두면 Part 9의 초정밀 타임라인을 훨씬 쉽게 읽을 수 있습니다.

Pod 소스 3가지

  • API server — Watch로 이 노드에 바인드된 Pod 목록을 받음 (기본)
  • Static Pods — /etc/kubernetes/manifests/의 YAML 파일, apiserver에 "mirror pod"로 등록됨. kube-apiserver·etcd 자체가 이 방식으로 돌 때가 많음.
  • HTTP endpoint — --manifest-url (거의 안 쓰임)

SyncLoop

kubelet의 메인 루프는 syncLoop입니다. 이벤트 원천이 위의 3가지 소스 + 컨테이너 상태 변경(PLEG) + 주기적 sync. 각 이벤트는 HandlePodAdditions/Updates/Removals/Syncs를 호출하며, 이것이 다음 단계로 진행됩니다.

syncPod() ├─ checkGuard (중복 실행 방지) ├─ generateAPIPodStatus ├─ computePodActions (컨테이너를 create / kill / restart?) ├─ killContainer(s) (필요 시 SIGTERM → preStop → SIGKILL) ├─ createContainer(s) │ ├─ pull image (필요 시) │ ├─ CRI: RunPodSandbox ← pause 컨테이너 + netns 생성, CNI ADD 호출 │ ├─ CRI: CreateContainer │ └─ CRI: StartContainer ├─ probe 업데이트 (liveness/readiness/startup) └─ update status → apiserver

PLEG — Pod Lifecycle Event Generator

kubelet이 "컨테이너가 죽었음/살아났음"을 알아채는 메커니즘입니다. 주기적으로 CRI의 ListPodSandbox + ListContainers를 호출해 상태 스냅샷을 비교합니다. 이 호출이 느려지면 kubelet 전체가 정체되고 "PLEG is not healthy" 로그가 찍힙니다. Part 8의 노드 장애 사례에서 다시 만납니다.

노드 리스(Lease) 하트비트

kubelet은 10초마다 coordination.k8s.io/Lease 객체를 업데이트해 "나는 살아있다"고 알립니다. Node Controller는 node-monitor-grace-period(기본 40초)에 리스 업데이트가 없으면 노드를 NotReady로 마크, pod-eviction-timeout(기본 5분) 뒤 Pod를 다른 노드로 evict합니다.

3.1Pod · Kubernetes의 최소 단위

Kubernetes는 개별 컨테이너를 스케줄링하지 않습니다. Pod라는 묶음을 스케줄링합니다. Pod는 "함께 같은 네트워크·스토리지를 공유하는 하나 이상의 컨테이너"입니다. 대부분의 Pod는 컨테이너 하나짜리지만, 사이드카를 두는 경우 둘 이상이 됩니다.

Pod가 공유하는 것

  • network namespace: 모든 컨테이너가 같은 127.0.0.1와 포트 공간을 공유. 내부 통신은 localhost로 가능.
  • IPC / UTS namespace: 같은 호스트명, 공유 메모리
  • 볼륨: spec.volumes에 선언된 볼륨은 여러 컨테이너가 마운트 가능
  • cgroup의 부모: 같은 kubepods-* 슬라이스 아래 배치

pause 컨테이너

각 Pod에는 보이지 않는 pause 컨테이너가 PID 1로 동작합니다. 역할은 두 가지: (1) namespace를 잡고 있는 "앵커" — 모든 사용자 컨테이너가 죽었다 살아나도 namespace는 유지, (2) 좀비 프로세스 수확(wait()). 이미지는 수십 KB에 불과한 C 바이너리입니다.

샘플 Pod YAML

apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  terminationGracePeriodSeconds: 30
  containers:
  - name: nginx
    image: nginx:1.25
    ports:
    - containerPort: 80
    resources:
      requests:  { cpu: 100m, memory: 128Mi }
      limits:    { cpu: 500m, memory: 256Mi }
    readinessProbe:
      httpGet: { path: /, port: 80 }
      initialDelaySeconds: 3
      periodSeconds: 10
    livenessProbe:
      httpGet: { path: /healthz, port: 80 }
      periodSeconds: 20
      failureThreshold: 3
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "nginx -s quit; sleep 10"]
  - name: logger          # 사이드카
    image: fluent/fluent-bit:3.0
    volumeMounts:
    - name: logs
      mountPath: /var/log/nginx
  volumes:
  - name: logs
    emptyDir: {}

requests vs limits — QoS의 근원

requests는 스케줄링에 사용되는 최소 보장량입니다. 스케줄러는 이 값을 보고 노드의 남은 리소스를 계산합니다. limits는 런타임 상한으로 cgroup의 cpu.max와 memory.max로 번역됩니다. 이 둘의 관계로 Pod의 QoS 클래스가 결정됩니다:

QoS조건OOM 시 우선순위용도
Guaranteed모든 컨테이너가 requests = limits마지막에 죽음DB·상태저장 워크로드
Burstablerequests < limits 이거나 일부만 설정중간대부분의 서비스
BestEffortrequests·limits 모두 미지정가장 먼저 죽음배치 잡, 비중요 워크로드

Probes — liveness, readiness, startup

livenessProbe
실패 시 컨테이너를 재시작. 데드락 감지 목적. 너무 공격적이면 정상 Pod를 무한 재시작시킴.
readinessProbe
실패 시 Service의 EndpointSlice에서 제외. 재시작은 하지 않음. 초기 warm-up 중이거나 백엔드 연결 준비 안 됐을 때 유용.
startupProbe
시작 시간이 긴 애플리케이션(JVM, 대용량 캐시 워밍) 보호용. 이 프로브가 성공할 때까지 liveness/readiness 비활성화.
함정 livenessProbe를 외부 의존성(DB 연결) 체크에 두면 안 됩니다. DB 일시 장애에 Pod 전체가 재시작되는 악순환. liveness는 "프로세스가 응답하는가"만, readiness는 "요청을 받을 준비가 됐는가"만 검사하는 것이 원칙입니다.

3.2Workload 7종

Pod는 직접 만들지 않는 것이 관례입니다. 대신 워크로드 리소스가 Pod의 수명 관리를 맡습니다. 7종을 용도별로 정리하면:

리소스정체성업데이트대표 용도
Deployment교체 가능한 stateless PodRollingUpdate (기본) / Recreate웹 앱, API 서버
ReplicaSetDeployment의 하위 — 직접 건들지 말 것-Deployment 뒤에서 Pod 수 유지
StatefulSet순서 있는 정체성을 가진 Pod (web-0, web-1…)OnDelete / RollingUpdateDB, Kafka, Zookeeper
DaemonSet모든 노드(또는 조건 맞는 노드)에 1개씩RollingUpdate / OnDelete로그 수집기, CNI, CSI 드라이버
JobN개 완료 후 종료-배치 작업, 마이그레이션
CronJob스케줄에 따라 Job 생성-정기 백업, 리포트
ReplicationController(구식) Deployment의 조상-신규 사용 금지

Deployment 해부

apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%        # 업데이트 중 추가 생성 가능한 Pod 비율
      maxUnavailable: 25%  # 업데이트 중 동시에 내려도 되는 Pod 비율
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
      - { name: web, image: myapp:v1.2.3 }

Deployment 컨트롤러는 변경 시 새 ReplicaSet을 만들고, 옛 RS의 Pod 수를 서서히 줄이며 새 RS의 수를 늘립니다. 롤백은 옛 RS에 다시 스케일을 올리는 식이라 즉시입니다. kubectl rollout undo를 쓰면 이 동작을 트리거합니다.

StatefulSet — 정체성의 무게

Deployment와 달리 StatefulSet의 Pod는 web-0, web-1, web-2처럼 고유 이름을 갖고, 순서대로 생성되고 역순으로 삭제됩니다. 각 Pod는 자기 PVC를 가지며, Pod가 재생성돼도 같은 볼륨에 다시 붙습니다. 이 정체성이 DB·큐 같은 상태저장 시스템에 필수적입니다. 

apiVersion: apps/v1
kind: StatefulSet
metadata: { name: postgres }
spec:
  serviceName: postgres-headless  # 필수 — headless service 지정
  replicas: 3
  selector: { matchLabels: { app: postgres } }
  template:
    metadata: { labels: { app: postgres } }
    spec:
      containers:
      - name: postgres
        image: postgres:16
        volumeMounts: [{ name: data, mountPath: /var/lib/postgresql/data }]
  volumeClaimTemplates:
  - metadata: { name: data }
    spec:
      accessModes: ["ReadWriteOnce"]
      resources: { requests: { storage: 100Gi } }
      storageClassName: gp3

volumeClaimTemplates이 포인트입니다. 각 Pod마다 data-postgres-0, data-postgres-1 PVC가 자동 생성되고, 해당 Pod에만 바인드됩니다.

DaemonSet

DaemonSet은 "모든 노드에 한 Pod"를 보장합니다. nodeSelector나 affinity로 대상 노드를 좁힐 수 있습니다. 대표 사용자: kube-proxy, CNI 드라이버(Calico, Cilium), CSI node plugin, 로그 수집기(fluent-bit), 노드 메트릭 에이전트(node-exporter).

Job과 CronJob

Job은 Pod를 N개 완료시킵니다. parallelism과 completions로 병렬도와 목표 성공 수를 지정. CronJob은 crontab 표기를 받아 Job을 주기적으로 생성합니다. 중요 필드:

  • concurrencyPolicy: Allow|Forbid|Replace — 동시에 실행 중인 Job이 있을 때의 정책
  • startingDeadlineSeconds — 스케줄 시간 지났을 때 얼마까지 여전히 시작 시도할지
  • ttlSecondsAfterFinished — 완료된 Job을 자동 삭제할 시간

3.3Service와 DNS · 서비스 디스커버리

Pod의 IP는 언제든 바뀝니다(죽고 재생성). 그래서 안정된 접근 지점이 필요하고, 그것이 Service입니다. Service는 "셀렉터로 Pod 그룹을 고르고, 그 앞에 고정 IP+DNS 이름을 제공"하는 추상입니다.

4가지 타입

Type어디서 접근 가능?구현
ClusterIP (기본)클러스터 내부만가상 IP + kube-proxy 룰
NodePort노드 IP:PORT로 외부 접근NodePort 30000-32767 열림 + iptables DNAT

Service의 예시

apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  type: ClusterIP
  selector: { app: web }
  ports:
  - name: http
    port: 80            # Service의 포트
    targetPort: 8080    # Pod의 containerPort
    protocol: TCP

Endpoints vs EndpointSlice

Service를 만들면 Endpoints(구) 또는 EndpointSlice(신, 1.21+ 기본)가 함께 생성되며, 여기에 매칭된 Pod의 IP·포트 목록이 담깁니다. 단일 Endpoints 객체의 경우 수천 Pod가 있으면 업데이트가 Watch에 부하를 주고, 전체를 다시 보냅니다. EndpointSlice는 100개씩 끊어 부분 업데이트를 보내므로 대규모에서 훨씬 효율적입니다.

Headless Service

spec.clusterIP: None으로 설정하면 가상 IP가 안 만들어지고, DNS 질의는 각 Pod의 IP 목록을 A 레코드로 반환합니다. StatefulSet과 함께 써서 web-0.web.default.svc.cluster.local처럼 개별 Pod에 DNS로 접근할 때 필수.

DNS 이름 규칙

클러스터 안에서 모든 Service는 <name>.<namespace>.svc.cluster.local 형태의 DNS 이름을 갖습니다. 같은 네임스페이스에서는 <name>만으로도 해석됩니다. CoreDNS가 이를 담당합니다.

심화 resolv.conf의 ndots:5 설정이 기본입니다. 도메인에 점이 5개 미만이면 search 도메인을 먼저 시도합니다. "google.com" 같은 외부 도메인을 호출하면 google.com.default.svc.cluster.local부터 물어보고 실패, 다시 google.com.svc.cluster.local... 여러 차례 실패한 뒤에야 외부 DNS로 나갑니다. 지연의 원인이 됩니다. Part 4·Part 8에서 더 다룹니다.

3.4Ingress와 Gateway API

Service는 L4입니다. HTTP 경로 기반 라우팅, TLS 종결, 호스트 기반 분기 같은 L7 기능이 필요하면 Ingress를 씁니다. Ingress는 "규칙"일 뿐이고, 실제로 리버스 프록시를 돌리는 것은 Ingress Controller(nginx, Traefik, Istio Gateway, AWS LB Controller 등)입니다. 

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  tls:
  - hosts: [shop.example.com]
    secretName: shop-tls
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api(/|$)(.*)
        pathType: ImplementationSpecific
        backend: { service: { name: api, port: { number: 80 } } }
      - path: /
        pathType: Prefix
        backend: { service: { name: web, port: { number: 80 } } }

Gateway API — Ingress의 후계자

Ingress는 2015년 알파 시절 디자인이라 한계가 많습니다. 주석(annotation)으로 모든 고급 기능을 표현하다 보니 컨트롤러마다 호환되지 않고, 역할 분리(플랫폼 운영자 vs 앱 개발자)가 어렵습니다. Gateway API(2023 GA)는 이를 해결합니다:

  • GatewayClass — 인프라팀이 만든 게이트웨이 구현 종류
  • Gateway — 실제로 트래픽을 받는 리스너(호스트·포트·인증서)
  • HTTPRoute / TCPRoute / TLSRoute — 앱팀이 만드는 라우팅 규칙
  • 역할 분리가 명시적이고, 타입이 강해 주석 의존이 사라짐
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: main }
spec:
  gatewayClassName: istio
  listeners:
  - name: https
    port: 443
    protocol: HTTPS
    hostname: "*.example.com"
    tls:
      certificateRefs:
      - name: wildcard-tls
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop }
spec:
  parentRefs: [{ name: main }]
  hostnames: [shop.example.com]
  rules:
  - matches: [{ path: { type: PathPrefix, value: /api } }]
    backendRefs: [{ name: api, port: 80 }]
  - matches: [{ path: { type: PathPrefix, value: / } }]
    backendRefs: [{ name: web, port: 80 }]

3.5ConfigMap과 Secret

애플리케이션 설정과 이미지를 분리하는 것이 12-factor의 원칙입니다. Kubernetes는 두 리소스로 이 분리를 제공합니다.

ConfigMap — 평문 설정

apiVersion: v1
kind: ConfigMap
metadata: { name: app-config }
data:
  LOG_LEVEL: info
  FEATURE_X: "true"
  nginx.conf: |
    server { listen 80; location / { return 200 "hi"; } }

사용 방법 세 가지:

# 1) 환경변수로 주입
spec.containers[].envFrom:
- configMapRef: { name: app-config }

# 2) 파일로 마운트 (키 = 파일명)
spec.volumes:
- name: cfg
  configMap: { name: app-config, items: [{ key: nginx.conf, path: nginx.conf }] }
spec.containers[].volumeMounts:
- { name: cfg, mountPath: /etc/nginx/conf.d }

# 3) 일부 키만 env에
spec.containers[].env:
- name: LOG_LEVEL
  valueFrom: { configMapKeyRef: { name: app-config, key: LOG_LEVEL } }

Secret — "base64는 암호화가 아니다"

Secret은 ConfigMap과 거의 같은 형태지만 값이 base64로 인코딩됩니다. 중요 — base64는 단순 인코딩으로, 암호화가 아닙니다. etcd에 접근할 수 있으면 Secret을 그대로 볼 수 있습니다. 그래서 실무 방어는 3가지:

  1. etcd encryption-at-rest: apiserver 옵션 --encryption-provider-config로 etcd 저장 시 AES 암호화. EKS는 KMS로 이 키를 보호하는 옵션을 제공합니다.
  2. 외부 시크릿 관리: external-secrets-operator로 AWS Secrets Manager·Vault의 값을 Secret으로 동기화.
  3. CSI Secret Store: Pod 시작 시 마운트 타이밍에만 시크릿을 파일로 내려받고, etcd에는 아무것도 저장하지 않음.
WATCH OUT kubectl get secret my-secret -o yaml로 base64 값이 보인다고 놀라지 마세요 — 그게 정상입니다. 실제 방어선은 RBAC(secrets 읽기 권한 제한)과 etcd 암호화입니다.

3.6Volume·PV·PVC

Pod의 컨테이너 파일 시스템은 기본적으로 휘발성입니다(Pod 삭제 시 overlayfs upper가 날아감). 영속 데이터를 저장하려면 Volume을 붙여야 합니다. K8s의 볼륨은 20종 이상이지만, 핵심 세 가지 종류만 기억하면 됩니다.

Ephemeral volumes
emptyDir, configMap, secret, downwardAPI, projected. Pod 수명과 함께 사라짐. 임시 작업 공간이나 설정 주입에 사용.
Persistent Volumes (PV)
클러스터 범위의 스토리지 자원. 관리자가 수동 생성(정적)하거나 StorageClass로 자동 생성(동적). 실제 구현은 CSI 드라이버.
Projected volumes
여러 볼륨을 한 디렉터리로 합치는 추상. Secret + ConfigMap + ServiceAccount token을 하나의 마운트로 표현할 때 사용.

PV와 PVC

PV(PersistentVolume)는 실제 디스크(EBS 볼륨, EFS, NFS, Ceph RBD 등)의 레퍼런스입니다. PVC(PersistentVolumeClaim)는 "나는 용량 100Gi, RWO, gp3 StorageClass가 필요하다"는 요청입니다. K8s는 PVC를 적절한 PV에 바인드합니다. 정적이면 미리 만든 PV 중 조건 맞는 것, 동적이면 StorageClass가 새 PV를 즉시 생성. 

apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: data }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: gp3
  resources:
    requests: { storage: 20Gi }
---
# Pod에서 사용
spec:
  containers:
  - name: app
    volumeMounts: [{ name: data, mountPath: /data }]
  volumes:
  - name: data
    persistentVolumeClaim: { claimName: data }

AccessMode 4종

  • RWO (ReadWriteOnce) — 한 노드에서만 쓰기. EBS 같은 블록 스토리지.
  • ROX (ReadOnlyMany) — 여러 노드에서 읽기만.
  • RWX (ReadWriteMany) — 여러 노드에서 동시에 읽기·쓰기. NFS·EFS·CephFS.
  • RWOP (ReadWriteOncePod, 1.27+) — 한 Pod에서만 쓰기. 두 Pod가 같은 PVC를 잡는 레이스 방지.

3.7RBAC와 ServiceAccount

Kubernetes의 권한 체계는 RBAC(Role-Based Access Control) 기반입니다. 4개의 리소스로 구성됩니다.

ServiceAccount (SA)
Pod 내부의 애플리케이션이 apiserver에 요청할 때 쓰는 "신원". 네임스페이스에 속함.
Role / ClusterRole
Role은 네임스페이스 범위, ClusterRole은 클러스터 전역. "이 리소스에 어떤 verb를 할 수 있다"는 규칙의 묶음.
RoleBinding / ClusterRoleBinding
Role을 Subject(User, Group, SA)에 바인드.
apiVersion: v1
kind: ServiceAccount
metadata: { name: deployer, namespace: prod }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: deploy-manager, namespace: prod }
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: deployer-binds-deploy-manager, namespace: prod }
subjects:
- kind: ServiceAccount
  name: deployer
roleRef:
  kind: Role
  name: deploy-manager
  apiGroup: rbac.authorization.k8s.io

BoundServiceAccountToken (1.22+)

과거에는 모든 SA에 영구 토큰이 Secret으로 자동 생성됐습니다. 보안 취약 — 노출되면 무한정 유효했죠. 현재는 Projected Token Volume으로 JWT가 주기적으로 로테이션됩니다. 토큰에는 Pod·네임스페이스·SA 정보가 담겨 apiserver가 "이 토큰을 이 Pod가 사용 중인가"를 검증할 수 있습니다. 이 메커니즘이 EKS의 IRSA 작동의 기반입니다.

3.8네임스페이스 거버넌스

네임스페이스는 리소스를 논리적으로 그룹화하는 경계입니다. 팀·환경·프로젝트로 나눕니다. 혼자 쓰는 클러스터라도 기본 5개는 존재합니다.

  • default — 아무 지정 없이 만든 리소스가 들어감
  • kube-system — 클러스터 컴포넌트(kube-proxy, CoreDNS 등)
  • kube-public — 모두가 읽을 수 있는 리소스용(거의 안 씀)
  • kube-node-lease — 노드 하트비트(Lease) 저장

ResourceQuota

apiVersion: v1
kind: ResourceQuota
metadata: { name: team-a, namespace: team-a }
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    persistentvolumeclaims: "10"
    services.loadbalancers: "2"   # 예산 통제
    count/pods: "100"

ResourceQuota가 설정된 네임스페이스에서 requests·limits를 쓰지 않은 Pod 생성은 즉시 거부됩니다.

LimitRange

"requests·limits가 없으면 기본값으로 채워라" 같은 규칙. LimitRanger Admission이 읽어 Pod spec을 mutate합니다.

PriorityClass

Pod의 상대 우선순위. 숫자가 높을수록 먼저 스케줄링되고, 리소스 부족 시 낮은 우선순위 Pod를 선점(preempt)할 수 있습니다. system-cluster-critical(2000000000)은 CoreDNS 등이 씁니다. 사용자 Pod는 0~1000000000 범위에서 정합니다.

PART 4 · Networking

네트워킹 심층

초심자가 가장 먼저 벽에 부딪히는 영역입니다. CNI의 ADD 호출 한 번부터 Service IP가 실제 네트워크에 존재하지 않는다는 사실까지 — 패킷의 여정을 따라갑니다.

4.1Pod 네트워킹의 4대 요구사항

Kubernetes가 네트워크 구현을 고르지 않고 CNI(Container Network Interface)라는 플러그인 스펙만 정한 이유는, "아래 4가지만 지켜라"라는 추상화를 CNI 구현체들에 위임하기 위함입니다.

  1. 모든 Pod는 고유 IP를 가진다 — NAT 없이 통신 가능.
  2. 모든 Pod는 다른 모든 Pod와 NAT 없이 통신할 수 있다 — 같은 노드든 다른 노드든.
  3. 모든 노드의 에이전트(kubelet, kube-proxy)는 해당 노드의 모든 Pod와 통신할 수 있다.
  4. Pod가 보는 자기 IP는 다른 Pod가 보는 그 Pod의 IP와 같다 — NAT로 왜곡되지 않음.

이 요구사항은 프로그래머의 "그냥 IP로 통신하면 되네" 직관을 유지하기 위한 것입니다. 이 약속을 배반하는 네트워크 구성은 다양한 기묘한 버그를 낳습니다.

HISTORY Docker의 기본 브리지 네트워크는 조건 4번을 지키지 않습니다 — 컨테이너가 호스트에서 보면 172.17.x.x지만, 다른 호스트의 컨테이너에서 보면 호스트의 NAT된 IP로 보입니다. K8s가 "컨테이너 오케스트레이션의 네트워킹"을 처음부터 새로 정의해야 했던 이유입니다.

4.2CNI 스펙과 주요 구현

CNI(Container Network Interface) 스펙은 매우 단순합니다. "Pod를 만들 때 이 바이너리에 JSON을 주고 실행하면, IP와 라우팅이 설정된다"는 약속입니다.

CNI 플러그인의 수명주기

# kubelet이 새 Pod를 만들 때
/opt/cni/bin/calico  < stdin: JSON {CNI_COMMAND: ADD, CNI_NETNS: /var/run/netns/xxx, ...}
# 플러그인은 아래 작업을 수행하고 결과 JSON을 stdout으로
#   1. veth 페어 생성
#   2. 한쪽 끝을 Pod netns로 이동 → eth0으로 이름 변경
#   3. IP 할당 (IPAM 플러그인 호출)
#   4. 라우팅 테이블 설정
#   5. 노드 간 연결 설정 (오버레이 또는 BGP)
# 종료
/opt/cni/bin/calico  < stdin: JSON {CNI_COMMAND: DEL, ...}
# 반대 작업 수행

오버레이 vs 언더레이

VXLAN·IPIP 같은 오버레이는 Pod 패킷을 UDP/IP 헤더로 감싸 노드 간에 전달합니다. 장점: 언더레이 네트워크(클라우드 VPC, 데이터센터 라우터)가 Pod IP를 알 필요가 없음. 단점: 캡슐·탈캡슐 CPU 비용, MTU 조정 필요.
언더레이(BGP 등)는 Pod IP를 네트워크 장비가 직접 라우팅. 장점: 오버헤드 없음, 성능. 단점: 라우터 설정이 필요.

4.3kube-proxy 3모드 — 어떻게 Service IP가 작동하는가

Service IP는 "가상"이라고 했습니다. 실제 동작은 kube-proxy가 각 노드에 설치한 NAT 규칙에 달려 있습니다. 역사적으로 세 가지 모드가 있었습니다.

(1) userspace — 이제는 레거시

초기에는 kube-proxy가 유저 스페이스 프록시로 동작하며 각 Service마다 포트를 열고, iptables는 "모든 Service 패킷을 kube-proxy로 리다이렉트"하는 역할만 했습니다. 패킷이 유저 스페이스를 경유하니 느리고, 단일 실패점이었습니다. 거의 사용하지 않습니다.

(2) iptables — 가장 흔함

kube-proxy는 이제 패킷 경로에서 빠지고, iptables 규칙만 설치합니다. 예: 

iptables -t nat -L KUBE-SERVICES
# Chain KUBE-SVC-XXXX (for Service 10.96.0.5:80)
#   -m statistic --mode random --probability 0.333 -j KUBE-SEP-AAA
#   -m statistic --mode random --probability 0.500 -j KUBE-SEP-BBB
#   -j KUBE-SEP-CCC
#
# Chain KUBE-SEP-AAA (for Pod 10.244.1.2:8080)
#   -j DNAT --to-destination 10.244.1.2:8080

규칙 자체는 커널에서 실행되므로 빠르지만, 서비스 수·Pod 수에 비례해 규칙 수가 선형 증가합니다. 서비스 1만 개에서 규칙이 수십만 개가 되고, 규칙 갱신 때마다 전체 iptables-restore를 돌려 지연이 발생합니다.

(3) IPVS — 수천 서비스에 유리

IPVS(IP Virtual Server)는 리눅스 커널의 L4 로드 밸런서로 해시 테이블 기반이라 O(1) 조회입니다. kube-proxy를 --proxy-mode=ipvs로 띄우면 NAT 규칙을 IPVS로 관리합니다. 수백~수천 서비스가 있는 클러스터에서 지연이 현저히 줄어듭니다. 대신 IPVS가 커널 모듈로 로드돼야 하고, 진단 도구(ipvsadm)가 iptables와 다릅니다.

(4) eBPF (kube-proxy 대체)

Cilium은 eBPF 프로그램을 NIC·socket 훅에 붙여 iptables·IPVS 없이 같은 기능을 구현합니다. 소켓 수준에서 바로 목적지를 치환하기 때문에 패킷이 스택을 탈 필요가 없어 지연이 가장 낮습니다. kubectl -n kube-system delete ds kube-proxy로 kube-proxy를 아예 치울 수 있는 설정을 지원합니다.

성능 직관 서비스 수가 적으면 iptables·IPVS·eBPF 사이의 차이는 거의 없습니다. 수천 개 이상부터 의미가 생기고, 수만 개가 되면 eBPF/IPVS가 필수입니다. 그러나 "수만 서비스"가 아닌 이상 iptables로도 충분합니다.

4.4Service IP의 정체 · 패킷을 따라가기

같은 노드의 Pod A가 Service svc(ClusterIP 10.96.0.5:80)에 붙어있는 Pod B(10.244.1.2:8080)를 호출할 때, 패킷이 어떤 경로로 가는지 단계별로 따라가 봅니다. iptables 모드 가정.

[Pod A: curl 10.96.0.5:80] │ │ 패킷 src=10.244.2.5:53123 dst=10.96.0.5:80 ▼ Pod A의 eth0 (veth의 컨테이너 쪽) │ ▼ 호스트 bridge(cni0) 또는 veth peer │ ▼ netfilter PREROUTING: KUBE-SERVICES chain 매칭 │ → KUBE-SVC-xxx (ClusterIP 10.96.0.5) │ → KUBE-SEP-yyy (확률적으로 Pod B 선택) │ → DNAT: dst = 10.244.1.2:8080 ▼ 패킷 src=10.244.2.5:53123 dst=10.244.1.2:8080 │ ▼ 라우팅 결정: 10.244.1.2는 로컬 노드인가? │ ├── 같은 노드면 cni0 통해 Pod B eth0으로 └── 다른 노드면 CNI가 설치한 라우트 따라 노드 N 으로 송신 (VXLAN 캡슐화 또는 BGP 라우팅) │ ▼ 노드 N의 cni0 → Pod B eth0 │ ▼ [Pod B: 응답 src=10.244.1.2:8080 dst=10.244.2.5:53123] │ ▼ 응답 패킷이 노드 A로 돌아옴 │ conntrack 테이블이 "이 플로우는 10.96.0.5:80에서 온 것" 기억 │ POSTROUTING에서 src를 10.96.0.5:80으로 un-DNAT(SNAT 역방향) ▼ Pod A의 소켓은 10.96.0.5:80 응답으로 해석 → 성공

중요: Service IP는 네트워크 어디에도 실제로 존재하지 않습니다. 패킷의 목적지로만 나타나고, 즉시 Pod IP로 DNAT됩니다. 그래서 Service IP에 ping을 쏠 수 없고(ping은 ICMP로 DNAT 대상이 아님), ip addr에도 없습니다.

4.5CoreDNS와 DNS의 함정들

클러스터 DNS는 CoreDNS(2018년부터 kube-dns 대체)가 기본입니다. Pod로 실행되며, Service로 노출됩니다. 대부분 ConfigMap coredns의 Corefile로 설정이 끝납니다. 

.:53 {
    errors
    health { lameduck 5s }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
      pods insecure
      fallthrough in-addr.arpa ip6.arpa
      ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf {
      max_concurrent 1000
    }
    cache 30
    loop
    reload
    loadbalance
}

ndots:5의 함정

Pod의 /etc/resolv.conf는 자동으로 이렇게 설정됩니다: 

search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

ndots:5는 "도메인에 점이 5개 미만이면 먼저 search 도메인을 뒤에 붙여 시도하라"는 뜻입니다. google.com (점 1개)을 요청하면:

  1. google.com.default.svc.cluster.local — NXDOMAIN
  2. google.com.svc.cluster.local — NXDOMAIN
  3. google.com.cluster.local — NXDOMAIN
  4. google.com — 드디어 성공

4배의 DNS 질의. 대부분은 빠르지만, conntrack UDP race(아래) 같은 이슈와 만나면 지연이 크게 튑니다. 해결책: 외부 도메인 끝에 .을 붙여 FQDN으로 만들거나(google.com.), Pod에 dnsConfig.options.ndots: "2"로 재정의.

CoreDNS 5초 지연 — 유명한 conntrack race

같은 소켓에서 UDP 질의 2개를 빠르게 보내면 둘 다 같은 source 포트를 씁니다. 각 질의가 다른 Pod의 CoreDNS로 DNAT될 때 conntrack 항목이 동시에 추가되며 커널의 레이스 조건으로 일부가 드롭됩니다. DNS 클라이언트는 5초 타임아웃 후 재시도합니다. 관측적으로 "가끔 DNS가 정확히 5초 느리다"로 나타납니다.

방어 전략:

  • NodeLocal DNSCache — 각 노드에 DNS 캐시를 두어 TCP로 CoreDNS와 통신. UDP 레이스를 피함.
  • single-request-reopen — glibc 옵션으로 A/AAAA를 별도 소켓으로 보냄. dnsConfig.options에 추가.
  • use-vc — DNS 질의를 TCP로.

4.6NetworkPolicy — 기본은 "올오픈"

Kubernetes의 기본 네트워크는 "모든 Pod가 모든 Pod와 통신 가능"입니다. 이를 좁히려면 NetworkPolicy를 씁니다. NetworkPolicy가 효과를 내려면 CNI가 이를 구현해야 합니다(Calico, Cilium, Weave 등은 지원, Flannel 단독은 미지원). 

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: api-allow-web, namespace: prod }
spec:
  podSelector:
    matchLabels: { app: api }
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: web } }
    - namespaceSelector: { matchLabels: { team: platform } }
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - podSelector: { matchLabels: { app: db } }
    ports: [{ protocol: TCP, port: 5432 }]
  - to:     # DNS는 열어둬야 함
    - namespaceSelector: {}
      podSelector: { matchLabels: { k8s-app: kube-dns } }
    ports: [{ protocol: UDP, port: 53 }]

중요한 함정

  • NetworkPolicy는 거부 규칙이 아니라 허용 규칙입니다. 아무 정책도 없으면 올오픈, 하나라도 걸리면 그 Pod는 "화이트리스트 외 차단".
  • DNS를 잊지 마세요. egress 제한을 걸면서 CoreDNS에 53/UDP를 허용하지 않으면 이름 해석이 실패하고 앱이 먹통이 됩니다.
  • Namespace 단위의 차단은 default-deny-all 정책을 두고 필요한 것만 여는 것이 표준.

Cilium의 L7 정책

표준 NetworkPolicy는 L3/L4까지입니다. Cilium은 CRD(CiliumNetworkPolicy)로 L7 HTTP 경로·메서드까지 제어 가능: 

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata: { name: web-to-api-get-only }
spec:
  endpointSelector:
    matchLabels: { app: api }
  ingress:
  - fromEndpoints:
    - matchLabels: { app: web }
    toPorts:
    - ports: [{ port: "8080", protocol: TCP }]
      rules:
        http:
        - method: GET
          path: "/api/v1/.*"

4.7LoadBalancer 구현과 externalTrafficPolicy

Service type: LoadBalancer는 클라우드에서만 "그냥 동작"합니다. 온프레미스에서는 MetalLB가 표준 솔루션입니다.

클라우드 컨트롤러의 일

AWS의 경우 LoadBalancer Service가 생기면:

  1. Cloud Controller Manager 또는 AWS Load Balancer Controller(권장)가 감지
  2. NLB를 VPC에 생성 (또는 클래식 ELB, ALB)
  3. Target Group을 만들고 각 노드의 NodePort를 대상으로 등록
  4. 헬스체크가 통과하면 트래픽 수신 시작
  5. Service status의 loadBalancer.ingress.hostname에 DNS 이름 기입

externalTrafficPolicy: Cluster vs Local

이 필드는 "LB에서 노드로 들어온 트래픽을 어떻게 처리할지"를 정합니다.

Cluster (기본)
  • 어떤 노드든 LB가 고른 노드로 트래픽 도착
  • 그 노드가 kube-proxy로 임의의 Pod(다른 노드 포함)로 재분배
  • 장점: 균등 분산
  • 단점: 추가 홉, 소스 IP가 노드의 IP로 SNAT됨
Local
  • LB가 고른 노드에 Pod가 없으면 패킷 드롭
  • Pod가 있으면 그 노드의 Pod로만 전달
  • 장점: 소스 IP 보존, 한 홉
  • 단점: 노드별 Pod 수가 불균등하면 트래픽 불균등

실무 권고: 원본 IP가 필요한 웹 서비스(로깅·보안)는 Local, 내부 서비스는 Cluster로 충분. Local은 노드별 헬스체크를 반드시 LB에 연결해야 합니다.

MetalLB — 온프레미스의 LoadBalancer

MetalLB는 두 모드로 동작합니다:

Layer 2 모드
ARP로 "이 IP는 나야"를 선언. 한 노드가 모든 트래픽을 받아 kube-proxy로 분산. 단순하지만 그 노드가 병목.
BGP 모드
네트워크 라우터와 BGP 피어링. 같은 IP를 여러 노드에서 광고해 ECMP로 분산. 라우터 설정 필요.

Q1. 10.96.0.5(ClusterIP)에 ping이 안 되는 이유는?

  2. NetworkPolicy로 기본 차단돼 있다

  4. 장점: 인증 통합 / 단점: TLS 미지원
Local은 SNAT을 피해 원본 IP를 보존하는 대신, 노드별 Pod 분포에 분산이 종속됩니다.

5.1스토리지 기초 — 블록·파일·오브젝트

현대의 스토리지는 세 가지 주요 추상으로 구분됩니다. Kubernetes 볼륨도 이 구분을 따라갑니다.

K8s 볼륨으로 오브젝트 스토리지를 "파일처럼 마운트"하는 CSI 드라이버(s3fs, mountpoint-s3)도 있지만, 성능·일관성 제약이 있어 주 용도로는 권장되지 않습니다.

5.2CSI 아키텍처 — 왜 이렇게 복잡한가

초기 K8s는 볼륨 드라이버를 "in-tree"로 코어 안에 품었습니다. 새 스토리지 지원을 추가하려면 K8s 릴리스 주기를 기다려야 했고, 벤더들이 주도권을 갖기 어려웠습니다. CSI(Container Storage Interface)는 이 문제를 풉니다 — 벤더가 자기 드라이버를 컨테이너로 패키징해 배포하면 끝.

CSI 드라이버의 3 구성요소

Identity Plugin
"너 어느 CSI 드라이버야?" — 이름·버전·기능을 응답. StatefulSet/Deployment 하나면 충분.
Controller Plugin
볼륨 생명주기(Create/Delete/Attach/Detach/Expand)를 책임. 보통 Deployment로 1개.
Node Plugin
각 노드에 DaemonSet으로 뜸. 볼륨을 해당 노드에 stage하고 Pod의 경로에 publish(마운트)함.

sidecar 패턴

벤더는 자기 플러그인만 쓰고, K8s와의 접점(PVC watch, 이벤트 전달)은 표준 사이드카가 담당합니다.

  • external-provisioner — PVC를 보고 CreateVolume 호출
  • external-attacher — VolumeAttachment 객체를 보고 ControllerPublishVolume 호출
  • external-resizer — PVC 크기 변경 감지 → ExpandVolume
  • external-snapshotter — VolumeSnapshot → CreateSnapshot
  • node-driver-registrar — node plugin을 kubelet에 등록

5.3StatefulSet 실전 · 순서와 정체성

StatefulSet의 Pod는 <name>-0, <name>-1, ... 순서로 올라오고, 각 인덱스가 자기 PVC를 갖습니다. 업데이트는 기본 OrderedReady로 가장 높은 인덱스부터 역순으로, 동시 1개만. 이 엄격함이 복제된 DB의 리더 교체 같은 시나리오에서 데이터 손실을 막습니다.

Headless Service와 DNS 정체성

spec.serviceName을 가리키는 Service는 clusterIP: None(headless)이어야 합니다. 그러면 각 Pod에 대해 DNS 레코드가 생깁니다: 

postgres-0.postgres-headless.default.svc.cluster.local → Pod A의 IP
postgres-1.postgres-headless.default.svc.cluster.local → Pod B의 IP
postgres-2.postgres-headless.default.svc.cluster.local → Pod C의 IP

Primary가 postgres-0로 고정되면 애플리케이션이 이 DNS 이름으로 접속하면 됩니다. Pod가 재생성돼도 IP는 바뀌지만 이름은 그대로.

volumeClaimRetentionPolicy (1.27+)

전통적으로 StatefulSet을 삭제해도 PVC는 남았습니다(데이터 보호 목적). 1.27부터 정책을 선택 가능: 

spec:
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain   # StatefulSet 삭제 시 PVC 유지 (기본)
    whenScaled: Delete    # scale-down 시 여분 PVC 삭제

5.4데이터베이스를 K8s에 올릴 때의 함정

"Cattle, not pets"라는 K8s 철학과 DB는 태생부터 충돌합니다. 그래도 실무에서는 자주 올리게 되고, 그 함정을 알아야 합니다.

① 디스크 I/O와 cgroup

PostgreSQL·MySQL은 fsync와 버퍼 캐시 관리에 민감합니다. cgroup의 blkio 제한은 쓰지 말 것(커널이 fsync latency를 악화시킴). 대신 전용 노드에 StatefulSet을 taint/toleration으로 고정하는 편이 안전합니다.

② 백업과 스냅샷

VolumeSnapshot CRD로 EBS·RBD 스냅샷을 찍을 수 있지만, DB는 애플리케이션 레벨 일관성을 보장하지 않습니다. pg_dump 또는 pgBackRest 같은 DB 네이티브 툴을 CronJob으로 주기 실행하는 것이 안전.

③ 업그레이드

StatefulSet의 podManagementPolicy를 Parallel로 하면 모든 Pod가 동시에 내려갑니다 — 대개 사고. OrderedReady를 유지하고, 업그레이드 순서는 "follower 먼저 → leader 마지막" 이 되도록 애플리케이션 쪽에서 leadership 관리.

④ Operator 사용

실제 프로덕션에서는 Operator가 표준 선택입니다. PostgreSQL은 zalando/postgres-operator 또는 CloudNativePG, Kafka는 Strimzi, Redis는 OT-Container-Kit/redis-operator, MySQL은 Percona Operator. Operator가 StatefulSet·백업·failover·업그레이드를 대신 처리해 줍니다. Part 9에서 Operator 패턴의 본질을 다룹니다.

⑤ Kafka의 특수성 — 대용량 로그와 rebalance

Kafka 브로커는 수 TB의 디스크를 먹습니다. Pod 재스케줄 시 다른 노드로 이동하면 파티션 replica 재구축이 몇 시간 걸릴 수 있습니다. nodeAffinity로 Pod를 특정 노드에 고정하고, PV도 해당 노드의 로컬 SSD(local-path-provisioner나 CSI의 토폴로지)를 사용하는 것이 일반적.

6.1관측성 3축 — Metrics·Logs·Traces

분산 시스템을 운영하려면 "지금 시스템 안에서 무슨 일이 벌어지고 있는가"를 외부에서 관측해야 합니다. 세 축이 관례입니다.

Metrics (수치)
시간에 따른 숫자 시계열. CPU 사용률, 요청 수, 레이턴시 분포. 저장·집계가 쉽고 경보에 적합.
Logs (이벤트)
비정형 또는 구조화된 이벤트. "왜 그 요청이 실패했는가"의 상세가 담김.
Traces (스팬 그래프)
한 요청이 여러 서비스를 타면서 만든 스팬의 트리. 분산 추적.

사고 조사는 대개 Metrics로 "언제·어디"를 좁히고 → Logs로 "무엇"을 확인 → Traces로 "왜"를 분해하는 순서로 진행됩니다.

6.2Prometheus · Grafana · PromQL 기초

Prometheus는 pull 방식 메트릭 수집기입니다. 각 타겟(Pod/서비스)이 /metrics 엔드포인트에 텍스트 포맷으로 노출하면 Prometheus가 주기적으로 스크레이프합니다.

주요 exporter

  • node-exporter — 노드 OS 메트릭(CPU, 메모리, 디스크, 네트워크)
  • cAdvisor — 컨테이너 단위 리소스 (kubelet에 내장)
  • kube-state-metrics — K8s 오브젝트 상태(Deployment replica, Pod phase 등)
  • 애플리케이션 exporter — redis_exporter, postgres_exporter, blackbox_exporter 등

PromQL 기초

# Pod별 CPU 사용률 (초당 CPU 초)
rate(container_cpu_usage_seconds_total{namespace="prod"}[5m])

# 네임스페이스별 현재 Pod 수
count by (namespace) (kube_pod_info)

# 99퍼센타일 요청 레이턴시 (5분 윈도우)
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# Deployment 가용성 — 준비 replica / 원하는 replica
sum by (deployment) (kube_deployment_status_replicas_available)
  / sum by (deployment) (kube_deployment_spec_replicas)

# 최근 1시간 내 CrashLoopBackOff 들어간 Pod
kube_pod_container_status_waiting_reason{reason="CrashLoopBackOff"} == 1

Prometheus Operator

직접 Prometheus를 운영하기보단 Prometheus Operator(=kube-prometheus-stack)를 쓰는 것이 표준입니다. ServiceMonitor와 PodMonitor CRD로 "이 라벨의 서비스를 스크레이프"를 선언하고, PrometheusRule로 경보 규칙을 선언합니다. 

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata: { name: api-metrics, namespace: prod }
spec:
  selector:
    matchLabels: { app: api }
  endpoints:
  - port: metrics
    interval: 30s
    path: /metrics
---
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata: { name: api-alerts }
spec:
  groups:
  - name: api
    rules:
    - alert: HighErrorRate
      expr: |
        sum(rate(http_requests_total{app="api",status=~"5.."}[5m]))
          / sum(rate(http_requests_total{app="api"}[5m])) > 0.05
      for: 5m
      labels: { severity: critical }
      annotations:
        summary: "API 5xx rate is above 5%"

로그 — Loki와 Fluent Bit

ELK(Elasticsearch)는 여전히 널리 쓰이지만, 비용 대비 K8s 로그량이 커서 Grafana Loki가 점점 표준이 됩니다. Loki는 로그 본문을 인덱싱하지 않고 메타(라벨)만 인덱싱해 비용이 매우 낮습니다. 노드 DaemonSet으로 Fluent Bit 또는 Vector가 각 컨테이너의 stdout을 수집해 Loki로 보냅니다.

트레이스 — OpenTelemetry

OTel(OpenTelemetry)이 사실상 표준입니다. 앱은 OTel SDK로 계측해 OTLP 프로토콜로 보내고, OTel Collector가 수집해 Jaeger/Tempo/Datadog/Honeycomb 중 하나로 전송합니다.

6.3오토스케일링 — HPA·VPA·CA·Karpenter

HPA (Horizontal Pod Autoscaler)

메트릭(기본 CPU·Mem)에 따라 Pod 수를 늘리고 줄입니다. 1.23부터 v2 API가 GA되어 커스텀 메트릭과 외부 메트릭을 지원합니다. 

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 50
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 60 }
  - type: Pods
    pods:
      metric: { name: http_requests_per_second }
      target: { type: AverageValue, averageValue: 100 }
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 급격한 축소 방지
      policies:
      - { type: Percent, value: 10, periodSeconds: 60 }

VPA (Vertical Pod Autoscaler)

Pod의 requests/limits 자체를 자동 조정. Pod를 재생성해야 적용되므로 Deployment와 궁합이 있고, HPA와 같은 메트릭(CPU/Mem)에는 동시에 쓰면 충돌합니다. "Recommend only" 모드로 권고만 보는 편이 실무에서 많이 쓰입니다.

Cluster Autoscaler (CA)

노드를 늘리고 줄입니다. Pending Pod가 있으면 노드 그룹(AWS ASG, GCP MIG)에 "하나 더 띄워달라" 요청. 유휴 노드는 10분 지나면 축소. 단점: 사전 정의된 노드 그룹 안에서만 동작하고, 인스턴스 타입 조합이 복잡해지면 선택 로직이 비효율적.

Karpenter (AWS 발, OSS)

CA의 한계를 극복한 차세대 노드 오토스케일러. Pending Pod의 리소스 요구에 맞는 최적의 인스턴스 타입을 실시간으로 선택하고 EC2 API로 직접 띄웁니다. Spot/온디맨드 섞기, AZ 분산, 노드 통합(bin-packing) 모두 자동. EKS에서 사실상 표준. 

apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: default }
spec:
  template:
    spec:
      requirements:
      - key: kubernetes.io/arch
        operator: In
        values: [amd64, arm64]
      - key: karpenter.sh/capacity-type
        operator: In
        values: [spot, on-demand]
      - key: node.kubernetes.io/instance-type
        operator: In
        values: [m6i.large, m6i.xlarge, m6i.2xlarge, c6i.large, c6i.xlarge]
  limits:
    cpu: 1000
  disruption:
    consolidationPolicy: WhenUnderutilized
    expireAfter: 720h

6.4Pod Security Standards

1.25에서 PodSecurityPolicy(PSP)가 제거되고 그 자리를 Pod Security Standards(PSS)가 차지했습니다. 세 레벨 정의:

레벨허용용도
Privileged거의 모든 것시스템·특권 워크로드(CNI, CSI, 모니터링 에이전트)
Baseline알려진 권한 상승 차단 · privileged, hostPath 일부, hostNetwork 금지일반 애플리케이션 (최소 권장)
Restricted모범 사례 전부 · runAsNonRoot 필수, allowPrivilegeEscalation 금지, Capabilities drop ALL 등보안 민감 워크로드 (권장)

네임스페이스 레이블로 적용합니다. warn, audit, enforce 세 모드 중 선택. 단계적 도입 시 audit부터: 

kubectl label namespace prod \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.30

securityContext 체크리스트

spec:
  securityContext:           # Pod 수준
    runAsNonRoot: true
    runAsUser: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
  - name: app
    securityContext:         # 컨테이너 수준 — Pod 것 덮어씀
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true

        drop: ["ALL"]

    - { name: tmp, mountPath: /tmp }   # RO 루트일 때 쓰기 필요 영역 마운트
  volumes:
  - { name: tmp, emptyDir: {} }

PART 7 · EKS

EKS 실전

AWS 관리형 Kubernetes에서만 보이는 고유한 함정 — VPC CNI의 IP 고갈, IRSA OIDC 흐름, AWS LB Controller, 그리고 Karpenter까지.

7.1관리형 컨트롤 플레인의 진짜 의미

EKS에서 "컨트롤 플레인 관리형"이란 구체적으로 AWS가 다음을 대신 운영해 준다는 뜻입니다.

  • kube-apiserver 다수(최소 2 AZ)에 걸쳐 HA 구성, 자동 패치 (단, K8s 마이너 버전 업그레이드는 사용자 트리거)
  • etcd 3노드 이상, 자동 백업, eks KMS 키로 암호화
  • kube-scheduler, kube-controller-manager, cloud-controller-manager
  • 컨트롤 플레인 수평 확장(요청량이 늘면 자동으로 스케일)

반대로 사용자가 여전히 책임지는 것은:

  • 워커 노드 — EC2 인스턴스, AMI 패치, kubelet 버전 업그레이드
  • 네트워크 CNI — 보통 AWS VPC CNI(기본 설치), 또는 Calico/Cilium 교체
  • CoreDNS, kube-proxy — EKS add-on으로 관리 편의 제공
  • Ingress 컨트롤러, CSI 드라이버, 모니터링, 로깅

API 엔드포인트

EKS 클러스터의 apiserver는 퍼블릭·프라이빗 엔드포인트 두 종류가 있습니다.

  • Public + Private — 기본. 인터넷에서도 접근 가능, 워커는 VPC 내부로 통신.
  • Private only — 인터넷에서 차단. bastion·VPN·Direct Connect 필요. 보안·규제 준수 요구 환경.

7.2AWS VPC CNI와 IP 고갈 이슈

EKS의 기본 CNI는 AWS VPC CNI입니다. 이 CNI는 각 Pod에 VPC IP를 그대로 부여합니다. 장점은 Pod가 VPC의 1등 시민이 된다는 것 — 보안 그룹, VPC 플로우 로그, Transit Gateway가 Pod를 직접 본다는 것.

ENI와 secondary IP의 흐름

EC2 인스턴스 하나는 ENI(Elastic Network Interface)를 여러 개 붙일 수 있고, 각 ENI는 여러 secondary IP를 가질 수 있습니다. 인스턴스 타입에 따라 "최대 ENI 수"와 "ENI당 IP 수"가 정해집니다.

인스턴스 타입최대 ENIENI당 IP최대 Pod(기본)
t3.small3411
m5.large31029
m5.xlarge41558
m5.4xlarge830234

"최대 Pod = ENI수 × (ENI당 IP수 - 1) + 2" 공식. 공식의 -1은 ENI의 primary IP를 노드 자체가 쓰기 때문.

Prefix Delegation

ENI당 IP 수가 너무 적어서 작은 인스턴스에서 Pod 밀도가 낮다는 문제를 해결하는 기능. ENI에 개별 IP 대신 /28 prefix(16개 IP)를 할당받게 설정: 

kubectl set env daemonset/aws-node -n kube-system \
  ENABLE_PREFIX_DELEGATION=true

이걸 켜면 m5.large도 110개 Pod까지 갈 수 있습니다. 단 VPC에 /28 조각이 연속으로 할당 가능해야 합니다.

VPC CNI 튜닝 변수

WARM_IP_TARGET
항상 여분으로 잡아둘 IP 수. 기본 안 설정. 높게 잡으면 파드 기동이 빠름, 낮게 잡으면 VPC IP 절약.
WARM_ENI_TARGET
여분 ENI 수. 기본 1.
MINIMUM_IP_TARGET
최소 확보 IP. 초기 스파이크 대비.
ENABLE_POD_ENI
개별 Pod가 자기 ENI를 가지게 함(Security Group for Pods). SG를 Pod 단위로 적용.
EKS 사례 대규모 트래픽 스파이크 시 "Pod Pending"의 원인이 VPC CNI의 IP 배분 지연인 경우가 많습니다. MINIMUM_IP_TARGET과 WARM_IP_TARGET을 높여 두면 완화됩니다. 또는 Prefix Delegation으로 대량 확보.

7.3IRSA와 EKS Pod Identity

IRSA (IAM Roles for Service Accounts)

Pod가 AWS API(S3, DynamoDB, SQS 등)를 호출할 때, IAM 권한을 어떻게 부여할까요? 예전에는 노드의 EC2 인스턴스 프로파일에 권한을 쌓았습니다. 문제: 같은 노드의 모든 Pod가 같은 권한을 공유. 최소 권한 원칙 위배. IRSA가 이를 해결합니다.

IRSA의 동작 원리:

  1. EKS 클러스터가 OIDC 프로바이더를 발급 (IAM에 등록)
  2. ServiceAccount에 IAM 역할 ARN을 annotation으로 연결
  3. Pod 시작 시 kubelet이 해당 SA의 projected JWT 토큰을 /var/run/secrets/.../token에 마운트
  4. AWS SDK가 자동으로 이 토큰과 함께 STS AssumeRoleWithWebIdentity 호출
  5. 임시 자격 증명을 받아 API 호출
# ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: s3-reader
  namespace: prod
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::111122223333:role/s3-reader-role
---
# 그 SA를 쓰는 Pod
apiVersion: v1
kind: Pod
metadata: { name: app }
spec:
  serviceAccountName: s3-reader
  containers:
  - name: app
    image: myapp:v1
    # 환경 변수는 mutating webhook이 자동 주입
    # AWS_ROLE_ARN=arn:aws:iam::.../s3-reader-role
    # AWS_WEB_IDENTITY_TOKEN_FILE=/var/run/secrets/.../token

IAM 역할의 Trust Policy에는 "이 SA만 AssumeRole 가능" 조건을 넣습니다: 

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/oidc.eks.ap-northeast-2.amazonaws.com/id/AABBCC..." },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "oidc.eks.ap-northeast-2.amazonaws.com/id/AABBCC...:sub": "system:serviceaccount:prod:s3-reader",
        "oidc.eks.ap-northeast-2.amazonaws.com/id/AABBCC...:aud": "sts.amazonaws.com"
      }
    }
  }]
}

EKS Pod Identity (2023 발표, 2024 GA)

IRSA는 강력하지만 클러스터마다 OIDC 프로바이더 등록, 신뢰 정책의 클러스터 ID 하드코딩 등 운영 부담이 있습니다. Pod Identity는 이를 단순화: EKS add-on eks-pod-identity-agent를 설치하고, "이 클러스터의 이 네임스페이스의 이 SA → 이 IAM 역할" 매핑을 AWS 콘솔/API로 등록하면 끝. OIDC 없이 동작하며 역할 재사용이 쉽습니다.

7.4노드 옵션 3종 — MNG vs Fargate vs Karpenter

Managed Node Groups (MNG)

AWS가 Auto Scaling Group을 관리해 주는 방식. AMI 업그레이드, 드레인, 롤링 대체를 AWS API로 트리거 가능. Spot·온디맨드 섞기 지원. 크기 계획은 여전히 사용자 몫.

Fargate

노드 없는 Pod 실행. Fargate 프로파일이 매칭되는 Pod는 독립된 micro-VM에서 실행. 장점: 노드 관리 0. 단점: Pod당 요금이 EC2 대비 높고, DaemonSet 불가(시스템 DaemonSet 자체가 없음), 일부 볼륨 타입 미지원(EBS는 안 됨, EFS는 됨), 시작 시간이 길다(40~90초). 배치 잡이나 가끔 쓰는 컨트롤러에 적합.

Karpenter

앞에서 설명한 오픈소스 노드 오토스케일러. EKS에서 사실상 표준. NodePool과 EC2NodeClass로 원하는 인스턴스 범위·AMI·서브넷을 지정.

실무 조합

한 클러스터 안에서 셋을 섞어 쓰는 것이 현실적입니다: 핵심 시스템(CoreDNS, Ingress) → MNG · 애플리케이션 → Karpenter · 배치/이벤트 → Fargate.

7.5AWS Load Balancer Controller

EKS에서 Ingress·Service LB를 실제로 ALB/NLB로 프로비저닝해 주는 컨트롤러입니다. kube-system에 Deployment로 배치합니다.

ALB Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip   # Pod IP 직접 (IP 타겟)
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80},{"HTTPS":443}]'
    alb.ingress.kubernetes.io/ssl-redirect: '443'
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-northeast-2:111:certificate/xxx
    alb.ingress.kubernetes.io/group.name: shared
spec:
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend: { service: { name: web, port: { number: 80 } } }

target-type: ip를 쓰면 ALB가 Pod IP를 직접 대상으로 삼습니다 — NodePort 홉이 사라지고 SNAT 문제도 해소. group.name이 같은 Ingress끼리는 하나의 ALB를 공유 → ALB 개수를 줄여 비용 절약.

NLB (Service type LoadBalancer)

apiVersion: v1
kind: Service
metadata:
  name: gateway
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: external
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
    service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing
spec:
  type: LoadBalancer
  ports:
  - { port: 443, targetPort: 8443, protocol: TCP }
  selector: { app: gateway }

7.6EBS·EFS CSI 드라이버

EBS CSI

기본 블록 스토리지. 1.23부터 in-tree provisioner가 제거돼 CSI 드라이버를 add-on으로 설치해야 합니다. gp3 권장(gp2 대비 성능·비용 유리). StorageClass: 

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: gp3 }
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
  kmsKeyId: arn:aws:kms:ap-northeast-2:...
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Delete

WaitForFirstConsumer가 중요합니다. 볼륨 생성 시점을 Pod 스케줄링 결정 후로 미뤄서 볼륨이 잘못된 AZ에 만들어지는 문제를 방지.

EFS CSI

여러 Pod가 동시에 읽고 쓸 수 있는(RWX) 파일 스토리지. 과금은 용량+I/O 기반이라 소규모엔 비쌈. 레이턴시가 EBS보다 높으므로 DB에는 비추. 공유 캐시·WordPress 업로드 같은 경우 적합.

gp3 튜닝

  • IOPS와 처리량(throughput)을 용량과 독립적으로 지정 가능 — gp2의 한계 해소
  • 기본 3000 IOPS / 125 MB/s. 필요 시 16000 IOPS / 1000 MB/s까지
  • 비용은 같은 크기에서 gp2보다 20% 낮음

7.7EKS 업그레이드 전략

K8s는 한 번에 한 마이너 버전씩만 올릴 수 있습니다. 1.28 → 1.29 → 1.30 순서로. 점프는 불가.

단계별 체크리스트

  1. 호환성 확인: kubectl convert로 deprecated API 검색. pluto/kubent 툴로 전체 매니페스트 스캔.
  2. 컨트롤 플레인 업그레이드: AWS 콘솔/CLI로 1단계 상승. apiserver가 순차 교체되며 약 10분 소요.
  3. kube-proxy / CoreDNS / VPC CNI add-on 업그레이드: 새 K8s 버전과 호환되는 버전으로.
  4. 워커 노드 업그레이드: MNG는 AWS가 rolling update로 교체. Karpenter는 disruption 정책으로 자동.
  5. 사용자 워크로드 검증: 통합 테스트 환경에서 먼저, 그 다음 프로덕션.
버전 지원 EKS는 각 마이너 버전을 약 14개월 지원합니다. 그 후에는 "extended support"(추가 비용)이거나 자동 업그레이드 대상. 운영 클러스터는 최소 분기 1회 업그레이드를 계획하는 것이 표준.

Blue-Green 업그레이드

노드 in-place 교체가 불안하면 새 노드 그룹을 만들어 Pod를 이관하는 방법도 있습니다. 구 NG에 taint를 걸어 새 Pod가 안 오게 하고, kubectl drain으로 기존 Pod를 신 NG로 옮긴 뒤 구 NG 삭제. PDB(PodDisruptionBudget)를 지켜 가용성을 보장할 것.

8.1Pod 상태 이상 (7건)

CASE 01Pod이 Pending 상태에서 움직이지 않는다
새 Deployment를 올렸는데 Pod가 몇 분째 Pending. kubectl get events에 FailedScheduling이 뜬다.
가장 먼저 의심해야 할 원인은?
정답은 ②. Pending은 스케줄링 단계에서 막힌 것이고, 이미지 풀은 스케줄 후 노드에서 발생합니다. etcd 장애면 Pending조차 못 찍힙니다.
로그/이벤트 
kubectl describe pod api-57b4-x8g9 -n prod | tail -20
# Events:
#   Warning  FailedScheduling  30s  default-scheduler
#     0/8 nodes are available: 3 node(s) had taint {dedicated: batch},
#     5 Insufficient memory.
원인 구조

스케줄러 필터가 모든 노드를 걸러냈습니다. 가능성:

  • requests에 맞는 CPU/Mem 여유가 있는 노드가 없음
  • taint가 있는 노드에 toleration이 없음
  • nodeSelector / affinity가 너무 엄격
  • TopologySpreadConstraints 위반
  • PVC의 VolumeBinding이 특정 AZ를 요구하는데 그 AZ에 노드가 없음
진단 
# 1. describe pod로 이유 직접 확인
kubectl describe pod <name>

# 2. 노드 리소스 여유
kubectl describe node | grep -A5 "Allocated resources"

# 3. 노드 taint
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints

# 4. Pod의 nodeSelector/affinity
kubectl get pod <name> -o yaml | yq '.spec | {nodeSelector, affinity, tolerations}'
해결
  • 리소스 부족이면 → 클러스터 확장(CA/Karpenter) 또는 requests 축소
  • taint 불일치면 → Pod에 toleration 추가 또는 taint 제거
  • affinity 엄격함이면 → preferredDuringSchedulingIgnoredDuringExecution로 완화
재발 방지

ResourceQuota와 LimitRange로 requests 누락을 막고, Karpenter의 consolidation으로 여유 버퍼 확보.

CASE 02ImagePullBackOff — 이미지를 가져오지 못한다
Pod가 ImagePullBackOff 또는 ErrImagePull 상태에 머문다.
원인 후보로 적절하지 않은 것은?
정답은 ③. 이미지 풀은 컨테이너 시작 이전이고, readinessProbe는 실행 이후의 관문.
로그/이벤트 
kubectl describe pod web-xxx | grep -A2 Warning
# Warning  Failed  Error: ImagePullBackOff
# Warning  Failed  Error: failed to pull and unpack image "myorg/api:v1.2":
#                 failed to resolve reference: pull access denied
진단 & 해결 
# 1. 이미지 이름/태그가 정확한지
kubectl get pod web-xxx -o jsonpath='{.spec.containers[*].image}'

# 2. Private 레지스트리라면 imagePullSecret
kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=$U --docker-password=$P
# Pod 또는 SA에 연결
kubectl patch sa default -p '{"imagePullSecrets":[{"name":"regcred"}]}'

# 3. Docker Hub 레이트 리밋이면 → 익명 pull을 피하고 Hub 계정 토큰 사용

# 4. 노드에서 직접 시도
crictl pull registry.example.com/myorg/api:v1.2
# 실패 로그가 kubelet 로그보다 더 명확
재발 방지
  • CI에서 태그가 존재하는지 push 직후 검증
  • Private 레지스트리 사용 시 ServiceAccount에 imagePullSecret을 기본 연결
  • 미러 레지스트리(ECR pull-through) 도입으로 외부 의존 줄이기
CASE 03CrashLoopBackOff — 컨테이너가 반복 재시작
Pod가 CrashLoopBackOff로 점점 긴 대기 시간(10s → 20s → 40s … 최대 5분)으로 재시작한다.
먼저 봐야 할 것은?
정답은 ②. CrashLoop은 컨테이너가 종료코드 0이 아닌 상태로 끝나고 다시 뜨는 것이므로, 죽기 직전 로그가 핵심 단서.
진단 
kubectl logs <pod> --previous
# 직전 컨테이너의 stdout/stderr. 애플리케이션 스택트레이스 여기

kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[*].lastState.terminated}'
# { "exitCode": 137, "reason": "OOMKilled", ... } 같은 힌트
#   137 = 128 + 9(SIGKILL) → OOMKill
#   143 = 128 + 15(SIGTERM) → graceful
#   1   → app 자체 에러
#   0   → 정상 종료인데 재시작? restartPolicy 문제
가장 흔한 원인들
  • OOMKill (137) → limits.memory 증가
  • livenessProbe 공격적 → 프로브 completed 인정 시간이 짧아 무한 재시작
  • 앱 설정 누락 → 필수 env/ConfigMap 미주입. kubectl logs --previous에서 "config not found" 등
  • init 컨테이너 실패 → 초기화 스크립트가 nil 반환
CASE 04OOMKilled — 메모리 초과로 강제 종료
Pod가 Status: Failed, Reason: OOMKilled로 종료. 재시작 후 같은 증상 반복.
OOMKill이 발생한 주체는?
정답은 ①. cgroup의 memory.max를 넘는 순간 커널이 SIGKILL. kubelet은 이 이벤트를 관찰해 OOMKilled로 기록만 합니다. ②의 "노드 전체 메모리 압박"이면 다른 이야기(eviction).
진단 방법 
# 1. 실제 사용 피크

# 또는 Prometheus에서
# container_memory_working_set_bytes{pod="..."}

# 2. cgroup의 한계 값
kubectl get pod <pod> -o jsonpath='{.spec.containers[*].resources.limits.memory}'

# 3. OOM 발생 시점 커널 로그 (노드 SSH 필요)
dmesg -T | grep -i oom
# [Fri Apr 12 14:22:31 2026] Memory cgroup out of memory: Killed process 12345 (java)
#   total-vm:2097152kB, anon-rss:999123kB, file-rss:0kB
해결·조치
  • limits.memory를 실제 피크의 1.3~1.5배로 상향
  • JVM 등은 -XX:MaxRAMPercentage=75.0로 cgroup을 인식하게
  • 메모리 누수라면 힙 덤프 수집 후 앱 수정
  • requests.memory = limits.memory (Guaranteed QoS)로 설정해 다른 Pod와 경합 최소화
CASE 05Pod Evicted — 노드 리소스 압박으로 추방
kubectl get pods에 Status: Evicted Pod가 계속 쌓임. 노드는 Ready 상태.
Evicted는 무엇을 의미하는가?
정답은 ②. kubelet의 "node-pressure eviction" 메커니즘. 기본 임계값: memory.available<100Mi, nodefs.available<10%, imagefs.available<15%.
원인 구조

kubelet은 10초마다 노드 상태를 점검. 임계값 초과 시 먼저 BestEffort Pod, 그 다음 Burstable 중 사용량이 requests를 크게 넘는 것, 마지막 Guaranteed 순서로 evict. 그 과정에서 Pod에 "Evicted" 라벨이 붙음.

해결 
# 쌓인 Evicted Pod 청소
kubectl get pods -A --field-selector=status.phase=Failed \
  -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,REASON:.status.reason \
  | grep Evicted
kubectl delete pods -A --field-selector=status.phase=Failed

# 원인 해결: 노드에 디스크 여유 확보
# - emptyDir가 큰 Pod 식별
# - imagefs.available 낮으면 오래된 이미지 GC:
kubectl get events | grep -i eviction
# 임계값 조정이 필요하면 kubelet 플래그 --eviction-hard 수정
CASE 06Terminating stuck — Pod 삭제가 끝나지 않는다
kubectl delete pod 후 Terminating 상태가 30분 이상 지속.
가장 흔한 원인은?
정답은 ③. Pod에 finalizer가 붙어 있으면 GC가 대기. 또는 노드가 NotReady이면 kubelet이 삭제 처리를 할 수 없음.

# VolumeAttachment 잔존 확인

해결 
# 1. 원인 제거가 원칙(노드 복구, 볼륨 detach 재시도, finalizer를 건 컨트롤러 수정)

#                      upstream: "http://10.244.1.5:8080/api"

# 흔한 원인

9.3Operator 패턴 · 쿠버네티스를 확장하는 방법

Kubernetes의 진짜 힘은 "리소스를 직접 정의할 수 있다"는 점입니다. 사용자가 CRD(CustomResourceDefinition)를 등록하면 apiserver가 그 리소스를 네이티브처럼 저장·Watch·Admission 대상으로 삼습니다. 그 리소스를 감시하며 실제 세상을 재조정하는 프로그램이 Operator입니다.

Reconcile 루프

func (r *MyAppReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var app myappv1.MyApp
    if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    // 1. 원하는 상태 계산
    desired := buildDeployment(&app)

    // 2. 현재 상태 조회
    var current appsv1.Deployment
    err := r.Get(ctx, types.NamespacedName{Name: desired.Name, Namespace: desired.Namespace}, &current)

    // 3. 차이 있으면 Patch/Create
    if errors.IsNotFound(err) {
        ctrl.SetControllerReference(&app, desired, r.Scheme)
        return ctrl.Result{}, r.Create(ctx, desired)
    }
    if !reflect.DeepEqual(current.Spec, desired.Spec) {
        current.Spec = desired.Spec
        return ctrl.Result{}, r.Update(ctx, &current)
    }

    // 4. 상태를 CR의 .status에 기록
    app.Status.Replicas = current.Status.Replicas
    return ctrl.Result{RequeueAfter: time.Minute}, r.Status().Update(ctx, &app)
}

이 동일한 패턴이 K8s 내부의 모든 컨트롤러에도 적용됩니다 — Deployment 컨트롤러, ReplicaSet 컨트롤러, JobController… Kubernetes는 사실 "거대한 Reconcile 루프의 모음"입니다.

Finalizer

CR을 삭제할 때 특정 정리 작업이 끝날 때까지 delete를 막고 싶을 때 사용. metadata.finalizers 리스트에 식별자를 추가하면 K8s는 deletionTimestamp만 설정하고 객체를 남겨 둠. Operator가 정리 완료 후 finalizer를 지우면 실제 삭제 진행.

실제 Operator 예시

  • cert-manager — Certificate CR 만들면 Let's Encrypt에서 인증서 발급, Secret으로 저장.
  • Strimzi Kafka Operator — Kafka CR 만들면 ZooKeeper, Brokers StatefulSet, 토픽까지 구축.
  • ArgoCD — Application CR로 Git 레포의 manifest를 클러스터와 동기화.
  • External Secrets Operator — ExternalSecret CR로 AWS Secrets Manager 값을 Secret으로 동기.

9.5Borg의 유산 — 왜 K8s는 이렇게 생겼는가

Kubernetes의 많은 설계가 Google의 내부 시스템 Borg(2003~)와 그 후계인 Omega에서 왔습니다. 몇 가지 핵심 철학:

① Declarative API
"이 상태가 되면 좋겠다"만 선언하고, 시스템이 스스로 도달. 장애·실패가 국소적으로 머묾.
② Level-triggered reconciliation
"변화 이벤트를 놓치면 재앙"이 아니라 "현재 상태와 원하는 상태의 차이를 반복적으로 줄임". 이벤트 유실에 견고.
③ Loose coupling via shared state (etcd)
컴포넌트가 서로를 직접 호출하지 않음. 공통 저장소의 상태만 관찰. 각 컴포넌트를 독립적으로 업그레이드·재시작 가능.
④ Job 단위가 아닌 Pod 단위
Borg는 "Job"이 기본이었지만 K8s는 더 작은 Pod가 기본. 더 유연한 컴포지션(사이드카·init 컨테이너).
⑤ 명시적 확장 메커니즘
CRD + Admission Webhook + Custom Scheduler. 플랫폼 엔지니어가 K8s를 상위 언어처럼 다룰 수 있음.

이 철학이 일관되기에 K8s는 운영 실수·부분 장애·점진적 변경에 대해 직관에 반하지 않습니다. "왜 이렇게 복잡한가?"에 대한 답은 "단순한 주장이 모였기 때문에 전체는 복원력이 있다"는 것입니다.

  1. 이벤트의 순서를 엄격히 보장한다
  2. 현재 상태와 원하는 상태의 차이를 반복적으로 좁혀간다 — 이벤트 유실에 견고
  3. 우선순위 기반 큐잉이 기본이다
  4. 부하에 따라 Pod 수가 자동으로 변한다

10.2kubectl 치트시트

조회·디버깅

# 네임스페이스 전체 현황
kubectl get all -n prod

# Pod의 실행 명령·환경 자세히
kubectl describe pod web-abc -n prod

# 라벨로 필터
kubectl get pods -A -l app=api,env=prod

# 에러 이벤트만
kubectl get events -A --field-selector type=Warning \
  --sort-by=.lastTimestamp

# JSONPath로 원하는 필드만
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.phase}{"\n"}{end}'

# 모든 컨테이너에서 문자열 검색
for p in $(kubectl get pods -o name); do
  kubectl logs $p --all-containers 2>/dev/null | grep -l "ERROR" && echo $p
done

# Pod 내부 쉘
kubectl exec -it web-abc -- /bin/sh

# 임시 디버그 컨테이너 주입 (distroless Pod 디버깅)
kubectl debug web-abc -it --image=busybox --target=web

# 노드에 디버그 Pod 띄워 호스트 접근
kubectl debug node/ip-10-0-0-10 -it --image=ubuntu
# chroot /host

편집·적용

# 즉시 수정
kubectl edit deploy web

# 이미지만 변경
kubectl set image deploy/web web=myapp:v2

# 리소스 쿼리 수정
kubectl patch deploy web -p '{"spec":{"replicas":5}}'

# 드라이런으로 YAML 생성
kubectl create deploy web --image=nginx --dry-run=client -o yaml > web.yaml

# Server-Side Apply (권장)
kubectl apply -f web.yaml --server-side --force-conflicts

롤링·롤백

kubectl rollout status deploy/web
kubectl rollout history deploy/web
kubectl rollout undo deploy/web --to-revision=3
kubectl rollout restart deploy/web   # 이미지 그대로 재기동

포트포워딩·프록시

# 로컬 8080 → Pod 80
kubectl port-forward pod/web-abc 8080:80

# Service로
kubectl port-forward svc/api 8080:80

# 웹 UI로 apiserver 프록시
kubectl proxy --port=8001
# http://localhost:8001/api/v1/namespaces/...

노드 관리

kubectl cordon node-3                 # 새 Pod 스케줄 차단
kubectl drain node-3 --ignore-daemonsets --delete-emptydir-data
kubectl uncordon node-3               # 다시 스케줄 허용

kubectl taint node node-3 dedicated=batch:NoSchedule
kubectl label node node-3 disktype=ssd

10.3디버깅 원라이너 모음

# 네임스페이스 Pod들의 CPU·메모리 실시간

Pod · 컨테이너 필드

apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: default
  labels: { app: web, env: prod }
  annotations:
    # mutable metadata. 컨트롤러가 읽고 쓰는 자리 (서비스 메쉬 주입 표식 등)
    sidecar.istio.io/inject: "true"
  ownerReferences: []   # 상위 컨트롤러가 채움 (GC용)
spec:
  serviceAccountName: default    # 지정 안 하면 default 사용
  nodeSelector: { disktype: ssd } # 노드 라벨 매칭 (AND)
  affinity:                       # 더 풍부한 조건
    nodeAffinity: {}
    podAffinity: {}
    podAntiAffinity: {}
  tolerations:                    # taint를 용인
  - key: dedicated
    operator: Equal               # 또는 Exists
    value: gpu
    effect: NoSchedule            # NoSchedule | PreferNoSchedule | NoExecute
  priorityClassName: high         # 우선순위 (preemption)
  terminationGracePeriodSeconds: 30
  restartPolicy: Always           # Always | OnFailure | Never (Job/CronJob에서만 의미)
  dnsPolicy: ClusterFirst         # ClusterFirst | Default | None
  dnsConfig:                      # 세밀 제어 (resolv.conf 덮어쓰기)
    options:
    - { name: ndots, value: "2" }
    - { name: single-request-reopen }
  hostname: web                   # Pod의 /etc/hostname
  subdomain: web                  # headless service와 조합 시 DNS
  hostNetwork: false              # true면 Pod가 노드 IP·포트 사용
  hostPID: false                  # 노드의 PID namespace 공유
  shareProcessNamespace: false    # 같은 Pod 컨테이너끼리 PID 공유
  automountServiceAccountToken: true
  imagePullSecrets:
  - { name: regcred }
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway   # DoNotSchedule | ScheduleAnyway
    labelSelector:
      matchLabels: { app: web }
  securityContext:
    runAsUser: 10001
    runAsGroup: 10001
    runAsNonRoot: true
    fsGroup: 10001                # 볼륨의 소유 그룹을 이것으로 chown
    fsGroupChangePolicy: OnRootMismatch
    seccompProfile: { type: RuntimeDefault }
    supplementalGroups: [2000]
    sysctls:
    - { name: net.core.somaxconn, value: "1024" }
  initContainers:
  - name: migrate
    image: myapp:v1
    command: [sh, -c, "migrate up"]
  containers:
  - name: app
    image: myapp:v1
    imagePullPolicy: IfNotPresent # Always | Never | IfNotPresent
    command: ["/bin/app"]         # ENTRYPOINT 덮어쓰기
    args: ["--log=info"]          # CMD 덮어쓰기

A.2자주 보는 안티패턴 25선

  1. requests/limits 둘 다 미설정 — BestEffort QoS로 떨어져 OOM·evict 1순위.
  2. CPU limits를 requests와 동일하게 박음 — 버스트 여유가 없어 throttle로 레이턴시 튐.
  3. livenessProbe에 외부 의존성 체크 — DB 장애에 앱 재시작 폭풍.
  4. hostPath로 호스트 디렉터리 마운트 — 보안·이동성 모두 최악. CSI 혹은 emptyDir로.
  5. root(UID 0) 컨테이너 실행 — 탈취 시 호스트 침해 가능. runAsNonRoot: true.
  6. 이미지 태그 :latest — 재현성 없음. 항상 이뮤터블한 sha256 digest 또는 semver 고정.
  7. Secret을 ConfigMap에 넣기 — 평문 노출. 반드시 Secret 타입 사용 + etcd 암호화.
  8. 같은 ConfigMap/Secret을 여러 네임스페이스에서 공유 — 네임스페이스 경계 자체가 불가. Sync 도구 필요.
  9. 1 Pod 1 컨테이너 외에 "관련 없는 컨테이너 묶기" — 같이 배포·업데이트 주기 강제. 사이드카 외 공유 불가.
  10. kubectl edit로 프로덕션 수정 — GitOps 반대. 상태가 Git과 드리프트.
  11. Deployment를 수동 삭제 후 재생성으로 업데이트 — 가용성 0 구간 발생. kubectl apply 또는 rollout restart.
  12. Service targetPort에 숫자 하드코딩 — 포트 변경 시 실수 쉬움. containerPort에 name 부여하고 targetPort는 name 참조.
  13. NetworkPolicy 없이 "모두 ingress 차단" 정책만 — egress DNS 안 열면 앱이 먹통.
  14. NodePort를 프로덕션 진입점으로 — LB 아래가 아니면 수평 확장·방화벽이 엉망.
  15. StatefulSet에 podManagementPolicy: Parallel — 순서 보장 깨짐. 초기 부트스트랩이 있는 DB 반드시 OrderedReady.
  16. PVC를 Deployment에 붙이기 — replica 1 초과 시 multi-attach로 망가짐. StatefulSet이 정답.
  17. emptyDir에 대용량 쓰기 — 노드 디스크 고갈 → DiskPressure → 대량 eviction.
  18. Job의 backoffLimit 무한 또는 기본(6)으로 — 영구 실패 시 apiserver에 무한 이벤트 홍수.
  19. Webhook failurePolicy: Fail + 자기 자신을 차단하는 NetworkPolicy — 자체 마비. objectSelector·namespaceSelector로 자기 제외.
  20. 서비스 메쉬 사이드카를 가진 Pod에 readiness 미설정 — 사이드카 준비 전 트래픽 유입으로 500.
  21. Single-AZ 클러스터 — AZ 장애 시 전체 다운. 최소 3 AZ.
  22. RBAC에 * 와일드카드 남발 — 침해 시 수평 이동 쉬움. 최소 권한.
  23. HPA와 VPA를 같은 메트릭에 동시에 — 상호 간섭으로 요요. 둘 중 하나만.
  24. CoreDNS를 HPA 없이 1 replica로 — 노드 장애 시 클러스터 전체 DNS 멈춤. HPA + PDB 필수.
  25. 이미지 크기 수 GB — 풀 시간 길어 스파이크 대응 실패. distroless / multi-stage build.

A.3성능 튜닝 체크리스트

컨트롤 플레인

  • etcd 디스크는 전용 NVMe — fsync p99 < 12ms 목표
  • apiserver에 APF(FlowSchema) 구성 — 위험 클라이언트 격리
  • Watch 과다 클라이언트(리크) 감시 — apiserver_longrunning_requests
  • audit log의 샘플링 또는 PII 마스킹으로 디스크 I/O 제어
  • 컨트롤 플레인과 워커 노드를 다른 NodeGroup으로 — 네트워크 영향 격리

노드

  • kubelet의 --max-pods를 노드 크기에 맞게 설정
  • containerd snapshotter를 overlayfs로 고정 (일부 배포판 기본이 아님)
  • 노드 OS의 vm.swappiness=0, fs.file-max 상향
  • conntrack 테이블 크기 net.netfilter.nf_conntrack_max 상향
  • 이미지 GC 임계값 튜닝 — DiskPressure 예방

애플리케이션

  • JVM 앱은 -XX:+UseContainerSupport -XX:MaxRAMPercentage=75
  • Go 앱은 GOMAXPROCS를 cgroup 인식시키기 (go.uber.org/automaxprocs)
  • HTTP 클라이언트의 connection pool 크기 점검 — 기본이 너무 작거나 너무 큼
  • keep-alive timeout을 Ingress보다 길게 (502 방지)
  • preStop hook으로 sleep 10 후 graceful shutdown

네트워킹

  • NodeLocal DNSCache 배포 — DNS 5초 지연 방지
  • 수천 서비스 이상이면 IPVS 또는 Cilium eBPF
  • Service의 externalTrafficPolicy: Local 필요 시 LB 노드별 헬스체크
  • ALB target-type: ip로 NodePort 홉 제거

A.4보안 하드닝 체크리스트

  • 네임스페이스마다 PSS enforce=restricted 기본
  • 기본 ServiceAccount의 automountServiceAccountToken: false 설정
  • Secret에 etcd 암호화 (KMS)
  • 이미지 서명 (cosign) + Admission 검증 (Kyverno)
  • CIS Benchmark / kube-bench 정기 스캔
  • Falco·Tetragon으로 런타임 이상행위 감지
  • NetworkPolicy로 네임스페이스 간 기본 차단 (default-deny + 화이트리스트)
  • Service Mesh로 mTLS 강제 (내부 통신 암호화)
  • RBAC에서 * 금지 — 구체적 리소스·verb
  • 노드 SSH 금지 — kubectl debug node/로만 접근
  • 감사 로그 외부(S3/CloudWatch) 저장 + 14일 이상 보존
  • kubectl 사용자 인증은 OIDC(SSO) — 로컬 kubeconfig 파일 최소화

A.8FAQ · 면접 단골

Q. Pod와 Container의 차이를 한 문장으로?

Pod는 공동 네트워크·IPC·스토리지를 가진 하나 이상의 컨테이너 묶음 — K8s의 스케줄 단위. 컨테이너는 격리된 프로세스, Pod는 그 프로세스들의 "공동 주거지"입니다.

Q. Deployment vs StatefulSet 언제 쓰는가?

Pod가 교체 가능하면 Deployment (웹 앱, API). Pod가 고유한 정체성(이름·디스크·순서)을 가져야 하면 StatefulSet (DB, Kafka, ZooKeeper). "pets vs cattle"의 현대판.

Q. Service와 Ingress의 차이?

Service는 L4(TCP/UDP) 로드밸런싱과 클러스터 내부 DNS. Ingress는 L7(HTTP) 경로·호스트 기반 라우팅과 TLS 종결. Ingress는 내부적으로 Service를 가리키고, Service는 Pod를 가리킵니다.

Q. ConfigMap을 볼륨 마운트와 env 주입 중 어느 쪽이 좋나?

볼륨 마운트가 선호됩니다. Pod 재시작 없이 변경이 반영되고(약 1분 내 kubelet이 감지), 큰 설정 파일도 수용 가능. env는 한번 세팅되면 Pod 생명주기 끝까지 고정이라 런타임 변경 불가.

Q. etcd가 죽으면 실행 중인 Pod는 어떻게 되나?

계속 돈다. kubelet은 apiserver를 잃어도 기존 컨테이너를 감시·재시작합니다. 다만 새 Pod 생성·Service 변경·컨트롤러 작업은 모두 중단. 즉 기존 트래픽은 흐르지만 시스템은 얼어붙음.

Q. kubelet이 없이 컨테이너가 동작할 수 있나?

네. kubelet은 "관리자"에 가깝습니다. 프로세스 자체는 containerd가 실행 중이라면 살아 있습니다. kubelet이 죽으면 probe가 안 돌고 상태 보고가 안 될 뿐, 트래픽은 흐릅니다. 노드가 NotReady 판정되면 결국 Pod가 재배치됩니다.

Q. Service의 ClusterIP는 바뀔 수 있나?

불변. Service 생성 시 할당되고 삭제까지 고정. 이 덕에 클라이언트가 캐싱 가능합니다. 1.29+에서는 ipFamilyPolicy로 IPv6/듀얼 스택 지원이 있지만 주 IP는 여전히 고정.

Q. 수천 Pod의 로그를 중앙으로 모으려면?

노드 DaemonSet으로 Fluent Bit/Vector가 각 컨테이너의 /var/log/containers/*.log를 수집해 Loki·ES·CloudWatch로 전송. 앱은 stdout/stderr로만 내보내면 됩니다. 절대 파일로 쓰지 마세요 — 컨테이너 재시작 시 유실.

Q. 컨테이너의 시간대는 어디서 오나?

호스트의 /etc/localtime이 아니라 이미지 안의 tzdata + TZ 환경변수에 좌우됩니다. 대다수 distroless/Alpine은 UTC. 필요하면 Dockerfile에서 apk add tzdata 후 ENV TZ=Asia/Seoul.

Q. Headless Service는 언제 쓰나?

각 Pod의 IP를 개별적으로 참조할 때. StatefulSet이 대표적. 또는 클라이언트가 자체적으로 로드밸런싱·파티셔닝을 하는 경우(Kafka 클라이언트, gRPC native LB).

Q. Pod가 같은 노드 내부 통신 시 iptables 규칙을 타나?

ClusterIP로 접근하면 네. Pod IP로 직접이면 아니오(브리지/veth만 거침). Cilium eBPF는 이마저도 우회.

Q. Kubernetes 버전 업그레이드는 얼마나 자주 해야 하나?

업스트림은 4개월마다 마이너 릴리스. EKS는 약 14개월 지원. 따라서 최소 연 1회는 상승시키는 것이 표준입니다. 분기마다 상승이 가장 안전 — 변화 폭이 작음.

Q. 컨테이너 이미지 크기를 어떻게 줄이나?

multi-stage build: 빌드 스테이지와 런타임 스테이지를 분리, 런타임엔 바이너리만 복사. distroless: Google의 gcr.io/distroless/static은 20MB 내외. shell도 없어 보안 표면 축소. .dockerignore로 불필요 파일 제외.

Q. PV는 왜 클러스터 범위인가?

PV는 실제 물리 디스크의 레퍼런스이고, 클라우드의 디스크는 네임스페이스와 무관하게 존재하기 때문. 반면 PVC(요청)는 네임스페이스 범위여서 격리가 유지됩니다.

Q. CRD와 Aggregated API Server의 차이?

CRD는 apiserver가 자체 저장·서빙. 복잡한 비즈니스 로직이 없는 선언형 리소스에 적합. Aggregated API Server는 별도 apiserver 프로세스를 띄워 일부 경로(/apis/custom.example.com/v1)를 위임받아 처리. 복잡한 연산(집계, 실시간 조인)이 필요할 때.

Q. kubectl은 어떻게 exec/logs를 구현하나?

kubectl → apiserver → kubelet(10250) 순으로 HTTP upgrade(SPDY/WebSocket) 터널을 만듭니다. apiserver는 프록시 역할이고, 실제 bash 프로세스는 kubelet이 containerd에 요청합니다. 그래서 노드와 apiserver 사이에 10250 포트가 양방향 열려 있어야 합니다.

Q. Pod의 UID는 무엇이고 어떻게 부여되나?

metadata.uid는 apiserver가 생성 시 부여한 UUID v4. 같은 이름의 Pod라도 재생성되면 UID가 달라집니다. ownerReferences·finalizer가 이 UID로 부모-자식 관계를 유지합니다.

Q. initContainer와 sidecar의 경계는?

1.28까지 두 개념이 달랐습니다. initContainer는 순차 실행 후 종료하고 본 컨테이너가 시작. 1.29부터 sidecar container가 정식 등장 — restartPolicy: Always를 initContainer에 붙이면 병렬로 돌고 본 컨테이너 수명 내내 유지됩니다. Istio의 envoy·로그 수집기가 전형적 사이드카.

Q. 왜 Pod의 ephemeralContainers를 따로 두나?

kubectl debug는 기존 Pod에 컨테이너를 사후 주입합니다. 이 때 추가되는 컨테이너가 ephemeralContainers — probe·resources 없이 돌려면 일반 컨테이너 스펙과 구별이 필요. distroless 이미지 디버깅에 결정적.

Q. cluster-admin RoleBinding을 남용하면 왜 위험한가?

모든 네임스페이스의 모든 리소스에 대한 모든 verb가 허용됩니다. Secret 전체 읽기, 다른 네임스페이스 Pod exec으로 침투, CRD 생성으로 영구 백도어 설치까지 한 번에 가능. 최소 권한 원칙: Role 단위로 verb/리소스/네임스페이스를 좁혀야 합니다.

Q. Control plane과 워커 노드 사이에 VPN이 필요한가?

EKS의 경우 AWS가 관리하는 ENI를 사용자의 VPC에 꽂아 둡니다(eks-cluster-sg). 같은 VPC 내 통신이라 VPN이 필요 없습니다. 자체 관리 K8s에서 컨트롤 플레인이 다른 네트워크에 있다면 VPN/터널 필요.

Q. kubectl apply --server-side의 장점?

클라이언트가 merge하지 않고 apiserver가 필드 소유권을 관리. 여러 도구가 같은 리소스를 관리할 때 "누가 어떤 필드를 썼는지"가 추적돼 충돌이 명확해집니다. --force-conflicts로 강제 인수 가능. GitOps 도구에서도 기본값으로 채택 중.

Q. ResourceVersion과 UID의 차이?

UID는 객체 자체의 고유 식별자(변하지 않음). resourceVersion은 그 객체의 상태 스냅샷 번호(매 수정마다 증가). Watch는 resourceVersion으로 증분 전송, UID로는 대상 객체를 구분합니다.

Q. NodeLocal DNSCache가 해결하는 구체 문제 3가지?

  1. conntrack UDP race로 인한 5초 DNS 지연 — 로컬 캐시가 UDP→TCP로 CoreDNS에 포워드
  2. CoreDNS에 가해지는 전체 질의량의 80~90% 감소 (캐시 히트)
  3. CoreDNS 재시작 시 순간 장애 완화 — 로컬 캐시가 마지막 TTL 동안 응답

Q. 장애 대응에서 가장 먼저 봐야 할 3가지?

  1. kubectl get events -A --sort-by=.lastTimestamp | tail -30
  2. kubectl get pods -A --field-selector=status.phase!=Running
  3. 대시보드에서 apiserver·etcd의 p99 레이턴시와 에러율

이 세 가지로 "어디가 망가졌는지 큰 그림"을 2분 안에 파악합니다.

Q. Operator를 직접 만들어야 할 때와 안 만들어도 될 때?

만들지 마라: 기존 리소스(Deployment·ConfigMap)로 충분. CI가 Helm으로 배포 가능.
만들어라: 도메인 리소스의 수명주기(DB 프로비저닝·백업·장애 조치)가 복잡하고 반복적. 사용자가 "이 추상"을 쓰고 내부를 모르기 원함.

Q. CI에서 kubectl을 직접 쓰면 안 되는 이유?

드리프트와 권한 남발. GitOps로 Git에 병합 → ArgoCD/Flux가 sync하는 것이 원칙. CI는 이미지 빌드·테스트까지, 배포는 CD(GitOps 도구)가. 긴급 조치가 필요하면 임시로 kubectl 사용 후 반드시 Git에 반영.

Q. Pod의 CPU throttle 없이 성능 잡으려면?

  1. limits.cpu 제거(또는 requests의 3배+) → 버스트 허용
  2. 커널 5.14+의 cpu.cfs_burst_us로 짧은 버스트 허용
  3. Guaranteed QoS 확보 → 전용 CPU 핀 (cpuManagerPolicy: static)

Q. K8s가 해결하지 못하는 문제 5가지?

  1. 나쁘게 짜인 애플리케이션 — 메모리 누수, 블로킹 호출은 여전히 아픈 일
  2. 데이터 무결성 — K8s는 Pod를 되살릴 뿐, 데이터 정합성은 DB 책임
  3. 보안의 사람 요소 — RBAC를 `*`로 풀면 아무 방어도 안 됨
  4. 비용 관리 — 오토스케일이 잘못 맞으면 오히려 돈이 빠른 속도로 빠짐
  5. 조직 문제 — 팀 경계·커뮤니케이션은 기술로 해결되지 않음

A.9실무 에피소드 — 현장에서 배운 것들

다음은 실제 K8s 운영 현장에서 빈번히 관찰되는 이야기들입니다. 교과서에 잘 안 나오지만 중요한 "감각"의 영역.

에피소드 1 · "배포는 금요일 3시 이후 금지"

이 관행의 이유는 단순합니다 — 주말에 장애가 나면 대응 인력이 줄고, 긴급 롤백이 힘들며, 고객 피해가 평일 대비 복구 늦어집니다. Kubernetes의 롤아웃이 아무리 정교해도 사람의 개입이 필요할 수 있는 변경은 대응 가능한 시간에 하는 것이 원칙. 회사마다 구체적 규칙은 다르지만, "목요일까지만 프로덕션 변경"이 여전히 일반적입니다.

에피소드 2 · "Pod가 갑자기 사라졌다"

Pod가 Terminating도 없이 목록에서 지워지는 경우. 대부분은 다음 중 하나:

  • 상위 Deployment가 삭제됨 (OwnerReference cascade delete)
  • 노드가 축소되며 배포된 것으로 판단, Karpenter가 consolidation
  • kubectl delete pods --all 같은 광범위 명령의 여파
  • ResourceQuota 초과로 Admission이 생성 단계에서 거부 (실제로는 "생성 후 삭제"가 아니라 "생성 안 됨")

감사 로그(kubectl get events로 부족하면 apiserver audit)가 유일한 진실입니다. 반드시 남기고 있어야 합니다.

에피소드 3 · "TLS 인증서 만료로 클러스터가 멎다"

자체 관리(kubeadm 설치) 클러스터에서 1년 주기로 찾아오는 사건. kubeadm certs renew를 잊으면 apiserver 내부 통신 인증서가 만료되어 모든 컴포넌트가 재인증 실패로 연쇄 다운. EKS는 AWS가 자동 갱신하므로 이 문제는 없습니다. 

# 확인
kubeadm certs check-expiration

# 갱신
kubeadm certs renew all

# 모든 컨트롤 플레인 Pod 재시작
systemctl restart kubelet

에피소드 4 · "성공한 배포가 되돌아왔다"

"방금 배포해서 v2.0이 됐는데 30분 뒤 v1.9로 돌아가 있다". 원인 후보:

  • ArgoCD가 Git을 단일 진실 원천으로 삼고 syncPolicy.automated.selfHeal: true로 설정됨 — kubectl로 수동 변경한 것을 "드리프트"로 판단해 Git 상태로 되돌림
  • 두 개의 Operator가 같은 리소스의 다른 필드를 건드려 반복 충돌
  • Helm operator와 수동 edit의 충돌

GitOps 환경에서는 수동 edit을 하지 말고, 꼭 해야 한다면 일시적으로 sync를 비활성화. argocd.argoproj.io/sync-options: Prune=false 같은 annotation 활용.

에피소드 5 · "로그가 사라졌다"

CrashLoop 중인 Pod의 로그를 보려는데 kubectl logs가 비어 있음. --previous도 비어 있음. 원인은 컨테이너 재시작 간격이 로그 수집 시간보다 짧거나, 로그 로테이션이 너무 공격적이기 때문. 대응: stdout 외에 중앙 로그(Loki/ELK)에 항상 전송, Pod 스펙에 충분히 긴 restartPolicy 조건.

에피소드 6 · "DNS는 바뀌지 않았는데 외부 API 호출이 갑자기 느려졌다"

CoreDNS가 문제가 아니라 conntrack 고갈로 새 연결이 드롭돼 재시도 지연이 쌓이는 경우. 노드의 /proc/net/nf_conntrack_count를 보면 nf_conntrack_max에 근접해 있을 것. 앱의 HTTP 클라이언트가 매 요청마다 새 연결을 만들고 keep-alive를 쓰지 않는 경우에 가속됩니다. 단기 처방 — conntrack 상향, 장기 처방 — 앱의 연결 재사용.

에피소드 7 · "노드를 추가했는데 Pending Pod가 안 줄어든다"

새 노드가 올라와도 Pod가 그 노드로 안 가는 경우. 가장 흔한 이유:

  • 새 노드에 아직 CNI Pod가 안 뜸 → Pod 네트워크 준비 안 된 상태로 "Ready이지만 NetworkReady=false"
  • 기존 Pod의 nodeAffinity가 구 라벨 기준
  • Taint가 설정된 노드인데 Pod에 toleration 없음
  • TopologySpreadConstraints가 이미 다른 AZ로 강제

에피소드 8 · "EKS 업그레이드 후 kube-proxy가 튕긴다"

EKS 컨트롤 플레인은 업그레이드했는데 kube-proxy add-on을 같이 업그레이드 안 한 상황. apiserver와 kube-proxy의 버전 편차가 2 마이너를 넘으면 증상 다양. 업그레이드 순서: 컨트롤 플레인 → add-on(kube-proxy, CoreDNS, VPC CNI) → 워커 노드. 순서를 지키면 대부분 무사.

에피소드 9 · "카프카 파티션 리더가 오락가락한다"

Kafka를 K8s에 올렸을 때 Pod 재스케줄링 시 리더 교체가 발생. 데이터 로컬리티 없이는 파티션 replica가 완전히 재빌드되고, 그 동안 리더가 이리저리 옮김. 해결: Strimzi Operator 사용 + local persistent volume + Pod를 특정 노드에 nodeAffinity로 묶기. 혹은 애당초 "Kafka를 K8s에 올리지 말고 MSK 같은 매니지드 사용".

에피소드 10 · "메트릭은 정상인데 고객은 느리다고 한다"

p50·p95는 정상, 그런데 p99가 튀는 경우. 평균에 묻힌 tail latency가 실제 사용자 경험. 도구: Prometheus histogram_quantile로 p99, 그리고 분포의 분포(p99 of p99 across shards)를 관찰. 원인: GC pause, CPU throttling, 노드 간 cross-AZ 홉, 특정 엔드포인트만 느림.

A.10쿠버네티스 시스템콜 수준 풀이

kubectl exec이 실제로 하는 일

1
kubectl이 apiserver에 POST
URL: /api/v1/namespaces/default/pods/web/exec?container=app&command=bash&stdin=1&stdout=1&stderr=1&tty=1. "Upgrade" 헤더로 SPDY/WebSocket 전환.
2
apiserver가 kubelet에 프록시
Pod가 있는 노드의 kubelet(10250)에 연결 → 똑같은 업그레이드 터널.
3
kubelet이 CRI Exec
containerd의 gRPC Exec() 호출. 컨테이너의 PID namespace 안에서 execve("bash").
4
새 프로세스가 컨테이너 안에서 생성
PID 1의 자식. 종료 시 signal이 PID 1에 전파.
5
stdin/stdout이 터널로 왕복
사용자 키 입력 → kubectl → apiserver → kubelet → containerd → bash. 역방향도 마찬가지.

이 경로 전부에서 한 곳이라도 막히면 exec이 실패합니다. 가장 흔한 차단점은 apiserver ↔ kubelet 사이의 10250 포트(보안그룹, NetworkPolicy).

Pod 간 통신 첫 패킷의 초정밀 해부

Pod A(10.244.1.5) → Pod B(10.244.2.9) 첫 TCP SYN의 여정 (Calico BGP 모드):

  1. App process가 connect(10.244.2.9:8080) syscall. 커널이 TCP 상태를 SYN_SENT로.
  2. 라우팅 결정 → 10.244.2.0/24 via <gateway> (CNI가 설치한 라우트).
  3. eth0(veth의 컨테이너쪽)로 패킷 송신 → veth의 호스트쪽으로 pass-through.
  4. 호스트 네트워크 스택 진입. netfilter PREROUTING은 L2 브리지를 통과하지 않는 L3 라우팅 경로라 건너뜀(Calico BGP의 특징).
  5. 호스트 라우팅 테이블에서 "10.244.2.0/24 via <other-node-IP>" 매칭 → eth0으로 송신.
  6. 언더레이 IP 네트워크(VPC)가 패킷을 다른 노드로 전달.
  7. 다른 노드 eth0 도착 → netfilter INPUT가 아닌 FORWARD 체인(이 노드의 다른 Pod로 가므로).
  8. 라우팅 → 10.244.2.9는 로컬의 특정 veth와 연결 → 그 veth로 송신.
  9. veth의 Pod쪽 → Pod B의 net namespace → eth0 수신.
  10. 커널 TCP 스택이 LISTEN 상태 소켓에 매치 → accept 큐에 enqueue → SYN_ACK 회신.

각 단계가 2μs~30μs 정도. 총 1ms 미만에 들어가는 게 정상입니다. 5ms 이상이라면 어딘가 병목.

왜 "kubectl port-forward"는 HTTP 프록시인가

kubectl port-forward pod/web 8080:80은 로컬 8080에 리스너를 열고, 들어온 연결을 apiserver → kubelet → Pod의 80으로 터널합니다. kubelet은 이를 Unix 파이프로 CRI에 전달해 컨테이너의 netns로 nsenter + socat 비슷한 일을 수행. 즉 네트워크 라우팅을 우회하는 응용 계층 프록시입니다. VPN·방화벽 뒤에서도 동작하는 이유.

A.13복합 장애 시나리오 — 사고 조사 기록

단일 원인 장애는 상대적으로 쉽습니다. 어려운 것은 여러 원인이 엮인 복합 장애입니다. 아래는 실제 장애 조사에서 자주 마주치는 복합 시나리오 5건을 조사 기록 형식으로 정리한 것입니다.

사고 A · "apiserver가 느리고 Pod도 느리다"

현상: 모든 kubectl 명령이 3초 이상 걸림. 동시에 여러 Pod가 간헐적으로 CrashLoopBackOff 진입. LB 에러율 0.5% 상승.

타임라인:

T+0
모니터링 알람
apiserver p99 레이턴시 5s 초과
T+2m
조사 시작
audit log에서 특정 SA가 분당 5천 건의 LIST 호출 — Operator 버그로 전체 pods를 매초 조회
T+5m
2차 파급
apiserver가 포화로 kubelet의 status 업데이트도 느려짐 → 일부 Pod가 NotReady 같은 상태로 오인돼 트래픽에서 제외
T+7m
대응 1
문제 Operator의 Deployment scale down to 0
T+10m
정상화
apiserver 지연 정상화 → 모든 Pod Ready 복구
T+30m
근본 해결
Operator 버그 수정 PR · 그 전까지 APF FlowSchema로 해당 SA 격리

교훈: apiserver 과부하는 자체로도 문제지만 kubelet status 업데이트 지연을 통해 서비스 가용성에도 파급됩니다. 단일 Operator 버그 하나가 전체 클러스터를 마비시킬 수 있음을 기억하세요. APF는 사전에 설정해 두는 것이 좋습니다.

사고 B · "CoreDNS 장애로 EKS 클러스터가 먹통"

현상: 모든 앱의 외부 API 호출 실패. 에러 메시지는 "no such host" 또는 타임아웃.

조사: CoreDNS Pod들이 모두 CrashLoopBackOff. Pod 로그에 "plugin/forward: no nameservers found".

원인 체인:

  1. CoreDNS ConfigMap의 forward . /etc/resolv.conf는 노드의 /etc/resolv.conf를 상위 DNS 목록으로 사용.
  2. 해당 날짜에 VPC DHCP 옵션 세트가 변경되면서 노드의 resolv.conf에 nameserver 라인이 삭제됨.
  3. CoreDNS가 재시작 시 새 설정을 로드하려 했으나 상위 서버가 없어 foward 실패 → probe 실패 → CrashLoop.
  4. 연쇄적으로 클러스터 DNS 전체 다운 → 모든 앱이 영향.

긴급 조치: Corefile의 forward 절에 명시적 IP(예: forward . 169.254.169.253 — AWS VPC resolver)를 하드코딩.

교훈: 인프라 변경(네트워크, IAM 등)은 K8s의 미묘한 의존성을 건드릴 수 있습니다. 외부 변경 → 클러스터 헬스체크를 체크리스트에 넣으세요. NodeLocal DNSCache가 있었다면 영향 범위가 줄었을 것.

사고 C · "새벽에 모든 Pod가 재시작됐다"

현상: 새벽 2시 17분에 갑자기 모든 애플리케이션 Pod의 restarts가 증가. 정확히 같은 시각. 서비스 3분간 불안정.

조사:

  1. kubectl get events에서 "NodeNotReady" → "NodeReady"가 전체 노드에 동시 발생
  2. 노드 kubelet 로그: "failed to reach apiserver"
  3. apiserver 로그: VPC DNS 해석 타임아웃 — 실제로는 노드 DNS를 통해 apiserver ELB로 가는 경로에 문제
  4. AWS Support: 해당 AZ의 VPC Route53 resolver 일시 장애 (3분)

왜 Pod가 재시작?: 노드가 NotReady로 떨어지자 node.kubernetes.io/not-ready taint가 추가되고, toleration이 없는 Pod가 evict. 복구 후 새 Pod가 다시 스케줄링.

완화: 모든 Pod에 다음 기본 toleration (K8s 기본값)

tolerations:
- key: node.kubernetes.io/not-ready
  operator: Exists
  effect: NoExecute
  tolerationSeconds: 300   # 5분 기다림
- key: node.kubernetes.io/unreachable
  operator: Exists
  effect: NoExecute
  tolerationSeconds: 300

기본 5분이지만, 짧은 네트워크 깜빡임에는 이 toleration을 600초 이상으로 늘리면 대량 이동을 피할 수 있습니다.

사고 D · "CSI 볼륨이 마운트되지 않는다"

현상: 새 Pod 생성 시 FailedMount가 지속. 기존 Pod는 문제없음.

조사:

  1. describe pod → MountVolume.MountDevice failed: rpc error: code = DeadlineExceeded
  2. kubelet 로그: CSI Node Plugin이 응답 없음
  3. CSI Node Pod(DaemonSet) 로그: IAM 인증 실패 "expired credentials"
  4. IRSA 역할의 Trust Policy가 최근 인프라 팀이 수정함 — OIDC sub 값에서 오타 ("serviceaccount" → "serviceAccount")

왜 기존 Pod는 문제 없었나?: 이미 마운트된 볼륨은 토큰 재발급 없이 사용. 새 마운트에만 STS 호출 필요. 이런 차이로 "일부 Pod만 실패"하는 기묘한 증상이 나타남.

교훈: IAM/RBAC 변경은 작은 오타 하나로 광범위한 영향. 변경 전 aws sts assume-role-with-web-identity로 실제 교환 성공 여부를 테스트.

사고 E · "Ingress는 200을 반환하는데 사용자는 502"

현상: 모니터링은 200이 90%, 502가 10%. 사용자 체감 에러율은 훨씬 높아 보인다는 CS 제보.

조사:

  1. ALB access log로 특정 클라이언트 IP의 502 비율 확인 → 10%가 아니라 40%
  2. 502가 나는 요청은 모두 10KB 이상 POST body
  3. ALB의 idle timeout(60s) vs 앱의 keep-alive(65s) 불일치로 ALB가 연결을 끊을 때 앱은 응답 쓰는 중
  4. 또한 ALB가 해당 Pod로 요청을 보낸 뒤 Pod가 SIGTERM을 받는 경합이 있음 (롤링 업데이트 시)

대응:

  • 앱 keep-alive 75s (ALB idle timeout + 15s 버퍼)
  • preStop hook sleep 10 + graceful shutdown으로 연결 드레인
  • ALB의 deregistration delay를 30초로 설정

모니터링 개선: K8s 메트릭(200)만 보지 말고 LB와 엣지의 응답 코드를 엮어서 관찰. 실제 사용자가 받는 상태는 LB 응답.

A.14마스터피스의 나머지 — 잊기 쉬운 주제 한 줄 정리

본문에서 자세히 다루지 못한 주제들을 "한 줄 힌트"로 정리합니다. 각각은 독립적으로 파고들 가치가 있습니다.

  • Vertical Pod Autoscaler의 3 모드 — Off(권장값만 계산), Initial(Pod 생성 시만 적용), Recreate(주기적으로 Pod 재생성해 적용). Recreate는 HPA와 상충.
  • API Priority and Fairness의 FlowSchema — 요청을 범주(flow)로 분류하고, PriorityLevelConfiguration이 공정 큐잉을 담당. 설정은 기본값 그대로도 훌륭.
  • ClusterTrustBundle (1.30+) — TLS CA 번들을 API 리소스로 배포. 이전의 kube-root-ca.crt ConfigMap 반 복제 방식 대체.
  • Pod Resize API (1.27 alpha, 1.32+ 예정 stable) — Pod 재생성 없이 리소스를 조정. 장기적으로 VPA의 Recreate 모드를 제거할 것.
  • SchedulerProfile — 하나의 kube-scheduler에서 여러 스케줄링 정책을 동시에 운영 가능.
  • KubeVirt — K8s에서 VM을 Pod처럼 오케스트레이션. 레거시 VM을 점진적으로 마이그레이션하는 데 활용.
  • Gang Scheduling (Volcano, Kueue) — AI·배치 작업의 "모든 Pod 동시 시작 또는 모두 실패" 의미. kube-scheduler로는 부족.
  • Readiness Gate — Pod의 Ready 조건에 외부 시스템 상태를 추가. AWS LB Controller의 헬스체크 결과가 이로 반영됨.
  • EphemeralContainers 주입의 SecurityContext — 디버그 컨테이너에도 PSS 적용됨. Restricted 네임스페이스에서는 kubectl debug가 거부될 수 있음.
  • Pod Readiness 확장 (ReadyzEndpoint) — apiserver의 /readyz는 구성 요소별 체크 상세. LB 헬스체크 대상.
  • Extended Resources — GPU, 커스텀 하드웨어 등 K8s 기본이 모르는 자원. Device Plugin으로 광고, Pod spec의 resources.limits에 명시.
  • Hugepage — hugepages-2Mi, hugepages-1Gi도 K8s 리소스. DB·JVM 성능 튜닝에 유용.
  • Binpacking vs Spreading — 스케줄러의 MostAllocated는 binpacking(노드 수 절약), LeastAllocated는 spreading(장애 분산). 워크로드 특성에 맞춰 선택.
  • Topology Aware Routing (1.23+) — Service endpoint slice를 "같은 존 우선"으로 힌트. 교차 AZ 트래픽 비용 절감. annotation service.kubernetes.io/topology-mode: Auto.
  • Kubernetes Generic Ephemeral Volume — emptyDir의 CSI 버전. PVC를 Pod 수명과 함께.
  • CSI Inline Volume — PVC 없이 Pod spec에 바로 CSI 볼륨 정의. Secret Store CSI가 대표.
  • Mutating Admission의 순서 — 여러 웹훅이 있을 때 순서에 민감. AdmissionConfiguration으로 reinvocationPolicy: IfNeeded 설정 시 순환 호출.
  • Server-Side Apply의 소유권 충돌 — 여러 Controller/CI/kubectl이 같은 필드에 쓰면 last-writer-wins가 아니라 에러. 명시적 --force-conflicts가 필요.
  • EndpointSlice Mirror — 구식 Endpoints 클라이언트 호환을 위해 EndpointSlice에서 Endpoints를 자동 생성. 외부 Service(selector 없는)는 이 반대도 있음.
  • ServiceInternalTrafficPolicy — Service 내부 트래픽이 항상 같은 노드의 Pod로만 가도록. internalTrafficPolicy: Local.
  • kubectl explain --recursive — 리소스 필드 계층 전체를 한 번에 출력. kubectl explain pod.spec --recursive | less.
  • CRI-O vs containerd의 차이 — 거의 동등. 커뮤니티 채택률은 containerd가 약간 우위. Red Hat 생태계는 CRI-O 선호.
  • Ephemeral containers의 targetContainer — 기존 컨테이너의 pid/net namespace를 공유. strace·gdb로 라이브 프로세스 진단 가능.
  • kubectl run의 제한 — 1.18부터 Deployment 생성 기능 제거. 지금은 kubectl run이 Pod만 만든다.
  • PodScheduling 리소스 (Kueue) — 대기 중인 Pod를 큐잉 관리. 할당량과 공정성을 배치 작업에 적용.
  • JobSet (alpha) — 여러 Job을 한 단위로 관리. ML 분산 학습 등 복잡한 작업에 적합.
  • ClusterAPI의 기본 개념 — Cluster, Machine, MachineDeployment는 K8s 리소스처럼 보이지만 다른 클러스터를 관리. "K8s로 K8s를 만든다".
  • kubectl plugin — kubectl krew install로 stern(멀티 Pod 로그), neat(YAML 정리), tree(owner 체인)등.
  • kubeconfig의 Exec 인증 — aws eks update-kubeconfig가 넣는 건 실제 kubectl 실행 시 aws eks get-token을 exec하는 플러그인 방식.
  • etcdctl snapshot — 백업은 반드시 etcdctl snapshot save로. 파일 시스템 복사는 일관성 보장 안 됨.
  • kube-bench — CIS Kubernetes Benchmark의 자동화. 클러스터 보안 상태를 점수화.
  • Conformance Tests — sonobuoy로 자신의 클러스터가 CNCF 인증 Kubernetes 규격에 맞는지 검증.
  • Downward API의 두 주입 방식 — 환경 변수 또는 볼륨. Pod의 status.podIP는 컨테이너 시작 시에만 결정되므로 env보다 볼륨이 안전.
  • GitOps의 Pull vs Push — Pull(ArgoCD가 Git에서)이 기본. Push(Jenkins가 kubectl)는 드리프트·보안 구멍이 많음. Pull은 클러스터 내부에서 실행되므로 외부에서 접근 가능 API 불필요.
  • Dashboard vs Lens vs k9s — 공식 대시보드는 기본, Lens/OpenLens는 데스크톱 앱, k9s는 TUI. 팀마다 선호 다름. k9s는 CLI 파워 유저에게 필수급.
  • Chaos Engineering (Litmus, Chaos Mesh) — 의도적으로 Pod·노드·네트워크를 망가뜨려 복원력 테스트. 프로덕션 전 단계에서 주기적으로.
  • Kubernetes Event Exporter — events를 Slack/Webhook으로 전달. 경보 통합에 유용.
  • Kyverno의 Mutation vs Generation vs Verification — 단순 검증 외에도 Secret 자동 생성, 이미지 서명 검증 등 폭넓은 정책 엔진.
  • ExternalDNS — K8s의 Ingress/Service를 Route53·CloudDNS 등에 자동으로 A/CNAME 레코드 생성.
  • Skaffold — 로컬 개발에서 코드 변경 → 이미지 빌드 → K8s 배포를 자동화. 개발자 경험 개선.
  • Telepresence — 로컬 프로세스를 원격 클러스터에 "가상으로" 주입. 디버깅 혁명.
  • Knative — K8s 위의 Serverless. "0으로 스케일" + CloudEvents. CNCF Incubating.
  • KEDA — 이벤트 기반 오토스케일러. SQS 큐 길이, Kafka lag, Prometheus 메트릭 등을 트리거로 HPA를 확장.
  • OPA Gatekeeper의 Rego — Kyverno와 경쟁. Rego 학습 비용이 있지만 정책 표현력이 매우 높음.
  • IaC 도구 비교 — Helm(템플릿), Kustomize(오버레이), Pulumi/CDK8s(실제 프로그래밍 언어), Jsonnet(데이터 언어). 환경·팀에 따라 선택.

A.15디자인 결정 Q&A — 아키텍트의 사고법

실무 K8s 설계에서 마주치는 "어떻게 해야 할까" 질문 15개. 정답이 아닌 사고 과정을 제시합니다.

Q. 네임스페이스를 팀당 하나, 환경당 하나, 아니면 팀×환경?

대규모 조직은 클러스터를 환경별로(prod-cluster, stage-cluster) 분리하고, 그 안에서 네임스페이스를 팀/앱 단위로 나눕니다. 중소 규모는 한 클러스터 + 네임스페이스에 환경 prefix(prod-shop, stage-shop). 중요한 것은 일관된 naming 컨벤션과 ResourceQuota로 팀 간 격리.

Q. 한 클러스터에 팀 100개, 팀 10개인 클러스터 10개 중 어느 쪽?

대형 단일 클러스터는 운영 부담이 낮지만 폭발 반경이 큼. 작은 클러스터 여러 개는 격리가 강하지만 운영 툴·ArgoCD·네트워크 설정 중복. 실무 해답은 보통 도메인별 / 컴플라이언스 요구별로 2-5개입니다. 예: prod, prod-regulated, stage, dev, sandbox.

Q. 같은 앱의 여러 인스턴스를 여러 Deployment로? 아니면 하나의 Deployment + 라벨?

여러 Deployment를 추천. 이유: 각자 독립된 롤링 업데이트, 독립된 HPA, 독립된 PDB. 하나로 합치면 "일부만 롤백"이 어려움. 다만 ConfigMap·Secret 등 공유 리소스는 공유해도 OK.

Q. ConfigMap을 코드 저장소에 둘까, 클러스터 운영 저장소에 둘까?

앱 설정(포트, 기본 로그 레벨)은 앱 저장소, 환경별 오버라이드(prod의 replica 수, 리소스 요청)는 매니페스트 저장소. Kustomize의 overlays 패턴. Helm도 values.yaml로 같은 분리를 구현.

Q. 로그 수집을 사이드카에 할까, 노드 DaemonSet에 할까?

노드 DaemonSet이 기본: 자원 효율, 앱에 영향 없음. 사이드카는 앱별 로그 포맷팅이 특수하거나 stdout 못 쓰는 경우. 하이브리드: DaemonSet + 특수 앱만 사이드카.

Q. Pod를 Deployment로, StatefulSet으로, DaemonSet으로 — 판단 기준?

stateless 교체 가능 = Deployment. 정체성 필요 = StatefulSet. 노드마다 1개 = DaemonSet. 단순합니다. 애매한 경우는 "정체성이 정말로 필요한가"를 묻기 — 단지 "데이터가 필요해"와는 다르다.

Q. Ingress Controller는 몇 개?

보통 용도별로 2-3개: 외부 공개용 · 내부 서비스용 · 관리용(metrics/admin). 각각 별도 IngressClass와 별도 ALB로. 한 개로 통합하면 보안 경계가 흐려짐.

Q. NetworkPolicy를 처음부터 default-deny로, 아니면 서서히?

신규 클러스터는 처음부터 default-deny가 권장. 기존 클러스터는 audit 모드(Cilium)로 먼저 트래픽을 관찰, 필요한 정책을 도출한 뒤 enforce. "큰 빅뱅" 적용은 반드시 부분 장애를 유발.

Q. Secret을 etcd 암호화 + External Secrets Operator 둘 다?

네. etcd 암호화는 "etcd 접근자에게 숨기기", External Secrets는 "Git에 시크릿을 안 두기". 목적이 다릅니다. 둘 다 해야 안전.

Q. Helm vs Kustomize vs Pulumi 중 어느 걸?

제3자 앱 설치 = Helm (오픈소스 차트 생태계). 자체 앱의 환경별 배포 = Kustomize (심플, GitOps 친화적). 복잡한 로직이 필요한 인프라 자동화 = Pulumi/CDK8s (진짜 언어 사용). 세 가지를 섞는 것이 일반적.

Q. Service Mesh는 언제 도입?

마이크로서비스가 20개 이상이고 다음 중 2개 이상 해당: (1) mTLS 강제 필요 (2) 세밀한 트래픽 분할/Canary (3) 분산 추적 자동화 (4) 재시도·서킷 브레이커를 앱 밖으로. 미만이라면 추가 복잡도가 이득보다 큼.

Q. 한 노드에 Pod을 얼마나 밀집시킬까?

인스턴스 크기 × 최대 Pod 수의 균형. 너무 작으면 "노드 HA" 비용 증가(한 노드의 작은 Pod만 죽는 확률이 낮아도 총 노드 수가 많아 확률 증가). 너무 크면 장애 반경 큼. 실무 감각: m6i.2xlarge(8 vCPU/32GB)에 30-60개 Pod 정도가 기동성과 비용의 sweet spot.

Q. 운영 노드와 개발 노드를 같은 클러스터에?

안 하는 것이 원칙. 자원 경합, 보안 경계 희미, 실수로 운영 영향. 명확히 분리가 힘들면 최소한 nodeSelector + taint + NetworkPolicy로 강하게 분리.

Q. 장애 시 "Pod 재시작"과 "롤백" 중 어느 걸 먼저?

최근 변경이 있었다면 롤백 (kubectl rollout undo). 변경이 없었다면 재시작(kubectl rollout restart)으로 상태 초기화. 재시작이 안 고치면 근본 원인 조사. "Have you tried turning it off and on again?"는 K8s에서도 유효합니다.

Q. 경보를 심볼릭(전체)으로 할까 서비스별로 할까?

양쪽 다: 심볼릭 경보(apiserver down, etcd down)는 중앙 팀이, 서비스별(에러율, 레이턴시)은 서비스 팀이. 경보는 피로를 부르기 쉬우므로 SLO 기반으로 진짜 사용자 영향만 울리게.

A.16가이드를 마치며

Kubernetes를 처음 배울 때의 혼란은 대부분 "왜 이렇게 많은 움직이는 부품이 필요한가"라는 질문에서 시작합니다. 이 문서가 말하려 한 것은 그 질문에 대한 구조적인 답입니다 — 선언적 상태 + level-triggered reconciliation + loosely coupled controllers라는 세 가지 설계 원칙이 모든 복잡함의 배후에 일관되게 흐릅니다.

책 한 권을 읽고 나면 바로 3년차가 되는 것은 아닙니다. 3년차는 수많은 장애, 수많은 새벽 호출, 수많은 롤백 뒤에 옵니다. 하지만 이 문서의 지도를 가진 채로 그 경험을 쌓으면, 같은 경험이 흩어진 단편이 아니라 하나의 원근법 위에 정리됩니다. 그것이 이 문서의 유일한 목표입니다.

"왜 그런가?"를 계속 묻는 엔지니어가 되기를. Kubernetes는 보답합니다.
